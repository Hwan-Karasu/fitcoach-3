# Decisions (ADR)

Продуктовые и UI-решения владельца живут в нормативном пакете,
`docs/PROJECT_STATUS.md` и `docs/ui/UI_STYLE_DECISIONS.md`. Здесь —
технические решения и правила, которые нельзя нарушать.

## Неизменные правила

1. Источник истины — нормативный пакет (`AGENTS.md`); build120 — read-only.
2. V1 офлайн и только для тренера.
3. TypeScript strict; новые `.js`/`.mjs` не добавлять.
4. UI не обращается к SQLite; чужая фича — только через `public.ts`.
5. Запись в БД — только через `WriterCoordinator`; CAS по revision;
   `publish` после commit.
6. Календарь, тренировка и Credit Ledger — независимая семантика; правки не
   уничтожают факты.
7. Удаление клиента — только через участников-владельцев; без участника —
   fail-closed.
8. Статусы `OPEN/PROPOSED/PLANNED` не повышать без доказательства;
   production DDL, миграция, overlay APK, release — только после gates.
9. В Git нет секретов, JKS/PEM, паролей, реальных БД и PII
   (`npm run secrets:check`).

## Журнал

### ADR-001. Свой журнал миграций у каждого владельца данных (2026-10)
- Проблема: несколько фич пишут в один dev-файл SQLite.
- Решение: таблица `<owner>_schema_migrations` на владельца, общий файл через
  `SharedSqliteDatabase`.
- Альтернативы: общий журнал — связывает релизы фич; отдельные файлы БД —
  ломают атомарные кросс-модульные транзакции.

### ADR-002. Жесты календаря на RNGH + Reanimated (2026-10-16)
- Проблема: PanResponder пересоздавался при перерисовке, конфликт со скроллом.
- Решение: react-native-gesture-handler (Tap / Pan после долгого нажатия),
  геометрия — `"worklet"`-функции, колбэки через `scheduleOnRN`.
- Альтернативы: PanResponder + refs — хрупко и без нативного приоритета жестов.

### ADR-003. Тесты на Node strip-types без Jest (2026-10)
- Проблема: нужен быстрый запуск тестов домена и dev-хранилищ.
- Решение: `node --experimental-strip-types --test`, SQLite через
  `node:sqlite`-адаптер; тесты с `.tsx` — в `apps/mobile/scripts`.
- Альтернативы: Jest + babel — тяжелее и медленнее, лишняя конфигурация.

### ADR-004. Сначала проверенные библиотеки; перетаскивание — react-native-sortables (2026-10-17)
- Проблема: владелец требует не писать своё, если есть проверенная библиотека; конструктору анкеты
  нужно перетаскивание вопросов (§27.8) с автопрокруткой и переносом между разделами.
- Решение: перед новым модулем искать библиотеки (совместимость с Expo 57 / Reanimated 4, активность,
  лицензия) и предлагать владельцу; для перетаскивания — `react-native-sortables` (MIT, Reanimated 3/4,
  Expo, `Sortable.Grid` + `Sortable.Handle` + `scrollableRef`). Разделы и вопросы — один плоский список.
- Альтернативы: самописный жест на RNGH (написан и удалён), react-native-draggable-flatlist (давно не
  обновлялся), reanimated-dnd / drax (меньше пользователей). Готового конструктора анкет под RN нет
  (SurveyJS Creator и json-schema builders — только веб), доменные правила анкеты остаются нашими.

### ADR-005. Системный каталог упражнений — снимок RepDB Free через конвейер (2026-10-17)
- Проблема: нужен системный каталог (Product §29 утвердил RepDB Free), но RepDB не может быть доменной
  моделью, а лицензия запрещает публиковать набор как датасет.
- Решение: закреплённый коммит RepDB скачивается в `vendor/repdb/` (вне git), сборка нормализует в реестр
  FitCoach со своими ID `sys:repdb:<id>` и русскими названиями; сгенерированный JSON хранится в приватном
  репозитории как часть приложения. Если репозиторий станет публичным — убрать сгенерированный JSON и
  `repdb-names-ru.json` из истории и собирать их при сборке. Подпись RepDB — в каталоге и карточке.
  Картинки встроены в приложение (офлайн), лежат в `apps/mobile/assets/exercises/` вне git; в git только
  карта путей. После клона: `npm run catalog:fetch && npm run catalog:build`.
- Альтернативы: free-exercise-db (Unlicense, но не утверждён продуктом), wger (CC-BY-SA, переводы
  неполные), только свои упражнения (тренеру долго заполнять).

### ADR-006. Нижние окна — @gorhom/bottom-sheet, правки вложенной структуры — immer (2026-10-17)
- Проблема: конструктор программы — глубокая структура и много нижних окон; самописные Modal-окна
  не тянутся пальцем и плохо работают с клавиатурой.
- Решение: `@gorhom/bottom-sheet` (`BottomSheetModalProvider` внутри провайдера темы в PrototypeShell),
  `immer` для чистых правок черновика. Старые самописные окна (анкета, фильтры каталога) переводить
  на библиотеку при следующих правках этих экранов.
- Альтернативы: оставить свои Modal (без жестов), zustand (глобальный стор не нужен — состояние экрана).

### ADR-007. Дневник тренировки: факты без FK на план; клавиатура, вибрация, экран, уведомления — модули Expo (2026-10-17)
- Проблема: T03 — факты подходов должны пережить правку плана (§48.5.7, TX-02); длинная таблица
  числовых полей под клавиатурой; таймер отдыха в фоне.
- Решение: владелец `training.execution` со своим журналом миграций; выполнение = слот
  (клиент, программа, неделя, плановая тренировка), факт = плановый подход в выполнении; ссылки на план
  без FK. Подтверждение подхода — чистые функции `ExecutionRules` (авто/ручной). Библиотеки (согласие
  владельца «используй всё что необходимо»): `react-native-keyboard-controller` (KeyboardProvider в
  PrototypeShell, KeyboardAwareScrollView), `expo-haptics`, `expo-keep-awake`, `expo-notifications`
  (таймер отдыха: в Expo Go корневой модуль падает на `ExpoTopicSubscriptionModule` — грузить только части
  `expo-notifications/build/*` лениво, см. `app/composition/expoRestSignal.ts`). Ячейка пишет значение через 0,7 с или при уходе фокуса,
  смена исхода сначала дописывает отложенные значения.
- Альтернативы: FK на плановые подходы (правка плана стирала бы факты), запись на каждое нажатие
  (подтверждение и таймер срабатывали бы на первой цифре), свой KeyboardAvoidingView (хуже на Android).

### ADR-008. Конструктор задаёт цель подхода, а не вес и отдых; повторы и RIR — диапазоны (2026-10-18)
- Проблема: окно упражнения в конструкторе прятало подходы; вес и отдых в плане владельцу не нужны.
- Решение (владелец): карточка упражнения — «Подходов», «Повторы» (или время/метры), «RIR»; вес — только факт
  дневника, отдых — в самой тренировке (барабан у упражнения). Повторы `reps..reps_max`, RIR `rir_min..rir_max`
  (миграция v6 планов с CHECK), ввод через `sanitizeRange`/`parseRange`. «⇄» заменяет упражнение новой
  идентичностью (§48.5.7 п. 1). Поле `loadGrams` в плане остаётся в схеме, но конструктор его не показывает.
- Альтернативы: оставить окно упражнения (лишний шаг), отдельное поле «до» для диапазона (длиннее карточка).

### ADR-009. Порядок программ и мезоциклов принадлежит клиенту (2026-10-18)
- Проблема: владелец запросил перетаскивание программ/мезоциклов; порядок одного участника не должен менять книгу другого.
- Решение: существующий react-native-sortables (Grid/Flex + Touchable), долгое нажатие перемещает, короткое открывает.
  Программы — `sort_position` участия (миграция v8), мезоциклы — их `position`. Новый элемент библиотеки без порядка сверху.
  Команда принимает полный список уникальных ID своего активного участия; проверка и запись в одной транзакции,
  уведомление после commit. Порядок — настройка отображения клиента, общая ревизия плана, выбор и факты не меняются.
- Альтернативы: порядок в общей программе (затрагивает других участников); частичный список (даёт одинаковые позиции);
  только React state (теряет порядок при перезапуске).

## Шаблон

### ADR-010. Контекстные стрелки недель у общего tab bar (2026-10-18)
- Проблема: владелец запросил стрелки недель на плавающей панели; разные экраны имеют разные правила перехода.
- Решение: активный экран регистрирует действия через WeekNavigationProvider, tab bar отображает их.
  Focus cleanup убирает чужой контекст при смене вкладки, края диапазона недоступны.
  Запись/выбор соответствующей тренировки остаются ответственностью дневника, не панели.
- Альтернатива: поиск текущего экрана из tab bar создаёт зависимость общего компонента от фич.

### ADR-011. Историческая матрица хранит структуру, факты остаются у execution (2026-10-18)
- Проблема: каждая реальная правка мезоцикла должна оставлять собственную датированную историю без двойного счёта.
- Решение: перед записью изменённых недель в той же транзакции сохранять один снимок прежнего мезоцикла
  для каждого изменённого участника. Снимок неизменяем, сохраняет ID; текущий план читается отдельно.
  Порт возвращает текущую и все исторические версии с периодами. No-op и rollback истории не добавляют.
- Альтернатива: копировать результаты в снимок — исправления фактов расходились бы и статистика удваивалась.

### ADR-012. Предпросмотр и сохранение используют одно правило конфликтов (2026-10-18)
- Проблема: перенос разницы по lineage раньше молча затирал персональный вариант, UI показывал только пропуски после Save.
- Решение: applyWithConflicts сравнивает исходную/новую/целевую структуру; default keep, адресные ключи явного replace.
  Preview читает одну revision без записи; Save повторяет расчёт под CAS в транзакции вместе с версиями.
  Решения хранятся в recovery и сбрасываются при изменении исходной правки/области/участников.
- Альтернатива: перезаписывать всю неделю при одном конфликте — теряются не относящиеся к операции персональные изменения.

### ADR-013. Персональные недели простой программы поверх базовых слотов (2026-10-18)
- Проблема: три области простого дневника требуют разных предписаний по неделям без изменения identity фактов.
- Решение: недельные структурные overrides сохраняют ID слота; локальные области меняют только их,
  ALL сохраняет прежнюю матрицу и меняет базу. Общий конструктор переносит разницу с default keep.
  Каноническая замена получает новые child ID; execution остаётся независимым владельцем.
- Альтернатива: заменить базу при каждой локальной правке — меняет другие недели и скрывает персональные варианты.

### ADR-014. Компактность: видимая высота 36–42, зона нажатия 48 через hitSlop (2026-10-18)
- Проблема: владелец счёл интерфейс слишком крупным; правило проекта требует зону нажатия ≥48dp.
- Решение: шрифты −10% единой таблицей, кнопки/поля/чипы 36–42dp, недостающее до 48 — `hitSlop` в общих
  компонентах (AppButton, AppIconButton, SegmentedControl, SelectionChip). Поле ввода 42 — осознанное отступление.
- Альтернатива: глобальный масштаб шрифта — в RN нет штатного, а ручные размеры экранов всё равно остаются.

### ADR-015. Значки фильтров каталога: силуэт из библиотеки, оборудование — свои SVG (2026-10-18)
- Проблема: строки и эмодзи плохо читаются; в lucide нет спортивного оборудования.
- Решение (выбор владельца): мышцы — react-native-body-highlighter 3.2.0 (MIT, на react-native-svg), подсветка
  группы акцентом; оборудование — свой набор SVG в стиле lucide (`equipmentGlyphs.tsx`), узкие тренажёры —
  общий значок. Нижние окна фильтров — BottomSheet экрана: BottomSheetModal после закрытия не открывался снова.
- Альтернатива: Tabler Icons — нет гири, гребного, брусьев, колец, TRX; эмодзи — отклонены владельцем.

### ADR-016. Цвет недели — вложенная тема, правка мезоцикла — через workflow (2026-10-19)
- Проблема: цвет типа недели должен окрашивать весь экран (шапка, панель, карточки); правка мезоцикла в
  конструкторе может убрать недели, у которых уже есть результаты (другой владелец данных).
- Решение: `tintPalette` + `PaletteOverride` (тот же контекст темы), экран сообщает тон через
  `useReportScreenTone`. Сохранение мезоцикла — `workflows/saveTrainingMesocycle.ts`: дневник проверяет результаты
  удаляемых недель (`WEEK_HAS_RESULTS`), планы пишут в той же транзакции; ID тренировок сохраняются.
- Альтернативы: перекрашивать каждый компонент пропсом — десятки правок; удалять недели без проверки — теряет факты.

### ADR-017. Выход из группы — флаг участия, а не разделение программы (2026-10-19)
- Проблема: убранный участник должен сохранить программу и результаты, но выйти из группы. У выполнений
  `program_id` неизменяем триггером дневника.
- Решение: миграция планов v15 `group_left_at`; группа считается глазами участника (`programById(…, viewer)`).
  Добавление — копия мезоциклов источника с тем же родством.
- Альтернатива: новая программа для вышедшего — пришлось бы переносить выполнения между программами.
  Техдолг: название программы общее.

### ADR-018. Группа — общий мезоцикл (родство), а не общая программа (2026-10-19)
- Проблема: у добавляемого клиента может быть своя программа — общий мезоцикл должен лечь в неё (как в 2.0), а
  клиент остаться в группе.
- Решение: группа = копии мезоцикла одного `lineage_id` в любых программах участников (v16 `group_left_at` у
  мезоцикла); размещение копии — `preferredPlacement` (текущая Расширенная → последняя Расширенная → участие).
  Заменяет ADR-017: v15 у участия не используется (колонка осталась в dev-схеме).
- Альтернатива: оставить группу программой и копировать без связи — клиент выпал бы из переключателя.

### ADR-019. Стиль «Зефирка»: общий стиль + темы только цвета; кнопки ровно 44 (2026-10-19)
- Проблема: владелец прислал новый дизайн (`zefirka-package/`): шрифт Manrope, радиусы, тени, палитра.
- Решение: стиль (радиусы, тени, отступы, размеры, 44) — общий модуль `shared/ui/theme/style.ts`; цвета — темы;
  «Зефирка» — тема по умолчанию вне генерируемого каталога (нормативный пакет не меняем); новая зависимость
  `@expo-google-fonts/manrope` с согласия владельца. Кнопки и поля ровно 44 — решение владельца, заменяет ADR-014.
- Альтернатива: «Зефирка» как единственная тема — владелец оставил темы для цветов.

### ADR-020. Библиотеки графиков и календаря диапазона (2026-10-20)
- Проблема: нужны столбчатые и линейные графики с нажатием и выбор диапазона дат в календаре; свои графики на SVG без
  интерактивности, системный диалог даты выбирает одну дату.
- Решение: `react-native-gifted-charts` (+`expo-linear-gradient`) для графиков и `react-native-ui-datepicker` для диапазона —
  обе через `expo install`, с согласия владельца; обёртки в `shared/ui/components` (`BarChart`, `LineChart`,
  `DateRangeCalendar`) с цветами и шрифтом из темы. Доменные расчёты (`trainingStats`, `exerciseProgress`) — наши.
- Альтернативы: `victory-native` (тянет Skia), `chart-kit` (слабая интерактивность), `flash-calendar` (нет выбора месяца и года;
  API не подтвердила), `react-native-calendars` (больше зависимостей, диапазон вручную).

### ADR-021. Пакетное чтение планов и занятий + кэш чтения плана (2026-10-20)
- Проблема: открытие экранов и переключение участников занимало секунды — план читался сотней запросов (мезоцикл → неделя → упражнение),
  занятия — по пять запросов на каждое.
- Решение: пять запросов на всю программу клиента (`PeriodizedStore.readMesocycles`), пакетное чтение занятий
  (`readExecutions`); кэш `getPeriodizedPlan` в репозитории, сбрасываемый в `publish`, со сверкой членства; оповещение
  `selectionOnly` для записи выбора. Регрессия — тест стоимости чтения (число обращений не зависит от размера данных).
- Альтернативы: кэш в экранах (дублирование и рассинхрон), SQL-представление/JSON-агрегат (сложнее проверить).
- Ограничение: запись планов обязана оповещать подписчиков (`publish`) — на этом держится сброс кэша.

### ADR-022. Состав переключателя читается по показанным данным, не по маршруту (2026-10-20)
- Проблема: при смене участника `clientId` меняется раньше загрузки плана; группа по паре «новый клиент + мезоцикл
  прежнего» пуста — блок «Участники» пропадал на ~270 мс, прокрутка клампилась.
- Решение: `ProgramScreen` отдаёт `shown` (клиент/программа показанных данных); состав и счётчик читаются по ним,
  подсветка — по `activeClientId`; видимость — `isGroupOfMesocycle`. Панель недель держит снимок плана вместе
  со статусами. Модель «мезоцикл → родство → копии» не менялась.
- Почему отказались: сброс/восстановление прокрутки таймером и `scrollTo` (маскирует причину); общий контекст выбора.

### ADR-023. История занятий: решения к UX-контракту v1.1 (2026-10-20)
