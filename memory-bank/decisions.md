# Decisions (ADR)

Продуктовые и UI-решения владельца живут в нормативном пакете,
`docs/PROJECT_STATUS.md` и `docs/ui/UI_STYLE_DECISIONS.md`. Здесь —
технические решения и правила, которые нельзя нарушать.

## Неизменные правила

1. Источник истины — нормативный пакет (`AGENTS.md`); build120 — read-only.
2. V1 офлайн и только для тренера.
3. TypeScript strict; новые `.js`/`.mjs` не добавлять.
4. UI не обращается к SQLite; чужая фича — только через `public.ts`.
5. Запись в БД — только через `WriterCoordinator`; CAS по revision;
   `publish` после commit.
6. Календарь, тренировка и Credit Ledger — независимая семантика; правки не
   уничтожают факты.
7. Удаление клиента — только через участников-владельцев; без участника —
   fail-closed.
8. Статусы `OPEN/PROPOSED/PLANNED` не повышать без доказательства;
   production DDL, миграция, overlay APK, release — только после gates.
9. В Git нет секретов, JKS/PEM, паролей, реальных БД и PII
   (`npm run secrets:check`).

## Журнал

### ADR-053. Таймер отдыха и чтения данных: причины замедлений и правила (2026-10-29)
Отсчёт таймера (UI-поток) замедлений не вызывал. Причины: (1) барабан `react-native-timer-picker` — FlatList ×3 с окном в 5 строк,
прыжок у края попадает в несозданные ячейки; теперь `FullWheelList` создаёт все ячейки, стили/колбэки стабильны. (2) Правка отдыха
«все недели» читала все мезоциклы клиента (дважды), перечитывала каждую неделю и готовила тысячи UUID: `readMesocycle` (один),
`writeWorkouts(current)` без перечитывания, `opsNeedIds` — ID только когда операциям они нужны. (3) Прокрутка к упражнению суперсета —
`measureLayout` от тела дневника вместо `onLayout.y` карточки внутри рамки. (4) Каждый подход заставлял скрытые экраны («Клиенты»,
история, статистика) перечитывать сводки и все подходы клиента: `useFocusGatedVersion` — пересчёт один раз при возврате на экран;
карточки «в работе» кэшируются до изменения клиентов/планов; `signalId` таймера хранится только в памяти (recover при старте сам
снимает свои сигналы через `clearOwned`) — подход пишет таймер одной транзакцией. Правило отдыха (владелец): «все недели
мезоцикла» меняют отдых и там, где другие повторы/вес; защищён только вручную заданный иной отдых; «все недели этого типа» — только тип.
Точечный сброс кэша планов по клиентам отклонён: ревизия программы общая для участников.

### ADR-052. Исправления аудита дня: дата уведомления календаря, внешний сброс кэша, черновики шаблонов (2026-10-28)
Уведомление календаря после «Отменить завершение» идёт за день самой записи (`StartedAppointmentRef.localDate`), а не тренировки:
дату тренировки правят после завершения. Окончательное удаление клиента меняет записи календаря в чужой транзакции, поэтому
composition root подписывает `calendar.notifyExternalChange()` на изменения клиентов (как `accounting.notifyExternalChange()`);
кэш диапазонов (`RangeCache`) перечитывается. `deleteTemplate` в той же транзакции удаляет черновики правки шаблона
(`template:<id>`, `builder:template:<id>`). AUD28-04 (решение владельца 2026-10-28): «Отменить завершение» возвращает списание — hook `unsettle` в календарной транзакции
компенсирует действующее USED связанным RETURNED и возвращает резерв того же пакета (запись снова как до завершения); следующее
«Проведена» списывает ровно один раз. Ручной `clearOutcome` календаря не менялся.

### ADR-051. Импорт через ИИ (образец + промпт) удалён; остаётся импорт Excel и образец для импорта (2026-10-28)
Решение владельца: схема «заметки + образец + промпт → внешний ИИ → Excel» работает плохо (ADR-049 в этой части отменён). Удалены промпт (`AI_WORKBOOK_PROMPT`), страница и справка `AiTableHelp`, `aiTemplate`/`copyText`
в порте файлов, строка «Образец и промпт для ИИ» и зависимость `expo-clipboard`. Оставлены импорт Excel и **образец для импорта**: `features/import/domain/ImportSample.ts` (лист-матрица в формате 2.0: название,
«Упражнение | Подход | Неделя N», «План | Пред. | Повт. | Кг | Дата», тренировки и подходы строками, 3 недели) — скачивается строкой «Скачать образец для импорта» в списке «Создать программу» и кнопкой
«Скачать шаблон» на экране переноса (`WorkbookFilesPort.template()`). Образец читается импортом без настройки (тест `import-sample.test.ts`). Синонимы заголовков плоской таблицы в импорте сохранены.

### ADR-050. Шаблоны открываются и правятся в привычных конструкторах (2026-10-28)
Решение владельца: нажатие на карточку шаблона любого вида открывает его в конструкторе новой программы, а «Открыть и изменить» — в том же конструкторе в режиме правки шаблона. Отдельный редактор
`TemplateEditorScreen` удалён. Режим правки — флаг `templateEditId` у обоих конструкторов, сохранение `updateTemplate` (программы, созданные по шаблону раньше, не меняются, §48.16 п. 4).
Черновик правки хранится под своим ключом (`mesocycleBuilderDraftKey`: `builder:template:<id>`; Простой — `template:<id>`).

### ADR-049. Импорт из заметок удалён; заметки переделывает внешний ИИ по образцу и промпту (2026-10-28)
Решение владельца: функция «Вставить из заметок» (TEXT-LOG, ADR-045/046/047) убрана — разбор свободного текста в приложении слишком хрупкий. Тренер отправляет ИИ
(ChatGPT, Claude и др.) свои заметки или чужую таблицу вместе с образцом «строка = подход» и промптом, получает файл .xlsx и импортирует его обычным импортом Excel.
Удалены `TextLogImport.tsx`, `TextWorkoutLog.ts`, тест `text-workout-log`, поля `ImportTable.source/cycle`, экспорты в `import/public.ts`. Сохранены `AiWorkbookTemplate.ts` (образец и промпт,
формулировки теперь про «заметки или таблицу»), `AiTableHelp` и копирование в буфер. Доступ: на входе в импорт (список «Создать программу» → «Образец и промпт для ИИ») и внутри сверки таблицы.
Миграция execution v4 (ADR-048) потребовала поправить тест I06: перенос строк в базу v2 идёт по общим колонкам.

### ADR-048. «Завершить тренировку» отмечает сегодняшнюю запись календаря; запись плана — пачками (2026-10-28)
Решение владельца 2026-10-28, пересматривает §48.31.2 п. 3 и 7 (запрет сопоставления дневника и записи): «Завершить тренировку»
отмечает запись календаря «Проведена». Одно явное правило (не скрытый matcher): дата тренировки = сегодня; запись того же клиента на
сегодня, `SCHEDULED` без исхода, уже началась; из нескольких — с самым поздним началом (`pickStartedPending`). Импорт с прошлой датой
или без даты календарь не трогает; не начавшиеся и будущие записи не трогаются. «Отменить завершение» (и смена «Завершена» на другой
исход) снимает исход только той записи, что отметила эта тренировка (`training_sessions.calendar_appointment_id`, миграция
execution v4), и только если он всё ещё «Проведена». «Пропущена»/«Отменена» дневника календарь не трогают. Исход и запись —
одна транзакция (`workflows/completeWorkoutWithAppointment.ts`, участники `outcomeParticipant` у календаря и дневника), учёт — тот же
`resolveIn` (ровно один USED); подсказка в дневнике. `LegacyDevImport` теперь допускает в цели колонки, которых нет в старой базе.
Тот же день: `writeWorkouts` пишет только изменённые строки пачками (`upsertRows`/`deleteRows`), отсчёт таймеров идёт на UI-потоке
(`RestClock`), JS просыпается к `nextFinishAt`. На телефоне не проверено.

### ADR-047. Импорт из заметок: единый список упражнений, дубль без фактов, название тренировки отдельным шагом (2026-10-28)

Макет владельца: упражнения идут одним списком, у каждого пикер тренировки `1…N +`, внизу панель «Будет создано». Упражнение имеет
стабильный `id` (номер строки текста, копия — `<id>+<n>`); порядок списка — по тексту и не зависит от распределения. Номер дальше
последней тренировки создаёт пустые, в импорт они не попадают. «Дублировать» — плановая копия (`planSets`, строка без фактов): факты
не выдумываются; «Скопировать подходы» — отдельное подтверждённое действие. Название (обязательное) и дата тренировки — на следующем
шаге, когда всё разложено. Кнопка панели — «Далее»: запись идёт после сверки со справочником. «Похожие названия» — только оформление
(объединение внутри текста); справочник подключается на сверке. Схемы БД и миграций нет.
Уточнение (TEXT-LOG-4, после проверки build34): неделя и тренировка — разные оси. `LogWorkout.week` задаётся разбором (по датам хронологически,
без дат — неделя 1), у карточки два пикера: «Неделя» и «Тренировка» в неделе; «Дублировать» и корзина — на карточке, не в меню.
Уточнение (TEXT-LOG-5, решение владельца): пикер недели убран — неделя не отдельное решение, а следствие даты. `logWeeks` считает её из дат,
без дат — по порядку и «тренировок в неделю»; в карточке один пикер тренировки (на кнопках даты).

### ADR-046. Факты импорта правятся в черновике конструктора; sourceHash не пересчитывается (2026-10-28)

Просьба владельца: в карточке конструктора видеть и править факты импортированных тренировок. Блок «Факт по подходам» (Кг, Повт.)
есть только у циклов из Excel или заметок и меняет `imported.sessions` черновика до сохранения (`ImportedFacts.ts`); границы как у
импорта. `imported.sourceHash` — отпечаток исходного листа: по нему `applyWorkbook` узнаёт повторный импорт того же листа, поэтому
при правке он **не** пересчитывается (иначе ложный «Конфликт цикла»). После сохранения факты принадлежат тренировкам. Плановый вес в
карточку не возвращается (решение T02 в силе).

### ADR-045. Импорт тренировок из заметок через плоскую таблицу; Excel чужого формата — через внешний ИИ (2026-10-28)

Текст заметок разбирается (`TextWorkoutLog.ts`) в ту же плоскую таблицу `legacyFields`, что и матрица 2.0, и проходит обычные
`normalizeLegacyTable`, сверку и запись: новой схемы и миграций нет. Грамматика: строка с датой/«Тренировка…» — тренировка,
«вес на повторы» — подход, прочая строка с буквами — упражнение; недели календарные без пустых, лист на 52 недели; похожие
названия только предлагаются. План повторений — по типу цикла (CYCLE-PRESETS: сила 6–8, мощность 3–5, выносливость 12–15,
рекомпозиция 9–12, «Свой» — пусто), Excel сохраняет свои плановые значения. Чужой Excel не угадывается эвристикой: приложение даёт
образец «строка = подход» и промпт для внешнего ИИ (V1 офлайн), плюс однозначные синонимы заголовков.

### ADR-044. Прошедшая запись правится как будущая; пресеты дежурства — настройка вида (2026-10-27)

Решение владельца: время, тип, заметка и клиент прошедшей записи правятся в том же редакторе, что и будущей; исход — кнопки одним рядом. Домен: `updateAppointment(…, now)` принимает начавшиеся и COMPLETED записи без переписывания учёта и исхода; клиент меняется только `correctClient`/`linkGuestToClient` (компенсация RETURNED, ADR §22.1.4); тип с другим «требует списания» отклоняется; COMPLETED не переносится в будущее. Дежурство ставится касанием дня в шапке (`DutyDaySheet`, слияние `mergeDutyRange`); именованные диапазоны (≤ 8) хранятся в `AppearanceSetting.dutyPresets` рядом с `dutyColor`, без новой таблицы и DDL (не факт клиента, в окончательное удаление клиента не входит).

### ADR-043. Отказ от прямой миграции 2.0 → 3.0 (2026-10-27)

Решение владельца после аудита готовности: установка 3.0 поверх 2.0 с переносом всех данных не делается (готово ≈ 30 %, оставалось 4–8 недель). Единственный путь переноса — Excel-импорт/экспорт тренировок (ADR-042). Удалены `scripts/r02`, `r03`, `r04` и их тесты/команды, кандидат хранилища истории питания 2.0, `ClientWorkDataModel`. Сохранены R06 (бэкап 3.0), D01 (схема), чтение Excel 2.0. Питание, замеры, оплаты, календарь 2.0 в 3.0 не переносятся.

### ADR-043. Статус импортированных тренировок определяют записи (2026-10-27)

Уточнение владельца к правилу I06 («импорт завершает все тренировки»): оно отмечало завершёнными и будущие тренировки, которые ещё не начинались. Теперь запись — любое значение результата (повторы, вес, время, дистанция, в том числе в дропе или стороне подхода). Тренировка с записью завершена; пустая тренировка недели, где записи есть, тоже; неделя без записей целиком остаётся «не начата» (занятий для неё не создаётся). Исход, явно записанный в файле 3.0 («Пропущена», «Отменена», «Завершена»), сохраняется. Уже импортированные программы не менялись (повтор импорта разрешён, их можно импортировать заново). Чистая функция: `features/import/domain/TransferCompletion.ts` (`hasRecord`, `settleImportedSessions`); применяется в `compileWholeWorkbook` (библиотека) и в `cycleTransfer` (конструктор).

### ADR-042. Новый движок импорта и экспорта Excel (2026-10-27)

Решение владельца: переписать движок вместо исправлений. Читать файлы 3.0 и 2.0; повторный импорт той же книги тому же клиенту всегда разрешён (новая программа); экраны и порт `TrainingTransferPort` остаются; новые таблицы, прежние квитанции и сопоставления игнорируются. Из этого следует: квитанции, отпечатки, хеш каждой строки и круг через XLSX убираются; идентификаторы — случайные UUID через `Map`; проверка — чистая `validateTransfer` над моделью. Читатели файлов (`TrainingWorkbook`, `MatrixWorkbook`, `VisibleMatrixWorkbook`, `LegacyExcel`, `LegacyMatrix`) остаются как есть. План и срезы S1–S5: `docs/IMPORT_ENGINE_V2.md`.

### ADR-041. Импорт книги — пакетная запись и общий канонический JSON (2026-10-27)

На телефоне каждый запрос SQLite идёт через мост Expo, а `localeCompare` на Android Hermes идёт через платформенный Collator. Поэтому новые недели Расширенной программы и результаты импорта пишутся пачками (`shared/db/BatchInsert.ts`, ≤900 параметров), а канонический текст для хешей квитанций (`shared/training-transfer/CanonicalJson.ts`) запоминает порядок ключей по форме объекта. Порядок и вывод `canonical` менять нельзя: от них зависят сохранённые хеши повторного импорта; эталоны закреплены в `canonical-json.test.ts`. Замер на устройстве: ≈ 72 → ≈ 30 с на книге из 2880 результатов (dev).

### ADR-040. Удаление тренировки с импортированными результатами сначала спрашивает (2026-10-27)

Решение владельца (вариант А). В конструкторе до первого сохранения убранная тренировка с импортированными результатами без выбора действия отклоняет сохранение `WEEK_HAS_RESULTS` и ничего не пишет; `DELETE` не записывает эти результаты, `KEEP_HISTORY` записывает их историей удалённого плана (`origin`, `plan_deleted_at`). Так же ведёт себя правка сохранённого цикла. Раньше сохранение проходило молча и оставляло статус `COMPLETED` для тренировки, которой нет в плане. Код: `createTrainingTransfer.ts` (`resultsOfRemovedWorkouts`); тесты: `training-transfer.test.ts`.

### ADR-039. Одна версия TypeScript в корне и в приложении (2026-10-27)

Корень и `apps/mobile` используют TypeScript 6.0.3 (раньше 5.8.3 и 6.0.3). Основание: корневые скрипты компилируются 6.0.3 без ошибок, `typescript-eslint` 8.71.2 допускает версии `<6.1.0`; `typecheck`, `lint`, `arch:check`, `test:foundation` 1392/1392, `excel:test` 90/90 зелёные на 6.0.3. Новых библиотек нет.

### ADR-038. Ручная копия держит runtime lease до окончания публикации (2026-10-23)

Отдельный online-backup reader и внешний publisher входят в одну принятую runtime
команду; восстановление ждёт её полностью. Уход с экрана лишь снимает подписку,
controller продолжает операцию и сохраняет состояние. Настройка OS-папки находится
в private JSON вне SQLite: restore не возвращает чужие разрешения и расположение.
Отмена picker не меняет папку, одноразовый экспорт не меняет её для будущих копий.
Успех только после receipt, связанного с точным snapshot. Expo Go/dev отключены
до обращения к LIVE. Native IO пока не доказан; R06/D05 остаются OPEN.

### ADR-001. Свой журнал миграций у каждого владельца данных (2026-10)
- Проблема: несколько фич пишут в один dev-файл SQLite.
- Решение: таблица `<owner>_schema_migrations` на владельца, общий файл через
  `SharedSqliteDatabase`.
- Альтернативы: общий журнал — связывает релизы фич; отдельные файлы БД —
  ломают атомарные кросс-модульные транзакции.

### ADR-002. Жесты календаря на RNGH + Reanimated (2026-10-16)
- Проблема: PanResponder пересоздавался при перерисовке, конфликт со скроллом.
- Решение: react-native-gesture-handler (Tap / Pan после долгого нажатия),
  геометрия — `"worklet"`-функции, колбэки через `scheduleOnRN`.
- Альтернативы: PanResponder + refs — хрупко и без нативного приоритета жестов.

### ADR-003. Тесты на Node strip-types без Jest (2026-10)
- Проблема: нужен быстрый запуск тестов домена и dev-хранилищ.
- Решение: `node --experimental-strip-types --test`, SQLite через
  `node:sqlite`-адаптер; тесты с `.tsx` — в `apps/mobile/scripts`.
- Альтернативы: Jest + babel — тяжелее и медленнее, лишняя конфигурация.

### ADR-004. Сначала проверенные библиотеки; перетаскивание — react-native-sortables (2026-10-17)
- Проблема: владелец требует не писать своё, если есть проверенная библиотека; конструктору анкеты
  нужно перетаскивание вопросов (§27.8) с автопрокруткой и переносом между разделами.
- Решение: перед новым модулем искать библиотеки (совместимость с Expo 57 / Reanimated 4, активность,
  лицензия) и предлагать владельцу; для перетаскивания — `react-native-sortables` (MIT, Reanimated 3/4,
  Expo, `Sortable.Grid` + `Sortable.Handle` + `scrollableRef`). Разделы и вопросы — один плоский список.
- Альтернативы: самописный жест на RNGH (написан и удалён), react-native-draggable-flatlist (давно не
  обновлялся), reanimated-dnd / drax (меньше пользователей). Готового конструктора анкет под RN нет
  (SurveyJS Creator и json-schema builders — только веб), доменные правила анкеты остаются нашими.

### ADR-005. Системный каталог упражнений — снимок RepDB Free через конвейер (2026-10-17)
- Проблема: нужен системный каталог (Product §29 утвердил RepDB Free), но RepDB не может быть доменной
  моделью, а лицензия запрещает публиковать набор как датасет.
- Решение: закреплённый коммит RepDB скачивается в `vendor/repdb/` (вне git), сборка нормализует в реестр
  FitCoach со своими ID `sys:repdb:<id>` и русскими названиями; сгенерированный JSON хранится в приватном
  репозитории как часть приложения. Если репозиторий станет публичным — убрать сгенерированный JSON и
  `repdb-names-ru.json` из истории и собирать их при сборке. Подпись RepDB — в каталоге и карточке.
  Картинки встроены в приложение (офлайн), лежат в `apps/mobile/assets/exercises/` вне git; в git только
  карта путей. После клона: `npm run catalog:fetch && npm run catalog:build`.
- Альтернативы: free-exercise-db (Unlicense, но не утверждён продуктом), wger (CC-BY-SA, переводы
  неполные), только свои упражнения (тренеру долго заполнять).

### ADR-006. Нижние окна — @gorhom/bottom-sheet, правки вложенной структуры — immer (2026-10-17)
- Проблема: конструктор программы — глубокая структура и много нижних окон; самописные Modal-окна
  не тянутся пальцем и плохо работают с клавиатурой.
- Решение: `@gorhom/bottom-sheet` (`BottomSheetModalProvider` внутри провайдера темы в PrototypeShell),
  `immer` для чистых правок черновика. Старые самописные окна (анкета, фильтры каталога) переводить
  на библиотеку при следующих правках этих экранов.
- Альтернативы: оставить свои Modal (без жестов), zustand (глобальный стор не нужен — состояние экрана).

### ADR-007. Дневник тренировки: факты без FK на план; клавиатура, вибрация, экран, уведомления — модули Expo (2026-10-17)
- Проблема: T03 — факты подходов должны пережить правку плана (§48.5.7, TX-02); длинная таблица
  числовых полей под клавиатурой; таймер отдыха в фоне.
- Решение: владелец `training.execution` со своим журналом миграций; выполнение = слот
  (клиент, программа, неделя, плановая тренировка), факт = плановый подход в выполнении; ссылки на план
  без FK. Подтверждение подхода — чистые функции `ExecutionRules` (авто/ручной). Библиотеки (согласие
  владельца «используй всё что необходимо»): `react-native-keyboard-controller` (KeyboardProvider в
  PrototypeShell, KeyboardAwareScrollView), `expo-haptics`, `expo-keep-awake`, `expo-notifications`
  (таймер отдыха: в Expo Go корневой модуль падает на `ExpoTopicSubscriptionModule` — грузить только части
  `expo-notifications/build/*` лениво, см. `app/composition/expoRestSignal.ts`). Ячейка пишет значение через 0,7 с или при уходе фокуса,
  смена исхода сначала дописывает отложенные значения.
- Альтернативы: FK на плановые подходы (правка плана стирала бы факты), запись на каждое нажатие
  (подтверждение и таймер срабатывали бы на первой цифре), свой KeyboardAvoidingView (хуже на Android).

### ADR-008. Конструктор задаёт цель подхода, а не вес и отдых; повторы и RIR — диапазоны (2026-10-18)
- Проблема: окно упражнения в конструкторе прятало подходы; вес и отдых в плане владельцу не нужны.
- Решение (владелец): карточка упражнения — «Подходов», «Повторы» (или время/метры), «RIR»; вес — только факт
  дневника, отдых — в самой тренировке (барабан у упражнения). Повторы `reps..reps_max`, RIR `rir_min..rir_max`
  (миграция v6 планов с CHECK), ввод через `sanitizeRange`/`parseRange`. «⇄» заменяет упражнение новой
  идентичностью (§48.5.7 п. 1). Поле `loadGrams` в плане остаётся в схеме, но конструктор его не показывает.
- Альтернативы: оставить окно упражнения (лишний шаг), отдельное поле «до» для диапазона (длиннее карточка).

### ADR-009. Порядок программ и мезоциклов принадлежит клиенту (2026-10-18)
- Проблема: владелец запросил перетаскивание программ/мезоциклов; порядок одного участника не должен менять книгу другого.
- Решение: существующий react-native-sortables (Grid/Flex + Touchable), долгое нажатие перемещает, короткое открывает.
  Программы — `sort_position` участия (миграция v8), мезоциклы — их `position`. Новый элемент библиотеки без порядка сверху.
  Команда принимает полный список уникальных ID своего активного участия; проверка и запись в одной транзакции,
  уведомление после commit. Порядок — настройка отображения клиента, общая ревизия плана, выбор и факты не меняются.
- Альтернативы: порядок в общей программе (затрагивает других участников); частичный список (даёт одинаковые позиции);
  только React state (теряет порядок при перезапуске).

## Шаблон

### ADR-010. Контекстные стрелки недель у общего tab bar (2026-10-18)
- Проблема: владелец запросил стрелки недель на плавающей панели; разные экраны имеют разные правила перехода.
- Решение: активный экран регистрирует действия через WeekNavigationProvider, tab bar отображает их.
  Focus cleanup убирает чужой контекст при смене вкладки, края диапазона недоступны.
  Запись/выбор соответствующей тренировки остаются ответственностью дневника, не панели.
- Альтернатива: поиск текущего экрана из tab bar создаёт зависимость общего компонента от фич.

### ADR-011. Историческая матрица хранит структуру, факты остаются у execution (2026-10-18)
- Проблема: каждая реальная правка мезоцикла должна оставлять собственную датированную историю без двойного счёта.
- Решение: перед записью изменённых недель в той же транзакции сохранять один снимок прежнего мезоцикла
  для каждого изменённого участника. Снимок неизменяем, сохраняет ID; текущий план читается отдельно.
  Порт возвращает текущую и все исторические версии с периодами. No-op и rollback истории не добавляют.
- Альтернатива: копировать результаты в снимок — исправления фактов расходились бы и статистика удваивалась.

### ADR-012. Предпросмотр и сохранение используют одно правило конфликтов (2026-10-18)
- Проблема: перенос разницы по lineage раньше молча затирал персональный вариант, UI показывал только пропуски после Save.
- Решение: applyWithConflicts сравнивает исходную/новую/целевую структуру; default keep, адресные ключи явного replace.
  Preview читает одну revision без записи; Save повторяет расчёт под CAS в транзакции вместе с версиями.
  Решения хранятся в recovery и сбрасываются при изменении исходной правки/области/участников.
- Альтернатива: перезаписывать всю неделю при одном конфликте — теряются не относящиеся к операции персональные изменения.

### ADR-013. Персональные недели простой программы поверх базовых слотов (2026-10-18)
- Проблема: три области простого дневника требуют разных предписаний по неделям без изменения identity фактов.
- Решение: недельные структурные overrides сохраняют ID слота; локальные области меняют только их,
  ALL сохраняет прежнюю матрицу и меняет базу. Общий конструктор переносит разницу с default keep.
  Каноническая замена получает новые child ID; execution остаётся независимым владельцем.
- Альтернатива: заменить базу при каждой локальной правке — меняет другие недели и скрывает персональные варианты.

### ADR-014. Компактность: видимая высота 36–42, зона нажатия 48 через hitSlop (2026-10-18)
- Проблема: владелец счёл интерфейс слишком крупным; правило проекта требует зону нажатия ≥48dp.
- Решение: шрифты −10% единой таблицей, кнопки/поля/чипы 36–42dp, недостающее до 48 — `hitSlop` в общих
  компонентах (AppButton, AppIconButton, SegmentedControl, SelectionChip). Поле ввода 42 — осознанное отступление.
- Альтернатива: глобальный масштаб шрифта — в RN нет штатного, а ручные размеры экранов всё равно остаются.

### ADR-015. Значки фильтров каталога: силуэт из библиотеки, оборудование — свои SVG (2026-10-18)
- Проблема: строки и эмодзи плохо читаются; в lucide нет спортивного оборудования.
- Решение (выбор владельца): мышцы — react-native-body-highlighter 3.2.0 (MIT, на react-native-svg), подсветка
  группы акцентом; оборудование — свой набор SVG в стиле lucide (`equipmentGlyphs.tsx`), узкие тренажёры —
  общий значок. Нижние окна фильтров — BottomSheet экрана: BottomSheetModal после закрытия не открывался снова.
- Альтернатива: Tabler Icons — нет гири, гребного, брусьев, колец, TRX; эмодзи — отклонены владельцем.

### ADR-016. Цвет недели — вложенная тема, правка мезоцикла — через workflow (2026-10-19)
- Проблема: цвет типа недели должен окрашивать весь экран (шапка, панель, карточки); правка мезоцикла в
  конструкторе может убрать недели, у которых уже есть результаты (другой владелец данных).
- Решение: `tintPalette` + `PaletteOverride` (тот же контекст темы), экран сообщает тон через
  `useReportScreenTone`. Сохранение мезоцикла — `workflows/saveTrainingMesocycle.ts`: дневник проверяет результаты
  удаляемых недель (`WEEK_HAS_RESULTS`), планы пишут в той же транзакции; ID тренировок сохраняются.
- Альтернативы: перекрашивать каждый компонент пропсом — десятки правок; удалять недели без проверки — теряет факты.

### ADR-017. Выход из группы — флаг участия, а не разделение программы (2026-10-19)
- Проблема: убранный участник должен сохранить программу и результаты, но выйти из группы. У выполнений
  `program_id` неизменяем триггером дневника.
- Решение: миграция планов v15 `group_left_at`; группа считается глазами участника (`programById(…, viewer)`).
  Добавление — копия мезоциклов источника с тем же родством.
- Альтернатива: новая программа для вышедшего — пришлось бы переносить выполнения между программами.
  Техдолг: название программы общее.

### ADR-018. Группа — общий мезоцикл (родство), а не общая программа (2026-10-19)
- Проблема: у добавляемого клиента может быть своя программа — общий мезоцикл должен лечь в неё (как в 2.0), а
  клиент остаться в группе.
- Решение: группа = копии мезоцикла одного `lineage_id` в любых программах участников (v16 `group_left_at` у
  мезоцикла); размещение копии — `preferredPlacement` (текущая Расширенная → последняя Расширенная → участие).
  Заменяет ADR-017: v15 у участия не используется (колонка осталась в dev-схеме).
- Альтернатива: оставить группу программой и копировать без связи — клиент выпал бы из переключателя.

### ADR-019. Стиль «Зефирка»: общий стиль + темы только цвета; кнопки ровно 44 (2026-10-19)
- Проблема: владелец прислал новый дизайн (`zefirka-package/`): шрифт Manrope, радиусы, тени, палитра.
- Решение: стиль (радиусы, тени, отступы, размеры, 44) — общий модуль `shared/ui/theme/style.ts`; цвета — темы;
  «Зефирка» — тема по умолчанию вне генерируемого каталога (нормативный пакет не меняем); новая зависимость
  `@expo-google-fonts/manrope` с согласия владельца. Кнопки и поля ровно 44 — решение владельца, заменяет ADR-014.
- Альтернатива: «Зефирка» как единственная тема — владелец оставил темы для цветов.

### ADR-020. Библиотеки графиков и календаря диапазона (2026-10-20)
- Проблема: нужны столбчатые и линейные графики с нажатием и выбор диапазона дат в календаре; свои графики на SVG без
  интерактивности, системный диалог даты выбирает одну дату.
- Решение: `react-native-gifted-charts` (+`expo-linear-gradient`) для графиков и `react-native-ui-datepicker` для диапазона —
  обе через `expo install`, с согласия владельца; обёртки в `shared/ui/components` (`BarChart`, `LineChart`,
  `DateRangeCalendar`) с цветами и шрифтом из темы. Доменные расчёты (`trainingStats`, `exerciseProgress`) — наши.
- Альтернативы: `victory-native` (тянет Skia), `chart-kit` (слабая интерактивность), `flash-calendar` (нет выбора месяца и года;
  API не подтвердила), `react-native-calendars` (больше зависимостей, диапазон вручную).

### ADR-021. Пакетное чтение планов и занятий + кэш чтения плана (2026-10-20)
- Проблема: открытие экранов и переключение участников занимало секунды — план читался сотней запросов (мезоцикл → неделя → упражнение),
  занятия — по пять запросов на каждое.
- Решение: пять запросов на всю программу клиента (`PeriodizedStore.readMesocycles`), пакетное чтение занятий
  (`readExecutions`); кэш `getPeriodizedPlan` в репозитории, сбрасываемый в `publish`, со сверкой членства; оповещение
  `selectionOnly` для записи выбора. Регрессия — тест стоимости чтения (число обращений не зависит от размера данных).
- Альтернативы: кэш в экранах (дублирование и рассинхрон), SQL-представление/JSON-агрегат (сложнее проверить).
- Ограничение: запись планов обязана оповещать подписчиков (`publish`) — на этом держится сброс кэша.

### ADR-022. Состав переключателя читается по показанным данным, не по маршруту (2026-10-20)
- Проблема: при смене участника `clientId` меняется раньше загрузки плана; группа по паре «новый клиент + мезоцикл
  прежнего» пуста — блок «Участники» пропадал на ~270 мс, прокрутка клампилась.
- Решение: `ProgramScreen` отдаёт `shown` (клиент/программа показанных данных); состав и счётчик читаются по ним,
  подсветка — по `activeClientId`; видимость — `isGroupOfMesocycle`. Панель недель держит снимок плана вместе
  со статусами. Модель «мезоцикл → родство → копии» не менялась.
- Почему отказались: сброс/восстановление прокрутки таймером и `scrollTo` (маскирует причину); общий контекст выбора.

### ADR-023. История занятий: решения к UX-контракту v1.1 (2026-10-20)
- Проблема: контракт истории расходился с PC и правилами проекта (время занятия, шапка, фильтры, удалённый план, детали, архивные упражнения).
- Решение: см. `docs/ui/HISTORY_UX_DECISIONS.md` — время по PC §48.86.10/13/17; название программы в подзаголовке шапки; пилюли + «Тренировка»;
  «план удалён» одним блоком; новый read-only экран деталей; архивные упражнения с аналитикой; пропущенные/отменённые с метками; единая функция рабочих подходов.
- Почему отказались: второй «‹» в теле экрана, новый pill «Область» только в истории, миграция снимка происхождения, кнопка «Начать занятие».

### ADR-024. Хронология занятий: общий кэш read-model и время занятия в сессии (2026-10-20)
- Проблема: четыре экрана читали всю историю клиента независимо (≈ 80 мс и 28 обращений на вызов в Node, ×N экранов); время занятия не хранилось.
- Решение: `createTrainingHistory` кэширует расчёт по клиенту (параллельные читатели — один Promise; сброс при коммитах дневника клиента и изменениях его планов, кроме
  `selectionOnly`; ошибка не кэшируется). Время — `started_at/finished_at` у сессии (миграция v9), длительность не хранится, считается `sessionDurationSec`.
- Почему отказались: кэш в экранах (рассинхрон), хранение длительности (расхождение с отметками), время из `created_at/updated_at` (запрещено PC §48.86.10).

### ADR-025. Цели питания: «Расчёт» справочный, ручной ряд = активная цель (2026-10-20)
- Проблема: вкладка «Цели» (N03) и «предложение коридоров» (П6) расходились с привычным UX 2.0 (расчёт и ручная корректировка двумя рядами) и с UX-контрактом v1.1 (NUT-FS-04: предложение целей убрать).
- Решение (владелец): сегменты «Расчёт · Дневник · Статистика»; в «Расчёте» два ряда `NutritionTargetRows`: «Расчёт» (ккал и Б/Ж/У по формулам, только чтение, цель не меняет) и «Вручную» (min–max = действующая цель, `saveVersion` с сегодняшней даты на 7 дней,
  подтверждение, если на сегодня цели различались по дням). Коридоры §49.8, дни недели, версии и исключения сохранены: экран «Цели по дням недели» (`NutritionTargetsScreen`) открывается кнопкой. `proposeCorridors`/допуск удалены.
  Пол, возраст (из даты рождения) и рост — из карточки клиента (миграция clients v7 `sex`); вес и % жира — Measurements; профиль расчёта хранит только параметры расчёта (nutrition v7).
- Почему отказались: автоприменение предложения (§49.10 п. 1 требует явной команды, v1.1 запрещает); вкладка «Цели» (владелец); второй источник пола/роста в профиле расчёта (расхождение с карточкой).
- Поправка к Product Contract: §49.10 (П6) и §49.2 (структура вкладок) — вынести в пакет через source-gate; сам контракт не менялся.

### ADR-029. Цель дня = расчёт или ручная корректировка; рецепт по правилу ADR-028 (2026-10-21)

### ADR-030. Решения владельца по аудиту «Тренировок» (2026-10-21)
- Проблема: `docs/TRAINING_AUDIT.md` — четыре решения, нужные для исправлений TRN-005/014/015/020.
- Решение (владелец): (1) сокращение недель Простой программы с результатами — вопрос, не запрет; результаты остаются в истории (`WEEKS_HAVE_RESULTS` → подтверждение); (2) «0 повторов» недопустим, как тренировка без упражнений: ячейка подсвечивается и сохранение не проходит (ноль килограммов допустим); (3) «Отмена» в Простом конструкторе оставляет черновик; (4) правка существующего мезоцикла применяется к нему же: историческая версия — только при структурной разнице (§48.9.1 п. 4), название и настройки версию не создают, без изменений ничего не пишется.
- Технически: предварительные значения после копирования недели (`origin = COPY`) тренировку «В работе» не делают и `started_at` не ставят (§48.24, §48.34 п. 3); соответствие подходов при распространении правки — по месту в исходной неделе (`setSources`), не по месту в результате.
- Почему отказались от альтернатив: запрет сокращения недель — владелец выбрал вопрос; ID подходов в целевых неделях разные, поэтому сопоставление по ID «после» невозможно.

### ADR-031. Два пути правки Расширенной программы остаются; общий контракт инвариантов (2026-10-21)
- Проблема: аудит `docs/TRAINING_AUDIT.md` (TRN-009) — конструктор мезоцикла (`mesocycleSave`) и правка недели (`saveWeek`) записывают структуру по-разному; расхождения давали дефекты (TRN-004, 005; `saveWeek` убирал тренировку с результатами молча).
- Решение: не сливать. Это разные инструменты. Конструктор — декларативная правка своего мезоцикла открывшего клиента (экран показывает все недели, область применяется до сохранения). Правка недели — распространение по области и участникам с предпросмотром адресных конфликтов (§48.6, §48.22). Общий контракт для обоих и для любой новой записи структуры: (1) CAS по ревизии программы; (2) историческая версия мезоцикла — только при структурной разнице, одна на сохранение (§48.9); (3) тренировка с результатами не исчезает из плана без явного выбора тренера — иначе `WEEK_HAS_RESULTS`; выбор (решение владельца 2026-10-21): «Удалить с результатами» (окончательно, §48.30) или «Сохранить в истории» (выполнения получают снимок происхождения, как при «Удалить план, сохранить историю», §50.3); (4) факты не копируются и не переносятся; (5) черновик чистится при публикации и при удалении объекта. Инварианты проверяет workflow (`saveTrainingMesocycle`, `saveTrainingWeek`) в одной транзакции с дневником, а не экран.
- Почему отказались от альтернатив: объединение путей сложнее и рискованнее (разные модели — «целый мезоцикл» против «набор операций по родству»), а все найденные дефекты были нарушением общих инвариантов, а не самой раздвоенности.

### ADR-032. Переключатель участников и стрелки недель — слоты нижней панели навигации (2026-10-22, заменяет прежний ADR-032)
- Проблема: смена мезоцикла сдвигала экран программы, когда полоса участников появлялась/исчезала в раскладке экрана. Замеры на телефоне отвергли варианты: закрепление внутри прокрутки + `maintainVisibleContentPosition` (компенсацию при появлении полосы Android не делает, нажатия по закреплённой полосе теряются), JS-компенсация (всегда на кадр позже), резерв места (пустота), слой поверх экрана (перекрывает шапку).
- Решение: полоса участников — строка внутри нижней панели навигации (RootTabBar), а не часть экрана; кнопки панели ужимаются, высота панели прежняя (76 dp). Экраны кладут стрелки недель и строку в слоты (`shared/ui/components/TabBarSlots.tsx`, хранилище `slotStore.ts`) под своим `route.key`; панель показывает записи экрана в фокусе (`focusedLeafKey` по вложенному состоянию навигации). Записи снимаются только при размонтировании экрана. Экран, чьи данные грузятся позже самого экрана, объявляет `TabBarPending` («ожидается»): панель держит прежнее, пока запись не готова; `useWeekNavigation(state, ready)`, `null` — явное «стрелок нет». Переключатель участников есть и в программе, и в дневнике (docked).
- Почему отказались от альтернатив: очистка слота по событиям фокуса экранов давала кадры без стрелок при переходе программа → тренировка (кнопки меняли размер); привязка к `useFocusEffect` не гарантирует порядок «новый поставил — старый снял».
- Ограничения: если экран, объявивший `TabBarPending`, так и не запишет значение, панель будет держать прежнее (сейчас — только программа и дневник, оба записывают в штатных сценариях).

## ADR-032: настройки тренера — отдельный владелец Settings (key-value, CHECK по ключам)

Таблица `dev_settings(workspace_id, key, value_json, revision)`, ключи ограничены CHECK; повреждённое значение читается как «не сохранено». Фичи получают настройки не импортом `settings`, а контекстом/пропсом (тема — `ThemePersistence`, замеры — `GroupVisibilityPreference`), привязка в `SettingsBinding`. Новый ключ — миграция с расширенным CHECK.

## ADR-033: «Отменить» на Главной — компенсирующая запись, а не удаление

Возврат = `RETURNED +1` со ссылкой на списание (USED по записи или ADJUSTMENT −1). Один возврат на списание гарантирует уникальный индекс `source_entry_id`, а триггер проверяет, что источник — списание −1 того же клиента и пакета. UI передаёт id списания, которое видел тренер (`expectedEntryId`); расхождение → `ACCOUNTING_STALE`. Запись календаря при этом не меняется.

## ADR-034: карточка клиента и ответы анкеты — один workflow, одна транзакция

`workflows/saveClientCard.ts` вызывает `ClientCardParticipant` (Clients) и `AnswersParticipant` (Questionnaire) в общей транзакции; уведомления владельцев — после commit. Сбой ответов откатывает и создание/правку карточки (раньше карточка оставалась, а ответы нет). Вес остаётся отдельным шагом: он принадлежит Measurements и пишется через его порт.

## ADR-035: уведомления — планировщик чистой функцией, ОС приводится к расписанию календаря

Напоминания не хранятся как отдельное расписание: `planReminders` строит полный набор из календаря и настроек, `diffSchedule` приводит ОС к нему (отмена лишних, добавление недостающих, чужие идентификаторы не трогаются). Лента центра — таблица событий с identity `(workspace, sourceType, sourceId, eventKind, eventVersion)`, статус монотонен (триггер), удаление клиента — через участника. Наступившие напоминания показываются в ленте как актуальные, без утверждения о доставке Android (§54.5 п.3). Тихие часы подавляют напоминание без переноса; таймер отдыха отдельный сигнал.

## ADR-038: публикация внешней копии через Android API, локальный Expo module (2026-10-23)

Product §46.16 требует default Download/Дневник атлета без обязательного picker;
§46.25 отделяет manual create от export. JS Expo File.rename не поддерживает SAF
content URI. Локальный Kotlin module использует MediaStore.Downloads + IS_PENDING
для default API29+ и DocumentsContract partial/rename для выбранной папки.
Private sealed snapshot проверяется по SHA/размеру; readback предшествует успеху.
Нет новой сторонней библиотеки и storage-wide permissions. Expo Go не содержит
локальный native module; optional JS lookup даёт capability state. Автоподключение
и TS receipt binding проверены, native compile/IO/APK остаются OPEN, не закрываются
зелёным JS bundle. Контракт/проверки: `docs/spikes/R06_ANDROID_PUBLICATION.md`.

## ADR-037: restore journal перед boot и receipts после последующих записей (2026-10-23)

Recovery вызывается до создания/открытия рабочей базы. Private journal содержит
только version, UUID операции и SHA исходной/входящей базы; пути выводятся из
фиксированного private root. Отсутствующий LIVE и повреждённый journal блокируют
boot, а не создают пустую базу. Runtime ждёт целые команды, освобождает все owners
и workflow lease, закрывает DB, выполняет замену, затем reopen/cache reset.
COMPLETED/ROLLED_BACK receipts допускают законные поздние записи и WAL: их не
сравнивают с прежним SHA и не удаляют sidecars. Проверка sidecars выполняется
перед файловыми операциями незавершённого restore. Повторный boot не откатывает
данные после успешного восстановления. Без receipt hash-защита блокировала бы
поздние записи; ранний запрет любого WAL блокировал бы нормальное SQLite recovery.
Доказательства и открытые gates: `docs/spikes/R06_RUNTIME_LIFECYCLE.md`.

## ADR-036: таймеры отдыха — независимые, с паузой, возвратом в тренировку и сворачиванием к краю

Решение владельца 2026-10-22 (уточнено): сохраняется §48.62 — по одному таймеру на упражнение каждого участника, остальные не прерываются (повтор подхода перезапускает только свой таймер); один таймер — во всю ширину, два — рядом, больше — «Ещё N». Добавлено: пауза/продолжение у каждого (остаток `pausedLeftMs`, сигнал снимается и ставится заново), происхождение (`programId`, `weekIndex`, `plannedWorkoutId`) — нажатие на карточку или системное уведомление возвращает в ту тренировку с прокруткой к упражнению (полезная нагрузка — только идентификаторы, §44.22), свайп вбок сворачивает панель к краю с ближайшим отсчётом. Состояние таймеров хранится отдельно от экрана и идентифицируется участником и плановым упражнением. Промежуточный вариант «один таймер на устройство» (§44.3) был реализован и отменён тем же днём.
