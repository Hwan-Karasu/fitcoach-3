### Иерархия данных и источники истины


### Основной поток записи (ввод подхода)

`ValueCell.onChangeText` → `PendingInputWrites.set` + таймер 700 мс → `flush` → `useWorkoutDiary.saveSet` → очередь `enqueue` →
`execution.saveSet` → `WriterCoordinator.write` (CAS по `revision` факта, правило подтверждения, drops/sides, `started_at`) → commit →
`publish` → **подписчики**: сам дневник (`version+1` → полная перезагрузка), `ProgramWeeksPanel` под ним в стеке (статусы + все
выполнения программы), `activeWorkouts` (список «в работе»), `ProgramMatrixScreen` (если открыт), кэш истории (сброс) → `applyFact`
в дневнике ставит ACK сразу, затем приходит перезагрузка.

### Что сделано правильно (не трогать без причины)

- Факты отделены от плана: нет FK на план, идентичность защищена триггерами (`*_identity_fixed`, `*_slot_fixed`, `origin_fixed`);
  структурная правка физически не может удалить факт.
- Кросс-модульные операции (копирование, перестановка недель, удаление, сохранение мезоцикла) — workflows с одной транзакцией и
  уведомлением после commit; ревизионные токены предпросмотра (`revisionToken`) защищают копирование от устаревшего подтверждения.
- CAS по ревизии программы во всех структурных правках, по ревизии факта/сессии — в дневнике.
- Ограничения целостности в схеме: CHECK с `CASE`/`COALESCE` (подтверждение без значения невозможно), `json_valid`, триггеры дроп-сета и
  разминки, `UNIQUE(слот)` выполнения.
- История — ссылки на канонические факты, а не снимки (§48.5.7 п. 6); «Удалить план, сохранить историю» — неизменяемый снимок происхождения.
- Таймер отдыха — абсолютный `endAt`, очередь команд, отмена устаревшего сигнала, восстановление после смерти процесса.
- Перестановка недель — смена номера у тех же выполнений (без клонирования), с временной позицией против `UNIQUE(mesocycle, position)`.
- Пакетное чтение плана и выполнений (ADR-021: план ≤ 12 обращений, занятия ≤ 8) с тестом-сторожем `training-read-cost.test.ts`.

### Точки архитектурного риска

1. **Две реализации правки структуры Расширенной программы** с разной семантикой (TRN-009): `WeekEditorScreen` → `saveWeek`
   (участники, предпросмотр конфликтов, Recovery Draft, rebase) и `PeriodizedBuilderScreen` в режиме правки → `mesocycleSave`
   (весь мезоцикл, локальная `applyBuilderScope` без конфликтов, без черновика, версия всегда). «Изменить» на экране программы ведёт во вторую.
2. **Сопоставление подходов по позиции при распространении правки** (`patchSets`, TRN-001) — общая функция для всех областей применения.
3. **Реактивность «каждая запись → полная перезагрузка всех подписчиков»** (TRN-010): корректно по статусам, но дорого и с окном гонки.
4. **Два пути записи фактов** — дневник (очередь, ACK, отложенные ячейки) и матрица (без очереди, TRN-011).

## Часть II. Реестр проблем

Приоритеты: P0 — потеря/повреждение результатов, P1 — воспроизводимые ошибки основных сценариев и неверные статусы,
P2 — техдолг, производительность, ограничения, P3 — локальные улучшения. **P0 не найдено**: факты в БД ни в одном
обнаруженном сценарии не уничтожаются без явного подтверждения, кроме TRN-007 (редкий сценарий, P1).

### TRN-001. Правка с областью «эта и следующие / все / тот же тип» сопоставляет подходы целевых недель по позиции

- **Категория:** Business Logic / Data identity. **Приоритет:** P1. **Статус:** подтверждено (H1).
- **Файл:** `apps/mobile/src/features/training/plans/domain/PeriodizedRules.ts`, строки 148–151 (`patchSets`), 204–209 (`updateExercise`).
- **Описание:** при удалении подхода №2 из 4 в открытой неделе и области «эта и следующие» в целевой неделе остаются ID подходов №1–3,
  а ID №4 удаляется. Факты №1–3 показываются против плана, факт №4 пропадает из дневника и матрицы (остаётся в БД и истории).
- **Первопричина:** `diffWeek` описывает изменение подходов как новый массив значений (`patch.sets`), без идентичности строк;
  `patchSets` назначает ID «по месту» — `sets[index]?.id ?? newId()`.
- **Доказательства:** H1 — неделя 2 с фактами 1,2,3,4 повтора; после удаления №2 в неделе 1 (FOLLOWING) видимые факты `[1, 2, 3]`.
  Цепочка: `saveWeek` → `prepareWeekEdit` → `applyWithConflicts` (`WeekConflicts.ts:107`) → `applyWeekOps`. Та же функция работает в
  `applyBuilderScope` (`MesocycleBuilder.ts:294`), `saveSimpleWorkout` (`DevTrainingPlansRepository.ts:339`), перебазировании
  недельных отличий в `saveSimplePlan` (`:451`) и `rebaseDraft` (`DraftRebase.ts:8`).
- **Последствия:** нарушение §48.5.7 п. 2 и п. 5 («сопоставлять по устойчивым идентификаторам, не по позиции»): в целевых неделях
  результат «съезжает» на чужую плановую строку, выполненный подход скрывается из дневника; «Пред.» и прогресс-бар недели считают по
  видимым строкам. Добавление подхода в середину даёт тот же сдвиг.
- **Решение:** перенести идентичность подходов в операцию: в `diffWeek` для `sets` строить операции по ID (удалить/добавить/изменить
  подход), а в целевой неделе сопоставлять подход по его ID, если он присутствует в «до» (у Простой программы ID общие для недель),
  иначе — по порядковому номеру **среди совпавших** с базовой неделей; удаление — только того же подхода. Минимальный вариант:
  при одинаковой длине «до/после» оставить позиционное сопоставление, при изменении числа подходов сопоставлять по ID «до» → ID цели
  через позицию в «до», а не в «после».
- **Альтернативы:** хранить у подхода `lineageId` (как у упражнений) — устойчивое родство при копировании; дороже (миграция).
- **Риск исправления:** правило используется везде, где есть область применения; возможны регрессии в конфликтах (`conflictReason`
  сравнивает `shape` без ID) и в rebase черновиков.
- **Проверка:** тест H1 как регрессионный (ожидать `[1, 3, 4]`), то же для добавления подхода в середину, для Простой программы
  (FOLLOWING и ALL) и для `applyBuilderScope`.

### TRN-002. Черновик Простого конструктора не сохраняется после смены ревизии программы

- **Категория:** Business Logic / React State. **Приоритет:** P1. **Статус:** подтверждено по цепочке кода (динамически — частично: CAS
  `saveSimplePlan` отклоняет старую ревизию, покрыто существующими тестами).
- **Файл:** `apps/mobile/src/features/training/plans/presentation/SimpleProgramBuilderScreen.tsx`, строки 70–79, 99–117, 28.
- **Описание:** при восстановлении черновика экран берёт `revision = recovery.baseRevision`. Если программа изменилась после создания
  черновика (отдых упражнения из дневника — `setExerciseRest` увеличивает ревизию, правка из дневника, переименование), «Сохранить»
  всегда даёт `PROGRAM_REVISION_CONFLICT`, а сообщение советует «Откройте её заново — черновик сохранён»; при повторном открытии
  восстанавливается тот же черновик с той же старой ревизией — замкнутый круг. Выйти можно только через «Отменить несохранённые изменения» (потеря правок).
- **Первопричина:** у Простого конструктора нет перебазирования черновика на текущий план (в отличие от `SimpleWorkoutEditorScreen:62`
  и `WeekEditorScreen:106`, где есть `rebaseDraft` и `REBASED_NOTICE`).
- **Последствия:** нарушение §48.29 п. 5 (сохранение после восстановления); правки тренера невозможно опубликовать.
- **Решение:** при загрузке, если `recovery.baseRevision !== saved.program.revision`, перебазировать: `rebaseDraft(saved.base,
  recovery.draft, current)` по тренировкам (или хотя бы показать сравнение и предложить «Применить мои правки к текущему плану» с
  новой ревизией), затем выставить `revision = текущая`.
- **Риск исправления:** rebase унаследует TRN-001; нужен тест на правку отдыха между черновиком и сохранением.
- **Проверка:** тест экрана/хука или репозитория: черновик (rev 5) → `setExerciseRest` (rev 6) → сохранение проходит, отдых из
  дневника не потерян.

### TRN-016. Мемоизация строк подходов не работает

- **Категория:** Performance. **Приоритет:** P3. **Статус:** подтверждено статически; эффект — требует Profiler.
- **Файл:** `WorkoutScreen.tsx:790–795` — `target={{ exercise, set, position }}` создаётся заново на каждый рендер, `memo(SetRow)` не срабатывает.

- **Проверка:** React Profiler: при вводе в одну ячейку перерисовывается одна строка.

### TRN-017. Масштабирование записи Простой программы

  очистки после «Отмена» на согласование. Ожидаемо ли это владельцу — уточнить.

### Проверено — дефекта нет

- **Отмена удаления (сценарий F):** удаление тренировки в конструкторе меняет черновик только в `onConfirm`

- **Перестановка упражнений и суперсеты в дневнике:** ID сохраняются (`reorderExercises`, `applySupersetPress`), факты по ID.
- **Завершение/отмена завершения:** исход хранится отдельно, факты не трогаются; «Завершить» ставит окончание один раз.
- **Изменение структуры завершённой тренировки** не сбрасывает «Завершена» (статус = сохранённый исход), §48.5.7 п. 3, 8.

- **Календарь и абонементы:** модуль тренировок не пишет в них и не читает их (поиск по `features/calendar`, `features/accounting`); §48.39 соблюдён.
- **Окончательное удаление клиента:** оба участника тренировок зарегистрированы (`createDevServices.ts:190–192`).
- **Таймеры отдыха:** абсолютный `endAt`, интервал 250 мс только при видимых таймерах, очистка в cleanup.

**Ответы на итоговые вопросы**

- **Наиболее опасны:** TRN-001 (результаты в других неделях привязываются к чужим строкам и скрываются), TRN-004 (результаты недели
  незаметно отвязываются при правке в конструкторе), TRN-007 (удаление явно сохранённой истории), TRN-003/TRN-002 (потеря несохранённой работы).
- **Общие первопричины:** позиционная передача подходов в операциях; конструктор Расширенной программы как отдельный путь записи;
  `origin` факта не участвует в правилах; реактивность без различения своих записей (см. таблицу группировки).
- **Реализовано правильно:** разделение плана и фактов без FK с триггерами идентичности; workflows и одна транзакция; CAS; история как
  ссылки на канонические факты; перестановка недель без клонирования; таймер на абсолютном времени; пакетное чтение с тестом-сторожем.
- **Лучше не менять:** схему фактов и триггеры, `WriterCoordinator`-транзакции workflows, `RestTimerService`, `PendingInputWrites`,
  модель истории, `react-native-sortables` (замена не обоснована).
- **Рефакторинг оправдан:** запись правки мезоцикла из конструктора (TRN-009); общий хук записи фактов (TRN-011); `diffWeek/patchSets` (TRN-001).
- **Минимальными изменениями:** TRN-007 (одно условие), TRN-008 (флаг), TRN-005 (сравнение до записи), TRN-012 (`signature` без порядка),
  TRN-013 (ошибка в хуке), TRN-016 (стабильные пропсы).
- **Проявится при масштабировании:** TRN-017 (`json_tree` и построчная запись растут с числом клиентов), TRN-010 (стоимость ввода растёт
  с числом упражнений и подписчиков), справочник упражнений на каждый экран.
- **Максимальный эффект при минимальном риске:** этап 0 (регрессионные тесты из probe), затем TRN-007, TRN-008, TRN-005, TRN-006 и
  TRN-012 — каждая правка локальна и покрыта готовым сценарием.
