# ARCH-HARDEN-1 — архитектурная диагностика и оздоровление

Дата: 2026-11-11. Ветка `hardening/arch-audit-2026-11-11` (от `perf/week-participant-navigation`, `f324a09`).
Все замеры и тесты — на ПК (Node 24.3, V8, `node:sqlite`). **На телефоне ничего не проверялось, APK не собирался.**

## 0. Что отличается от исходного задания

Предполагаемый стек не совпал с фактическим. В проекте **нет** Fastify, PostgreSQL, Supabase, Sync Engine, Context/useReducer
и глобального стора: V1 — офлайн-приложение одного тренера (`AGENTS.md`). Поэтому пункты про «одновременные запросы к серверу» и
«согласованность с бэкендом» неприменимы, а «будущая синхронизация» вынесена в рекомендации (§7).

Кодовая база за 10–11 ноября уже прошла три аудита (`docs/CODE_AUDIT_2026-11-10.md`, `docs/REVIEW_FIXES_2026-11-10.md`,
`docs/BKP_AUDIT_2026-11-11.md`). Их находки здесь не повторяются; ниже — только новое.

Первая находка плана (≈31 проверка целостности на запуск) была независимо найдена и исправлена параллельной сессией, пока шло
планирование (`84454a0`, UIX-FIT-11a). Базовый замер это показал (3 проверки вместо ожидаемых 31), и срез 1a сведён к остатку.

## 1. Карта фактической архитектуры

```text
App.tsx → createRuntime (app/composition/createServices.ts) → ApplicationBootGate
  BootCoordinator: recoverBeforeOpen → prepareWorkspace → openDatabase → loadThemePreference → APP_READY
экран (presentation) → public.ts фичи → порт домена → Dev*Repository (data)
                     → workflows/ (запись нескольких владельцев одной транзакцией)
                     → read-models/ (производное чтение, без записи)
Dev*Repository → SharedSqliteDatabase (один файл, одно соединение, аренды) → WriterCoordinator (очередь записи)
              → IsolatedSqliteConnection: handle чтения + отдельный handle записи, BEGIN IMMEDIATE, WAL, foreign_keys=ON
```

- **Слои.** 14 фич (`domain → data → presentation`, наружу только `public.ts`), 13 workflow, 11 read-model. `npm run arch:check`:
  688 файлов, запретных импортов и циклов нет.
- **Источник истины** — только SQLite (`fitcoach_v3.db`), у каждого владельца свой журнал миграций (13 владельцев схемы,
  `app/composition/schema.ts`). Состояние экранов — React state и ограниченные кэши снимков (`useWorkoutSnapshot` — 12 слотов;
  `planCache` репозитория планов; кэш `trainingHistory` по клиенту). Конкурирующих хранилищ состояния нет.
- **Путь записи подхода:** `TextInput` → `PendingInputWrites` (пауза 700 мс) → `useWorkoutDiary.enqueue` (`SerialWriteQueue`, CAS по
  `revision` из ответа предыдущей записи) → `DevTrainingExecutionRepository.saveSet` → `WriterCoordinator.write` (одна транзакция) →
  `publish` после commit → подписчики. Экран обновляется из ответа записи (ACK), без перечитывания.
- **Кросс-модульная запись** (завершение тренировки + запись календаря, карточка клиента + анкета + вес, копирование недели,
  удаление программы) идёт через `WorkflowDatabaseLease.write` — одна транзакция на команду, уведомления после commit.
- **Обслуживание** (восстановление, копия): `RuntimeCommandGate` закрывает приём команд → `SharedSqliteDatabase.withClosedDatabase`
  → файловая операция при физически закрытой базе → повторная инициализация.

## 6. Оставшиеся риски

- H2 и H3 выведены из кода и документированного поведения платформы, на устройстве не подтверждены. Для H2 нужен лог `[startup]`
  с телефона: стадия `restore.recovery` с ненулевой длительностью подтвердит причину.
- После H2 при холодном восстановлении прерванной операции пользователь видит заставку, а не текст «Восстанавливаем данные»;
  при неудаче экран восстановления показывается как раньше.
- `integrityVerifiedAtOpen` — договорённость composition root: если кто-то передаст флаг для соединения, открытого без проверки,
  полная проверка целостности при запуске пропадёт. Закреплено тестом на путь без флага.
- R1–R8 из реестра.
- Замечания ревью (не блокирующие, не исправлялись): `lastCompleted` без `listCompletedDays` при сбое истории одного клиента оставляет плитку пустой у всех (в приложении метод есть всегда); сбой закрытия базы после неудачной инициализации репозиториев при повторе покажет «Проверка локальной базы не завершена» вместо исходной причины.
- Ревью не успело проверить: очистку частично взятых аренд внутри `repositories.initialize` при сбое и повтор `BootCoordinator.retry` в этом сценарии.
- Остаются открытыми пункты прежних аудитов: окно SAFE/rename при публикации копии, нативный хеш без проверки на устройстве,
  нет lint-правила `react-hooks` (CA-19).

## 7. Рекомендации

1. **Проверить на телефоне лог `[startup]`:** после H5 стадия `restore.recovery` у пользователя с восстановленной копией должна стать близкой к нулю.
2. **Пакетные чтения для сводок** (учёт, анкета, состав программ) — один запрос на владельца вместо запроса на клиента (R5).
3. **Измерять на устройстве, а не на ПК:** лог `[startup]` уже есть; добавить в него число SQL-операций запуска.
4. **Индексы под рост истории** (R3, R4) — после замера на базе реального размера, миграцией владельца дневника.
5. **Правило для отложенных записей:** любой новый ввод с паузой подключает `useFlushOnBackground` — стоит закрепить lint-проверкой
   или пунктом в `docs/ui/UI_STYLE_DECISIONS.md`.
6. **Синхронизация тренера и клиента (вне V1).** Текущая модель к ней частично готова: у фактов есть `revision`, отмена — статусом,
   идентификаторы — UUID. Не хватает журнала изменений (outbox) на уровне транзакции владельца и устойчивых к часам меток
   порядка; вводить их стоит до первого сетевого кода, а не вместе с ним.
