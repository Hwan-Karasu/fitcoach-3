# Z03 — переключение недель: профиль реального устройства и кэш снимков

Дата: 2026-10-25. Основа: `2d4382e9e9461c21934c814fb0217588d64d31fd`, ветка `perf/week-participant-navigation`. Точка возврата: `backup/before-week-cache-2026-10-25`. Предыдущая резервная ветка и bundle от 2026-10-24 сохранены.

Работа выполнена в рамках Z03. Входы — текущие публичные порты планов/выполнений, навигация и сохранённые результаты; зависимости по backlog Z02/T05/K02/S03. Product refs §§2, 7, 48, 56; источник «Пред.» — уточнение владельца от 2026-10-24. Схема БД и статусы общих Android/release/migration gates не менялись.

## A. Найденные причины и фактическая цепочка

1. `WorkoutScreen.changeWeek` выставлял busy, ожидал `finishInput` даже без несохранённых полей, менял параметры маршрута, затем снимал busy. Эти состояния запускали несколько проходов экрана.
2. `useWorkoutSnapshot` на каждую смену ключа повторял `findWorkout`, `getWorkoutWithPrevious`, `getConfirmationMode`; локального кэша выполнений недель не было. В исходном прогоне каждое возвращение к неделе давало 6–7 чтений, хотя структура программы уже была в существующем кэше репозитория.
3. Пока чтения выполнялись, параметры маршрута уже относились к новой неделе, а содержимое ещё было прежним. Рендерилось промежуточное состояние с новыми callback-функциями и прежними строками.
4. `ScreenTone.useReportScreenTone` использовал смену tone как зависимость focus-effect: cleanup снимал цвет, новый effect ставил следующий. Обновлялся общий Theme Context; на типичном переходе скрытый `TrainingProgram` делал 2 commits, тело `ClientHeader` рендерилось 6 раз.
5. `WorkoutSetRow.ValueCell` подстраивал локальный текст под новые сохранённые значения через effect после commit. В профиле: 36 рендеров `SetRow`, 75 рендеров `ValueCell` на типичном переходе с 12 строками.

Массовое размонтирование полей не подтвердилось: у `ValueCell` в измеренных переходах 0 mounts/unmounts. Ключи упражнений по lineage и строки по позиции уже существовали; их не заменяли. `diaryFields` уже имел WeakMap-кэш, повторную мемоизацию туда не добавляли.

`plan` в диагностике — длительность Promise до продолжения JS, а не чистое время SQLite: её нельзя целиком приписывать БД. Например, в одном исходном переходе plan занял 321 мс при execution 6 мс и Previous 3 мс; React Profiler зафиксировал 384 мс суммарной работы измеренных деревьев. Часть ожидания — занятый JS-поток.

Путь после исправлений: нажатие → проверка pending/очереди → для сохранённого актуального снимка синхронный выбор из кэша и совместное обновление тона/маршрута → один согласованный набор плана, фактов, Previous и режима → reconciliation полей без effect-перекладывания текста → commit/следующий JS frame callback. При холодном чтении остаётся цельный прежний снимок с его номером недели и блокировкой ввода до готовности нового.

## B. Изменения

- **Снимки недель:** `useWorkoutSnapshot.ts` хранит максимум 12 LRU-записей в пределах живого дневника. Ключ включает клиента, программу, неделю и workout ID; для разных мезоциклов workout ID различаются. Замена владельцев репозиториев очищает кэш. Попадание выбирается во время render без нового loading-effect и SQL.
- **Инвалидация:** подписки на планы и выполнения очищают затронутые области и незавершённые запросы. Собственный ACK возвращает в кэш актуальное выполнение текущей недели, а зависимое «Пред.» последующих недель перечитывается. Selection/order-only события не сбрасывают результаты. Ошибки не сохраняются как успешный снимок.
- **Асинхронная корректность:** поздний ответ может наполнить кэш своего слота, но не заменяет активный экран. Запрос, удалённый инвалидированием, не публикует устаревший снимок. Версия обновления/повтор после ошибки принудительно перечитывает текущий слот.
- **Сохранение:** `PendingInputWrites.dirty` и `SerialWriteQueue.unsettled` позволяют пропустить пустое ожидание. Наличие pending-поля, выполняемой команды или неучтённой ошибки обязательно сохраняет прежний путь `flushAll → settle` и блокировку перехода при сбое.
- **Поля:** `useInputDraft` сверяет текст с идентичностью слота до commit. Фокус/pending защищают ввод того же слота; смена слота всегда выбирает его сохранённое значение. Pending-ключи включают полный слот, что разделяет одинаковые set ID Простых программ разных недель. Внешняя непустая заметка остаётся видимой.
- **Тема и независимые части:** тон сбрасывается только при реальном уходе с экрана. Для кэшированной недели тон и маршрут публикуются вместе. `RetainedScreenTheme` удерживает палитру и элемент скрытого экрана программы до фокуса. Тело шапки мемоизировано; стабильные обработчики читают актуальные действия через ref, поэтому Back/Search/Edit не получают старые замыкания.
- **Дополнительно:** callback сохранения/подтверждения строки стабилен между неделями; данные невидимой картинки «Поделиться» вычисляются только при запросе картинки. Исходные правила прокрутки недель, положение вертикального ScrollView, структура и стили интерфейса сохранены.

Навигационные параметры обновляются по-прежнему: они нужны для редактора, перехода к участнику и возврата к программе. Альтернативный локальный маршрут не вводился.

Prefetch соседей и виртуализация не добавлялись: их польза в этом сценарии не подтверждена. Сначала устранены измеренные повторные чтения и commits. Стандартный `freezeOnBlur` проверен в установленном native-stack: на Fabric он специально не замораживает экран непосредственно под верхним; в итоговой реализации не используется.

## C. Измерения до/после

Реальный **realme RMX3706, Android API 36, Expo Go 57.0.9 / SDK 57, development mode**. Текущая программа с 3 участниками, 12 плановыми подходами и другими активными тренировками. Использовались реальные сохранённые данные; значения полей не менялись.

Один управляемый прогон вызывает тот же обработчик карточек недель в последовательности 1→2→3→1. Между завершёнными переходами — одинаковые 100 мс покоя вне измеряемого интервала. Снято по 30 переходов; первые 3 отделены от таблицы повторных переходов (остаётся 27). Начальная точка — открытый дневник, поэтому это не измерение cold start приложения.

Измеряются React Profiler commits/actualDuration, рендеры выбранных компонентов, время SQLite Promise, выбор карточки в layout-effect и завершение готового содержимого на следующем JS frame callback. Это **не аппаратное измерение физического показа кадра** и не задержка доставки нативного touch-события: начало — вход в обработчик выбора недели.

Проверка с настоящим SQLite отдельно подтверждает 0 чтений и 1 commit самого хука при повторном выборе актуального снимка. В нативном прогоне 25 из 27 тёплых переходов имели 0 общих чтений; два содержали по одному чтению категории `other`, их источник не установлен, к чтениям недели они не приписываются.

Первые два незагруженных перехода после изменения: 690/743 мс и по 6 чтений; возврат к уже загруженной первой неделе — 390 мс и 0 чтений. Холодное открытие остаётся заметно медленнее повторного.

Дополнительная проверка `useTransition` с отдельной предварительной подсветкой дала median 673.27 мс / p95 819.62 мс, 3 commits и 24 рендера строк вместо 12. Эта версия удалена; итоговый код соответствует более быстрому прогону. Это пример отвергнутой оптимизации с измеримой регрессией.

Android `gfxinfo` в контрольном окне выбранного варианта: 524 кадра, 35 janky (6.68%), frame p95 81 мс. Окно включает служебные кадры и прокрутку ленты недель; это не FPS только дневника. Сопоставимого исходного gfxinfo-окна нет, поэтому улучшение UI FPS не заявляется.

## D. Проверки регрессий

Успешно: `npm run typecheck`, `source:verify`, `arch:check`, `secrets:check`, `training:test` (**249 тестов**), query-registry, isolated SQLite connection и navigation-appearance.

Новые тесты проверяют реальный SQLite и React hooks: 1→2→3→1 без чтений после прогрева; согласованность displayed week и фактов; ACK веса и обновление зависимого Previous; структурную правку отдыха; другого участника; ограничение LRU; смену владельца БД; быстрые асинхронные переходы и запоздавшие ответы; ошибки и повтор; поле той же строки с одинаковым set ID в другой неделе; защиту pending-ввода и неучтённой ошибки очереди. Существующие сценарии RPE, дроп-сетов, сторон, таймеров отдыха, копирования/перестановки недель и сохранения фактов также прошли.

«Пред.» по-прежнему ограничен соответствующей тренировкой недели N−1 того же цикла и программы. Первая неделя пустая. Полная история упражнения не менялась.

Для воспроизведения аппаратного прогона:

```powershell
adb -s <serial> reverse tcp:8099 tcp:8099
node_modules/node/bin/node.exe --experimental-strip-types apps/mobile/scripts/navigation-profile-server.ts <output-directory>
```

Открыть дневник с неделями 1/2/3 в Expo Go → Open React Native dev menu → `Profile workout weeks (30)`. Прогон возвращает исходную неделю, не создаёт фиктивные результаты и не запускается автоматически. Отправка обезличенного профиля идёт только на loopback-приёмник через ADB; код меню активен только в development mode. Обычная работа приложения профилирование не включает.

## E. Ограничения

- Цель визуального выбора ≤100 мс **не достигнута в измеренном Expo dev-сценарии**; показатель выбора карточки не улучшился. Не утверждаем, что все задержки устранены.
- Нет release/profile-сборки и полной JS flame graph: установленный Expo inspector отвечал `-32601` на `Runtime.evaluate`; использованы программный React Profiler и нативные счётчики. Измерения dev нельзя переносить на release. Общий Z03 остаётся OPEN.
- Сравнение проведено для одного реального устройства и текущей группы из 3 участников. Отдельного аппаратного сравнения для 1/6 участников, полноценных JS/UI FPS до/после и всех возможных размеров программ нет.
- Первая загрузка недели остаётся медленнее; память кэша намеренно ограничена 12 снимками. После правок и вытеснения требуются свежие чтения.

Основания метода: [React Native DevTools / Profiler](https://reactnative.dev/docs/react-native-devtools), [предупреждение об overhead dev mode](https://reactnative.dev/docs/performance.html). Метрики относятся к зафиксированному окружению и сценарию выше.
