## Правило «Пред.» — уточнение владельца от 2026-10-24

Это уточнение заменяет прежний поиск последнего подтверждённого выполнения упражнения по датам внутри программы.

- Источник — соответствующая тренировка строго недели N−1 того же клиента, программы и мезоцикла.
- На первой неделе любого мезоцикла «Пред.» пустой, независимо от истории других циклов.
- В Расширенной программе соответствие тренировок и упражнений определяется однозначным lineageId; в Простой — стабильным ID.
- Повторение того же упражнения каталога в другой тренировке или другом слоте не является заменой.
- Нет соответствия, предыдущая неделя без результатов, замена упражнения, удалённая тренировка — пустое значение. Поиск в N−2 и других циклах/программах отсутствует.
- Только подтверждённые, неудалённые факты. Разминки, дроп-сеты, стороны и порядок подходов сопоставляются прежними правилами. Фактическая дата результата остаётся подписью; источник определяется номером недели.
- Полная история упражнения остаётся на экране упражнения; факты не удаляются.

Порт планов `findWorkout` дополнен `previousWorkout`; владелец планов выбирает источник в пределах найденного мезоцикла. `PreviousQuery.source` передаёт точную пару тренировка/упражнение, `null` запрещает подстановку. Прямой вызов без source поддерживает только стабильные ID Простой программы. Execution не читает таблицы планов.

## Изменения производительности

- План, текущее выполнение и режим подтверждения читаются параллельно. Новый `getWorkoutWithPrevious` использует один снимок текущего выполнения и автоматически добавляет его дополнительные разминки.
- Все источники «Пред.» читаются одним запросом по точным слотам, мини-сеты и стороны — пакетами. Запросы не выполняются отдельной цепочкой на каждое упражнение. После уточнения правила оконное ранжирование кандидатов больше не требуется.
- Для поиска тренировки и стрелок недель используется существующий кэш структуры программы; одновременные чтения программы, плана и группы объединяются. Ошибочные Promise удаляются из кэша; ошибка чтения не кэшируется как отсутствие программы.
- Стрелки сохраняют навигацию всего текущего цикла. Группа участников привязана к мезоциклу и удерживается между неделями, с обновлением при изменениях состава/структуры.
- Смена текущего слота фильтрует уже загруженные активные тренировки в памяти. Подписки на выполнения, планы и клиентов обновляют список при изменениях.
- Скрытые экран программы и панель статусов откладывают чтения до возвращения в фокус. Исходный план экрана программы повторно используется при переходе к участнику.
- Мемоизированы карточки недель и полоса участников; обработчики выбора и расчёт прогресса стабилизированы.
- Сохранение ввода перед переходом сохранено. Повторные переходы блокируются синхронно; запоздавшие ответы не подменяют новый слот. Ошибка открытия оставляет ввод заблокированным и предлагает повторную загрузку. Прежний состав группы во время загрузки другого участника не нажимается.

Новых зависимостей и изменений схемы нет. FlashList не внедрялся в редактируемый дневник.

## Замер до/после на компьютере

Синтетические данные: 1/3/6 участников, 8 недель, 3 тренировки в неделю, 6 упражнений по 4 подхода. В первых трёх неделях сохранены результаты. В каждом сценарии первый переход измерен отдельно, затем 30 повторений; оба алгоритма действительно загружают шесть значений «Пред.», что проверяется assert.

Node 24.3.0, SQLite в памяти. Время относится к загрузке данных, не включает React, сохранение полей и Expo/native overhead. Разница включает оптимизации и новое ограничение источника «Пред.». Это не оценка ускорения на телефоне.

| Сценарий | Участников | SQL повторного перехода до → после | Медиана, мс до → после | p95, мс до → после | Первый переход, мс до → после |
|---|---:|---:|---:|---:|---:|
| Неделя | 1 | 65 → 11 | 3.261 → 0.381 | 4.649 → 0.535 | 6.767 → 3.657 |
| Неделя | 3 | 107 → 11 | 12.188 → 0.348 | 14.118 → 0.455 | 14.882 → 9.275 |
| Участник | 3 | 109 → 13 | 12.360 → 0.370 | 14.193 → 0.584 | 16.383 → 1.189 |
| Неделя | 6 | 170 → 11 | 38.622 → 0.337 | 43.311 → 0.431 | 48.195 → 29.888 |
| Участник | 6 | 172 → 13 | 67.422 → 0.376 | 75.463 → 0.619 | 43.266 → 1.148 |

Первый переход участника идёт после сценария недель, поэтому часть кэшей уже прогрета: его нельзя называть cold start. В замере после оптимизации навигация и группа консервативно запрашиваются на каждый переход, хотя UI сохраняет их в пределах цикла.

Повторить текущий замер: `npm run bench:navigation`. Исходный замер получен до изменений репозиториев на резервном SHA: тот же скрипт без `--optimized`. Для воспроизведения baseline скопировать скрипт в отдельный checkout резервной ветки и запустить без этого флага; не запускать baseline-режим на новых репозиториях и не называть это исходным кодом.

## Проверки и оставшаяся проверка телефона

Успешно: `source:verify`, `typecheck`, `arch:check`, `training:test` (245 тестов), тесты query registry и isolated SQLite connection. Новые регрессии проверяют N−1, первую неделю каждого цикла, другого клиента/программу/тренировку, повторяющиеся упражнения, удалённый источник, разминки, отсутствие результатов, ошибки загрузки, быстрые смены слота, скрытый экран и стоимость чтений.

На подключённом Android/Expo Go открывались программа и дневник, выполнялись переходы недель. Metro подтвердил выдачу нового bundle. Численные замеры median/p95, 30 подтверждённых переходов каждого сценария и React-профиль с телефона не получены: локальное Hermes/CDP-соединение закрывалось с кодом 1006. Это ограничение проверки, не доказательство выполнения целевых −30% или отсутствия регрессии p95 на устройстве.

Добавлена выключенная по умолчанию диагностика в памяти. В консоли React Native DevTools:

```javascript
globalThis.__FITCOACH_NAV_PERF__.enable()
// Выполнить переходы недель и участников на экране программы и дневника.
globalThis.__FITCOACH_NAV_PERF__.snapshot()
globalThis.__FITCOACH_NAV_PERF__.enable(false)
```

Снимок содержит вид перехода, общее JS-время до следующего frame callback после готовности, SQL-чтения, React commits/actualDuration и отдельные фазы plan/execution/previous/flush/counterpart/statuses. Фазы могут перекрываться; их длительности не складываются в total. Это приближение готовности интерфейса, не аппаратное измерение физического показа кадра. При выключенном React profiling commits/reactMs не интерпретировать как измеренный ноль. Имена, ID клиентов, SQL и значения полей не собираются; хранится максимум 300 записей, сеть/БД не используются.

Для приёмки на телефоне: одинаковые данные и режим Expo до/после, первый переход отдельно, по 30 повторений четырёх видов переходов для доступных групп. Сначала без незавершённого ввода, отдельно — с сохранением поля. Сравнить median/p95, затем повторить на production-подобной сборке в рамках её gates. Условие −30% и отсутствие ухудшения одиночного сценария остаются непроверенными на устройстве.
