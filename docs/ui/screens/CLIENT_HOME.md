# Главная клиента — спецификация экрана


## Актуальное решение A02: КБЖУ (2026-10-20, прямые уточнения владельца)

Этот раздел заменяет прежние описания КБЖУ ниже, включая OPEN-05/06. Product refs: §§49.10–49.16;
уточнения относятся к главной клиента, исходный пакет документов сохранён как проверяемый baseline.

- Источники: пол, рост и дата рождения — карточка клиента; вес и % жира — Measurements; профиль цели/активности — Nutrition.
- Без % жира автоматические БЖУ — «—», без подстановки 80 % веса. Калории по Миффлину доступны при достаточных данных.
  Маленькая подсказка открывает непосредственно «Питание → Расчёт». Оценка ВМС применяется и сохраняется только явно.
- «Точно»: белок 1,7/2/2,1 г/кг сухой массы (поддержание/набор/похудение), жир 0,8 г/кг, углеводы — остаток 4/9/4.
- «Коридор»: автоматический белок ±10 % от точного расчёта, жир 0,8–1 г/кг сухой массы, углеводы — остаток по противоположным границам.
  Переключение меняет и автоматические верхние БЖУ, без заполнения нижних полей и без изменения суточного ориентира.
- Нижние поля первоначально пустые, подсказки короткие: «22» / «22–30». В них восстанавливается только явно сохранённый ручной ввод.
- Один ручной нутриент: Б → пересчёт У, Ж → пересчёт У, У → пересчёт Б. Жир меняется в последнюю очередь.
  Два ручных значения → третий по остатку. Автоматический жир ограничен 0,8–1 г/кг, ручной — нет.
- При одном/двух ручных значениях калории остаются исходными; при трёх равны сумме 4/9/4 (для диапазонов — сумма границ).
  Отрицательный остаток или недопустимый диапазон жира дают ошибку и блокируют сохранение, введённое не подменяется.
- Очистка поля возвращает автоматический режим. Явное «Сохранить БЖУ» атомарно сохраняет ручные поля, режим и итоговый снимок с сегодняшней даты.
  Ошибка записи сохраняет черновик; revision защищает от устаревшей записи. Переключение клиентов изолировано ключом компонента.
- Экран и все переходы «Цели по дням недели» удалены. Старые числовые цели, включая 120/60/200, не подменяют формулу главной.
  Исторические версии в хранилище не удаляются; только новые метаданные ручного ввода применяются к текущему расчёту главной.

Проверки: domain/SQLite — `nutrition-calc.test.ts`, `nutrition-targets.test.ts` (включая upgrade v9→v10, rollback и CAS).
На подключённом Android визуально подтверждены отсутствие кнопки расписания, пустые поля и расчёт 111/52/281 вместо 120/60/200;
переключение в «Коридор» показывает 100–122 / 52–65 / 240–292 при том же ориентире 2034 ккал, подсказка «22–30» помещается.
Полный Android сценарий сохранения/повторного открытия и все темы/масштабы шрифта пока не проверены.

## Источники данных

- Абонемент — Client Session Pack + Credit Ledger (§22.1.2–22.1.4), не старые плоские поля 2.0.
- Вес и шаги — факты замеров (`measurements`), запись дня исправляется, а не дублируется.
- «Тренировка» и «Трен./нед.» — дневник (`training.execution`), по фактической дате выполнения.
- КБЖУ — проекция модуля Nutrition: автоматический расчёт и явная ручная корректировка (актуальное решение ниже).
- Карта файлов 2.0 (только для инвентаризации функций): `features/clients/screens/ClientHomeScreen.tsx`,
  `ui/home/HomeStatTiles.tsx`, `HomePackPanel.tsx`, `HomeDailySection.tsx` (вес, шаги, тренировка),
  `HomeKbjuSection.tsx`. Модель абонемента 2.0 не переносить.

## Согласованность (из документа)

- UI меняет только подтверждённую сущность, без параллельных локальных источников истины.
- Быстрый ввод не списывает тренировку в Calendar / Credit Ledger.
- Правка одного поля не пересоздаёт весь экран.
- Переход на «Питание» сохраняет выбранного клиента.
- «К списку клиентов» — реальная навигация, а не сворачивание приложения (UI-OWN-003).
