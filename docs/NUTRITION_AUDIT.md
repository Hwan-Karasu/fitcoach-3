### Хранение

Один общий dev-файл SQLite, общий `WriterCoordinator`. Каталог (`dev_food_products`, `dev_recipes`) — на рабочее пространство;
всё остальное — `workspace_id + client_id` с FK на `dev_clients` (RESTRICT). Числа — целые десятые (`*_x10`), `NULL` = «нет данных».
Дневная запись хранит **снимок** (название, основа, значения на основу, количество, состав рецепта JSON) и nullable `override_*`
с базой количества; «съедено» вычисляется при чтении. Цели — датированные версии × 7 дней недели + исключения даты.
Все 11 клиентских таблиц подключены к окончательному удалению клиента (3 participant'а).

### Потоки

**Запись (добавление еды):** `NutritionDiaryScreen` → `onAdd` → `AddFoodScreen` (выбор → `pickSnapshot` → `planBatch`) →
`diary.addEntries(clientId, entries, now, commandId)` → `writer.write`: квитанция идемпотентности → по каждой записи `UUID`, `max(position)`,
`INSERT`, `SELECT` → квитанция → commit → `publish({clientId, localDate})` по датам.

**Чтение и реактивность:** подписчики `subscribeCommittedChanges` по `clientId`:
`useNutritionDay` (окно ±3 дня, кэш по дате с поколением `tick`), `DiaryWeekHeader` (неделя + месяц в модальном окне),
`NutritionHomeCards` (свой `useNutritionDay` на сегодня), `NutritionStatsScreen` (весь период + все замеры),
`AddFoodScreen` (каталог/недавние). Итоги дня пересчитываются чистой функцией `summarizeDay` из снимков — отдельного
хранимого итога нет, поэтому рассинхронизации «запись ↔ итог» в хранилище быть не может.

**Цель дня — два разных источника** (см. NUT-001): дневник и главная — `dayOrientation`/`deriveHomeMacroTarget`
от живого расчёта; статистика — сохранённые версии через `resolveTarget`.

## Часть II. Реестр проблем

P0 не обнаружено: потерь фактов питания, порчи снимков дневника или нарушения изоляции клиентов анализ и тесты не выявили.

### NUT-001 — Цель одного и того же дня в дневнике и в статистике считается по-разному

- **Категория:** расчёты / архитектура. **Приоритет:** P1. **Доказательность:** подтверждено (код + скрипт H2). Нужна позиция владельца.
- **Файлы:** `domain/HomeMacroTargets.ts:47-54`, `presentation/NutritionDiaryScreen.tsx:167-169`,
  `presentation/NutritionHomeCards.tsx:118-125`, `domain/NutritionStats.ts:86-94,110-113`, `presentation/NutritionStatsScreen.tsx:134-136`.
- **Описание:** «Итого: съедено/ориентир» в дневнике для **любой** даты берёт `dayOrientation`, который для источника `SCHEDULE`
  игнорирует сохранённые коридоры и пересчитывает их из **текущего** ориентира расчёта (вес, % жира, шаги за последние 7 дней,
  профиль). Статистика оценивает тот же день по сохранённой версии (`resolveTarget`).
- **Первопричина:** нет единого read-model «цель на дату». Логика выбора цели продублирована в двух вариантах.
- **Доказательство (H2):** версия от 2026-10-01 сохранена при 2000 ккал; ориентир расчёта сейчас 2400.
  Для 2026-10-05: дневник «ориентир» **2400**, статистика «цель» **2000**. Без сохранённой версии дневник показывает 2400,
  статистика — «цели нет» (`compared = 0`).
- **Последствия:** прошлые дни в дневнике «плывут» после каждого взвешивания; дневник и статистика противоречат друг другу.
  Прямо расходится с Product §49.11.4 («открытие прошлой даты показывает историческую цель… а не текущие нормы») и §49.12.2
  («приоритет распространяется на дневник, статистику… без копирования несовместимой логики»).
- **Решение владельца (2026-10-21):** цель = расчётный ориентир либо то, что тренер ввёл вручную. Значит, источник истины —
  `deriveHomeMacroTarget` (расчёт + ручная корректировка, действующая на дату через `homeAdjustment` версии). Статистика должна
  перейти на ту же функцию (оценка «в коридоре» и средняя цель), а не на сохранённые числа `days` версии. Отдельная ветка «особая цель
  на дату» не нужна (см. NUT-007). Принятое следствие: расчётная часть цели прошлых дней берётся из текущих данных расчёта.
- **Риск изменений:** главная (`NutritionHomeCards`) показывает «живую» цель из ячеек ввода до сохранения — это нужно сохранить как
  предпросмотр, а не как цель дня.
- **Проверка:** доменный тест «дневник = статистика» для дат до/после версии, с исключением и без версии (H2 как регрессионный).

### NUT-002 — Смена единицы продукта молча искажает все рецепты с этим продуктом

- **Категория:** баг / целостность данных. **Приоритет:** P1. **Доказательность:** подтверждено (код + скрипт H1).
- **Файлы:** `domain/FoodRules.ts:36-59`, `data/DevFoodCatalogRepository.ts:112-128`, `presentation/FoodEditorScreen.tsx:157`,
  `data/DevRecipeCatalogRepository.ts:32-44` (JOIN живых значений), `domain/RecipeModel.ts:11-15`.
- **Описание:** количество ингредиента хранится «в эталонных единицах продукта» (`quantity_x10`), а значения продукта читаются живыми.
  Правка продукта разрешает сменить `unit` (`G → PIECE/PORTION/ML`), и смысл всех сохранённых количеств меняется.
- **Доказательство (H1):** «Рис» 130 ккал/100 г, в рецепте 200 г → порция 260 ккал. После правки продукта на «1 шт.» с теми же числами
  порция того же рецепта — **26 000 ккал**. Никакой ошибки или предупреждения.
- **Последствия:** все будущие добавления рецепта в дневник любого клиента получают ложные значения. История не страдает
  (снимки), но ошибка незаметна до первого странного итога.
- **Решение:** в `DevFoodCatalogRepository.update` в той же транзакции запрещать смену `basis_unit`, если продукт есть в
  `dev_recipe_ingredients` (новая ошибка `FOOD_UNIT_LOCKED`); в редакторе — неактивный выбор единицы с подсказкой. Смена `amountX10`
  безопасна (пропорция) и остаётся разрешённой.
- **Риск:** нужен понятный путь «создать копию продукта с другой единицей».
- **Проверка:** H1 как тест хранилища: `update` с другой единицей при наличии рецепта → `FOOD_UNIT_LOCKED`, значения рецепта не изменились.

### NUT-003 — «Сохранить» записи с копиями в другие приёмы — три транзакции; после сбоя окно не даёт повторить

- **Категория:** SQLite / баг. **Приоритет:** P1. **Доказательность:** подтверждено (код + скрипт H4/H5).
- **Файлы:** `presentation/NutritionDiaryScreen.tsx:247-254`, `presentation/EntryEditorDialog.tsx:44-47,76-82`,
  `presentation/nutritionFormat.ts:74`.
- **Описание:** при выборе нескольких приёмов в окне записи выполняются `editEntry` → `addEntries` → `setOverride` для каждой копии —
  отдельные транзакции и отдельные публикации.
- **Первопричина:** у порта нет команды «изменить запись и создать копии», поэтому сценарий собран в UI.
- **Доказательство (H4):** после успешного `editEntry` и сбоя на втором шаге: запись уже 200 г с правкой белка, копий нет.
  Окно остаётся открытым со **старой** `revision` (`editing` в экране не обновляется) → каждое повторное «Сохранить» даёт
  `DIARY_STALE` с текстом «Дневник обновлён, повторите действие», хотя повтор невозможен до закрытия окна.
  (H5): копия получает правку по всем четырём показателям (`{2400,500,100,60}`), у оригинала правлен только белок —
  копия ведёт себя иначе при «Вернуть значения каталога» и пометке «Питательность изменена».
- **Последствия:** частично применённая команда (нарушение правила «одна транзакция на команду», §49.5.6); тупик в UI.
- **Решение:** добавить в `editEntry` поле `copyToSlots: MealSlot[]` (или отдельный метод порта): правка + вставки копий с теми же
  `override_*` и базой — в одном `writer.write`, одна публикация. В `EntryEditorDialog` на `DIARY_STALE` закрывать окно
  (или перечитывать запись).
- **Риск:** порядок позиций копий; квитанция идемпотентности не нужна (окно закрывается после успеха).
- **Проверка:** тест хранилища с отказом SQLite посреди команды (по образцу `nutrition-diary.test.ts:110`): ни правки, ни копий.

### NUT-004 — Рецепт считается строже, чем день: те же продукты дают разные калории

- **Категория:** расчёты. **Приоритет:** P2. **Доказательность:** подтверждено (код + скрипт H3). Решение за владельцем.
- **Файлы:** `domain/RecipeRules.ts:53-57`, `domain/DiaryRules.ts:59-71`, `domain/RecipeBrowse.ts:16,25-37`,
  `presentation/RecipeEditorScreen.tsx` (подпись «—»).
- **Описание:** ADR-028 сделал суммы дня «как в 2.0» (неизвестное = 0; калории без числа — из известных Б/Ж/У по каждой записи).
  `recipeTotals` остался строгим: один ингредиент без значения делает итог рецепта `null`, а калории рецепта затем
  досчитываются из суммарных Б/Ж/У, игнорируя заявленные калории остальных ингредиентов.
- **Доказательство (H3):** A (100 ккал, Б10/Ж0/У10) + B (ккал нет, Б10/Ж нет/У0): отдельными записями — **140 ккал, Ж 0**;
  тем же составом как рецепт — **120 ккал, Ж «—»**.
- **Последствия:** одно блюдо по-разному в дневнике; рецепты с неполными ингредиентами выпадают из фильтров калорий/БЖУ.
- **Решение (владелец подтвердил 2026-10-21):** в `recipeTotals` применить то же правило, что `sumNutrients`
  (переиспользовать `entryNutrients` по ингредиенту + `sumNutrients`), обновить подписи редактора и README.
- **Риск:** меняются значения будущих добавлений рецептов (история не меняется — снимки).
- **Проверка:** H3 как доменный тест «рецепт = сумма тех же продуктов».

### NUT-005 — После повторного открытия продукта калории перестают считаться из Б/Ж/У

- **Категория:** баг / UI. **Приоритет:** P2. **Доказательность:** подтверждено кодом; на телефоне не проверено.
- **Файл:** `presentation/FoodEditorScreen.tsx:46-52,87`.
- **Описание:** при создании калории «(авто)» = 4/9/4 и сохраняются числом. При открытии на правку `setKcalManual(food.kcalX10 !== null)`
  делает их «ручными». Тренер меняет белок — калории остаются старыми, продукт сохраняется несогласованным.
- **Первопричина:** происхождение калорий (авто/вручную) не хранится и не восстанавливается.
- **Решение без миграции:** при загрузке `kcalManual = food.kcalX10 !== kcalFromMacrosX10(food)` — совпадение с 4/9/4 считать авторасчётом.
- **Проверка:** тест на функцию инициализации черновика (вынести в чистую функцию рядом с экраном).

### NUT-007 — Разовые исключения целей (§49.12, APPROVED) недоступны из интерфейса

- **Категория:** функциональный пробел. **Приоритет:** P2. **Доказательность:** подтверждено (`setException`/`clearException` вызываются только тестами).

### NUT-008 — Квитанции пакетной записи растут без ограничения

- **Категория:** SQLite / производительность. **Приоритет:** P2. **Доказательность:** подтверждено кодом; объём — оценка.
- **Файлы:** `data/DevNutritionDiaryRepository.ts:217-241`, `data/DevNutritionCatalog.ts:276-283`.
- **Описание:** каждое «Добавить (N)» сохраняет полный JSON payload (снимки с составом) и JSON результата навсегда; чистка только при
  удалении клиента. Оценка: ~4 КБ на команду × 10 команд/день ≈ 15 МБ на активного клиента в год.
- **Решение:** хранить хэш payload и id созданных записей; в той же транзакции удалять квитанции старше N дней или сверх последних 50 на клиента.
- **Риск:** окно идемпотентности сужается — достаточно минут, не лет.
- **Проверка:** тест: 60 команд → в таблице ≤ 50 квитанций, повтор последней идемпотентен.

### NUT-009 — «Недавние/Частые» и «Всё время» читают всю историю дневника

- **Категория:** производительность. **Приоритет:** P2. **Доказательность:** подтверждено кодом; эффект требует замера.
- **Файлы:** `presentation/AddFoodScreen.tsx:262-286`, `domain/CatalogPick.ts:12-21`, `presentation/NutritionStatsScreen.tsx:54,60-72`.
- **Описание:** при открытии вкладок, каждом изменении поиска (после 300 мс), смене приёма и любом commit дневника —
  `listEntries(clientId, "0001-01-01", today)` (все строки, `JSON.parse` состава и масштабирование каждой), затем
  `usageSuggestions` фильтрует весь массив для каждой из ≤50 позиций и делает до 50 отдельных `foods.get`/`recipes.get` (N+1, рецепт — 2 запроса).
- **Решение:** метод порта `listUsage(clientId, slot, order, limit)` с `GROUP BY source_kind, source_id` и последней записью
  (окно `ROW_NUMBER`), пакетные `foods.getMany(ids)`/`recipes.getMany(ids)`; поиск фильтровать по уже загруженному списку без повторного чтения.
- **Проверка:** тест «стоимости чтения» по образцу `training-read-cost.test.ts`: число обращений не зависит от длины истории.

### NUT-010 — Один commit дневника вызывает 4–7 параллельных перечитываний, в т. ч. скрытых экранов

- **Категория:** производительность / состояние. **Приоритет:** P2 (требует замера на телефоне).
- **Файлы:** `presentation/DiaryWeekHeader.tsx:18-29,45-51,132`, `presentation/useNutritionDay.ts:41-77`,
  `presentation/NutritionHomeCards.tsx:61`, `presentation/NutritionHomeScreen.tsx:36-45`, `presentation/NutritionStatsScreen.tsx:73-80`.
- **Описание:** на одно нажатие «+250 мл воды» перечитываются: окно ±3 дня дневника (записи и вода), неделя шапки (полные записи ради
  дат), **месяц скрытого модального календаря** (`MonthModal` смонтирован всегда), окно ±3 дня главной клиента, а если вкладку
  «Статистика» хоть раз открывали — весь её период и **весь журнал замеров**. Вкладки «Расчёт/Статистика» остаются смонтированными (`display: none`).
- **Решение:** монтировать `MonthModal` только при `visible`; для отметок дней — `listAccountedDates(from, to)` (`SELECT DISTINCT local_date`);
  статистика при скрытой вкладке помечает данные устаревшими и читает при показе; вода не должна инвалидировать статистику питания
  (передавать вид изменения в `DiaryCommittedChange`).
- **Проверка:** счётчик обращений к порту в тесте хука или dev-журнал запросов: один commit → ≤ 2 чтения видимого экрана.

### NUT-011 — Перерисовка всех карточек каталога при вводе в одной

## Часть III. План устранения

Порядок выбран так, чтобы каждый этап был отдельным коммитом и проверялся независимо.

**Этап 1. Целостность данных** — NUT-002, NUT-003.

**Этап 2. Расчёты и основные сценарии** — NUT-001, NUT-004, NUT-005. Решения владельца получены (ADR-029); NUT-020 не правится.

Готово, когда: тест «дневник = статистика» зелёный (без ручной корректировки, с корректировкой до/после её даты, сегодня); H3 даёт одинаковые калории.

**Этап 3. Архитектура** — NUT-006, NUT-007.

**Этап 4. Дублирование и мёртвый код** — NUT-014, NUT-015, NUT-017, NUT-012 (запись в ADR).

или пометить; правила 4/9/4, даты и середину коридора — свести к одной функции. Готово, когда: grep по удалённым именам пуст, тесты зелёные.

**Этап 5. Производительность** — NUT-009, NUT-010, NUT-011, NUT-021, NUT-008.
Сначала замер (dev-журнал обращений к портам и Profiler на телефоне), затем: `listUsage` + пакетные `getMany`, `listAccountedDates`,
монтирование `MonthModal` по видимости, ленивое обновление скрытой статистики, memo карточек, чистка квитанций.
Готово, когда: тесты «стоимости чтения» фиксируют число запросов; один commit → чтения только видимого экрана.

**Этап 6. Тесты и стабилизация** — NUT-013, NUT-018, NUT-019, NUT-022, NUT-023 и матрица ниже.

### Ответы

- **Самое опасное:** NUT-002 (рецепты молча искажаются на порядки) и NUT-001 (дневник и статистика показывают разные цели одного дня,
  прошлые цели «плывут»). Затем NUT-003 — частично применённая команда и тупик в окне.
- **Сохранить:** снимки дневной записи, целые десятые и `NULL` = «нет данных», CAS по `revision`, триггеры/CHECK в схеме, публикацию после
  commit, чистые доменные функции, квитанции идемпотентности, участников удаления клиента.
- **Переработать:** выбор цели на дату (один read-model), команду «правка + копии», запись «Данных дня» и «Расчёта» через workflow, чтение
  «Недавних/Частых».
- **Не трогать:** схему и миграции v1–v15, `normalizeSnapshot`/`summarizeDay`, `planOverride`, `planBatch`, `CalcRules`.
- **Точечными правками стабилизировать можно**: существенного рефакторинга не требуется; системных причин две — нет единой функции цели
  на дату и многошаговые команды собираются в UI вместо порта/workflow.
- **Наибольший эффект при минимальном риске:** запрет смены единицы у продукта в рецептах (одна проверка в транзакции), атомарная команда
  «правка + копии», единая функция цели на дату с доменным тестом.
