## A.1 Дерево экранов и переходов

```

│   ├─ TrainingProgram = ProgramScreen (структура, недели; карточки недель со статусами тренировок)
│   │     └─ ProgramWeeksPanel → открыть тренировку → TrainingWorkout
│   ├─ TrainingMatrix = ProgramMatrixScreen («Обзор программы»: упражнения × недели, план/«Пред.»/факт, версии структуры)

│   └─ Статистика = TrainingStatisticsScreen (AN/TrainingStatisticsScreen.tsx)
│         ├─ DrillDownModal (Modal над экраном) → открыть тренировку (returnToCaller)
│         ├─ «Новые личные рекорды», «Упражнения в периоде» → ClientExercise

Открытие тренировки из истории/статистики/упражнения: `navigation.push("ClientWorkspace", …TrainingWorkout… closeOnBack: true)`
(PrototypeShell.tsx:146-149 и :163-165). «Назад» из такой тренировки — `onExitClient()` (ClientPrimaryNavigators.tsx:168-172), то есть
возврат на предыдущий экземпляр `ClientWorkspace` под ним.

# Часть B. Схема данных

идентификаторов (`X/data/DevTrainingExecutionCatalog.ts:7-10`: «слот и подход хранятся как ссылки без FK, поэтому правка структуры
плана не стирает факты (§48.5.7, TX-02)»).

```

## B.1 Связи, идентификаторы, кардинальность

| Связь | Идентификаторы | Кардинальность | Примечание |
|---|---|---|---|
| Клиент → участие в программе | `(workspace, program_id, client_id)` | 1 : N | Архив — у **участия** (`archived_at`), не у программы (:28-37) |
| Программа ↔ клиент | members | **M : N** | Простая — ровно один клиент (триггер `dev_training_simple_single_member`, :40-45) |
| Программа → мезоцикл | `program_id`, `client_id`, `lineage_id` | 1 : N **на клиента** | У каждого участника **своя копия** мезоцикла; копии связаны `lineage_id` (общий мезоцикл группы = одно родство, UNIQUE(ws,program,client,lineage)) |
| Мезоцикл → неделя | `mesocycle_id`, `position` | 1 : N (≤ 52) | Тип недели `base/light/medium/heavy/deload` |
| Неделя → тренировка | `week_id` (триггер обязательности, :228-237) | 1 : N | `lineage_id` тренировки связывает «ту же» тренировку разных недель/копий |
| Тренировка → плановое упражнение → подход | `workout_id` → `planned_exercise_id` | 1 : N : N | Идентичность `planned_exercise_id` меняется при замене упражнения |
| **Выполнение → слот плана** | `client_id + program_id + week_index + planned_workout_id` | **1 : 1** на слот | UNIQUE ⇒ в одном слоте не бывает двух выполнений; повторение тренировки в другую неделю = другой `week_index` ⇒ другое выполнение. FK на план **нет** |
| Выполнение → факты | `session_id` | 1 : N | RESTRICT; факт: UNIQUE(session, `planned_set_id`) |
| Факт → упражнение | `exercise_id` (хранится в самом факте) | N : 1 | Не зависит от плана: замена в плане не меняет `exercise_id` старых фактов (триггер `identity_fixed`, :66-70) |
| Выполнение → календарь | — | **нет связи** | Календарная запись не содержит программы/тренировки (в `features/calendar` нет таких полей; в `rosterOverview.ts:76-77` «Последняя тренировка» = `null`) |
| Выполнение → мезоцикл | не хранится | вычисляется **при чтении** | `read-models/trainingHistory.ts:27-42, 52`: по текущему плану клиента ищется `"${weekIndex}:${workoutId}"` → `{mesocycleId, mesocycleTitle, workout}` |

# Часть D. Оценка готовности к новому UI/UX

## D.1 Можно реализовать существующими компонентами и данными
- **Иерархия «программа → мезоцикл → неделя → тренировка» как группировка списка**: запись `TrainingHistoryEntry` содержит
  `programId/programTitle/programKind/archived/planDeleted/mesocycleId/mesocycleTitle/weekIndex/workoutTitle/plannedWorkoutId/actualDate/status/confirmedSets/volumeKg/exercises[facts]`
  (`AR/trainingHistory.ts:9-31`). Группировка и сворачиваемые секции — чистая функция над списком; компонентов-аккордеонов в `shared/ui` **нет**
  (`HistoryCard` сам реализует раскрытие, `TrainingArchiveScreen.tsx:21-59`), нужны листовые `SectionList`/`FlatList`.
- **Режим «по упражнениям» (список упражнений клиента → история/прогресс)**: `exerciseActivity` уже даёт строки «упражнение: занятий, подходов, дата»
  (`trainingStats.ts:213-226`), «История/Прогресс» одного упражнения — готовый экран; нужен лишь список-вход без периода.
- **Графики, плитки, фильтры, рекорды**: `LineChart`, `BarChart`, `SegmentedControl`, `FilterPill`, `SelectionChip`, `DropdownMenu`, `StatusTag`,
  `EmptyState`, `DateRangeCalendar` (экспорты `S/shared/ui/components/public.ts`).

# Часть E. Проблемы, противоречия и риски

## E.1 Расхождения PC и реализации **[расхождение]**
1. PC §37.3 / §48.85.1.8 / §50.4.3: нажатие на историческую сессию открывает полный контекст тренировки. В «Истории занятий» перехода **нет** (`TrainingArchiveScreen` не принимает `onOpenWorkout`); он есть в DrillDown, в «Упражнении клиента», в рекордах.

3. PC §50.1: две вкладки в «Архиве» клиента — в приложении «Архив программ» перенесён на главный экран «Тренировки» (решение владельца 2026-10-20), PC не обновлён.
4. PC §48.86.13 (средняя длительность) — не реализовано, нет данных (плитка «Нет данных»).
5. PC §39.3 (по комментарию в коде): профиль учёта своего упражнения должен быть неизменяем при наличии фактов; `DevExerciseCatalogRepository.updateCustom` (:179-199) меняет `tracking_profile` без проверки фактов (комментарий :183 «фактов в V1-dev пока нет»). **[факт]** отсутствие проверки; последствия для истории — **[гипотеза]**.
6. Общее правило проекта «Факты не уничтожаются» vs PC §48.11/§48.30/§50.3 (полное удаление мезоцикла/тренировки/программы с результатами) и реализация (`P/domain/PlanDeletion.ts`, `X/domain/ExecutionCleanupParticipant.ts`): удаление реализовано как осознанная команда с подтверждением — это **утверждённое исключение**, UI обязан показывать последствия.

## E.2 Дублирование вычислений **[факт]**
Две независимые формулы «объёма»:
- `factVolume` (`X/presentation/programMatrix.ts:97-105`, используется как `volumeKg` в записи истории, `S/app/composition/createDevServices.ts:140`): только засчитанные подходы, **включая разминку**, `load × reps` без массы тела, дроп-сеты входят.
- `factTonnage`/`entryTonnage` (`AN/trainingStats.ts:69-106`): только **рабочие** (без разминки), с учётом массы тела для `addedLoad`/`assistance`, невычислимое → `null`.
Следствие: «Объём» в карточке «Истории занятий» и «Тоннаж» в «Статистике» для одной тренировки могут различаться. Так же различается «Подходов» в карточке (`confirmedSets` = все засчитанные, `trainingHistory.ts:67`) и «Рабочих подходов» в статистике (`isWorkingSet`, `trainingStats.ts:37`). Расхождение не ошибка расчёта, а две семантики с похожими подписями.

## E.3 Риски сохранности и идентичности
- **[факт]** Названия программы/мезоцикла/тренировки в истории — из текущего плана; переименование меняет подпись у старых записей (PC §48.85.1.4 это допускает: «переименование не теряет происхождение»); снимок — только при «удалить план, сохранить историю».
- **[факт]** Если тренировки больше нет в плане (структурная правка), запись остаётся с `workoutTitle: null` (подпись «Тренировки больше нет в плане», `TrainingArchiveScreen.tsx:39-40`); порядок упражнений — как в плане, убранные — после, в порядке записи (`trainingHistory.ts:53-61`).
- **[факт]** Архивированное **своё** упражнение исключается из справочника (`list()` фильтрует `archived_at IS NULL`, `DevExerciseCatalogRepository.ts:124-136`; `get` тоже, :148-156), а `exerciseLookup` строится из `list()` (`createDevServices.ts:100-107`) ⇒ в истории такое упражнение получит имя-заглушку «Упражнение» (`nameOf`, `TrainingArchiveScreen.tsx:91`), без метрик (не попадёт в тоннаж/графики: `factTonnage` возвращает `null`, `trainingStats.ts:70-74`), `ExerciseDetail` не откроется. **[runtime]** — проверить на устройстве.
- **[факт]** Сортировка при равной дате — по `session.id` (случайный), порядок «утро/вечер» в один день не восстановим (нет времени).
- **[гипотеза]** Одно и то же упражнение дважды в тренировке сливается в одну «сессию упражнения» (`exerciseSessions` берёт все его группы, `exerciseProgress.ts:54-59`) — это совпадает с PC (повтор — одно занятие), но подходы двух вхождений идут единым списком без разделения.

## E.4 Возможные ошибки связей программы и клиента
- **[факт]** Изоляция клиентов: хронология читается по `client_id` (`listClientExecutions`, `X/data/...Repository.ts:303-307`; `read-models/trainingHistory.ts:24`); UNIQUE слота содержит `client_id`; в тесте `training-history.test.ts:67-89` проверяется отсутствие чужих занятий.

## E.5 Ограничения текущей навигации

### Блок 2. Программы, мезоциклы, тренировки

**В9.** Реальная иерархия — см. часть B. У клиента: участие в программе → программа (Простая/Расширенная) → у Расширенной мезоцикл (свой на участника) → неделя → тренировка → плановое упражнение → плановый подход. Выполнение — отдельная ветка: сессия слота (клиент, программа, неделя, плановая тренировка) → факты подходов → мини-сеты/стороны/заметки.

**В10.** Выполнение ↔ план: составной ключ слота `client_id + program_id + week_index + planned_workout_id` (UNIQUE, `DevTrainingExecutionCatalog.ts:20-35`). Факт ↔ план: `planned_set_id`, `planned_exercise_id` (без FK). Факт ↔ упражнение: `exercise_id`. Мезоцикл и шаблон тренировки **не хранятся в сессии**: мезоцикл вычисляется при чтении по текущему плану (`trainingHistory.ts:27-42`), а связь «та же тренировка в разных неделях/копиях» — через `lineage_id` плана. «Исходный шаблон» (`dev_training_templates`) с выполнением не связан.
