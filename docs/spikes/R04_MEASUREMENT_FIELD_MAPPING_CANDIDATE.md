# R04 — кандидат разбора legacy-замеров

**Статус: SOURCE FIELD CANDIDATE / NOT TARGET-MAPPED / NO TARGET WRITES.**
Основание: Product §§49.14–49.18, Stage 3 Data Design и прочитанный только
для аудита build120 `.atbackup`. `client_measurements` содержит широкую строку,
а в FitCoach 3.0 каждый показатель должен оставаться самостоятельным фактом.
Это не инструкция автоматически загружать бэкап.

| Поле legacy `client_measurements` | Показатель Product §49.14 | Что сохраняет R04 |
|---|---|---|
| `neck` | шея | исходный field и точное десятичное значение |
| `shoulders` | плечи | то же |
| `chest` | грудь | то же |
| `waist` | талия | то же |
| `hips` | бёдра | то же |
| `upper_arm` | рука | то же |
| `thigh` | бедро | то же |
| `calf` | икра | то же |

`MeasurementValueCandidates.ts` образует provenance-ключ
`(account scope, source row ID, source field)` и не сливает повторные строки
клиента в один день. Пустое поле не превращается в `0`; некорректное и
неположительное значение остаётся отдельной причиной блокировки. Число
с десятичной запятой нормализуется только как строка (`35,555` → `35.555`),
без округления, конверсии единицы или записи `value_scaled`. Время в этой
таблице не хранится: кандидат имеет точность `DATE`, `measuredAt=null`.
Смена клиента или неверная дата не скрывают исходный атом, а добавляют
отдельные причины review. ID target-замера и дневной primary не назначаются.

На предоставленном файле 5 широких строк дали 22 непустых атома: все 22
сохраняют точное десятичное представление; 0 неверных значений, owner/date
проблем и target-mapped фактов. Единица у всех 22 **не подтверждена полем
источника**, поэтому target writes = 0. Отчёт выводит только агрегаты.

`client_day_facts.weight` — отдельный источник с provenance
`(account scope, client ID, date key, weight)`. Его значение хранится точно
как десятичная строка, дата имеет точность `DATE`, точное время неизвестно.
Нуль и неверное значение блокируются; unit и target ID не назначаются.
`clients.weight` — изменяемый снимок профиля **без даты измерения**. Product
§10 прямо запрещает считать его источником истины текущего веса: он служит
только сигналом сверки и сам по себе не создаёт target BodyMeasurement.

В предоставленном файле 27 клиентов, у 20 положительный снимок веса профиля;
в `client_day_facts` есть 20 положительных дневных значений. У 12 клиентов
есть оба источника: у 9 значение профиля равно хотя бы одному дневному после
точной строковой нормализации десятичного числа, у 3 такого совпадения нет.
Равенство **не доказывает**, что это один исторический факт; несовпадение
не разрешает создавать дополнительный недатированный замер. Никакого
автоматического merge, backfill или target write нет. Отметка `training=Да`
не создаёт Workout/Credit факт.

До R04 approval требуются: утверждённые D01 metric keys и единицы,
правило безопасного переноса значений/точности, target Client ID map,
сверка всех account DB, решение по конфликтующим измерениям одного дня,
staging parity по ключам и значениям, interruption/restore gates D03/D05.
