# R03 — синтетические миграционные фикстуры (кандидат)

**Статус:** `PARTIAL / NOT DONE`, 2026-10-15. Backlog R03 зависит от R02;
Product §52.5 и TECH §06 задают обязательные сценарии. R02 пока не доказал
полный device inventory всех account DB, поэтому эти данные не разрешают
production conversion или cutover.

## Источник и граница приватности

На временной read-only копии личного `.atbackup` проверены **только структура и
агрегаты**. В нём есть архивные записи (6) и выполненные sets, но в данном
файле нет shared-book групп двух клиентов, рецептов, дней с одной водой и
повторных замеров клиента в одну дату. Для отсутствующих edge cases созданы
синтетические значения с префиксом `synthetic-`; реальные строки, ID и JSON
пользователя не экспортировались в репозиторий. Временная копия удалена,
исходный backup сохранён.

## Что закреплено в тестовом наборе

- [`SyntheticLegacyFixture.ts`](../../scripts/r03/SyntheticLegacyFixture.ts)
  создаёт изолированную SQLite `:memory:` с **частичным legacy-подобным**
  schema slice: два клиента, общий book с тремя мезоциклами у каждого,
  раздельные sessions/sets, архив с выполненным fact ID, Calendar appointment,
  продукт/рецепт, записанный и water-only дни, два замера в одну дату.
  Питание теперь содержит реальный `meals_json`-формат в четырёх синтетических
  днях: продуктовую запись, рецепт с неизвестным белком, день только с водой
  и продуктовый снимок со строковыми КБЖУ. Два дня с едой имеют legacy-флаг
  `meals_recorded=0`, поэтому тесты применяют §49.22 к записям, не к флагу.
- Отдельные ожидаемые сценарии проверяют коррекцию завершённой Calendar-записи
  `USED A → RETURNED A → USED B` по Product §22.1.4 и десять структурных
  ревизий без клонирования source fact. Они **не выдаются за legacy ledger rows**:
  в переданном backup отдельной таблицы Credit Ledger нет.
- [`synthetic-manifest.json`](../../scripts/r03/synthetic-manifest.json)
  фиксирует count и SHA-256 каждого набора синтетических строк. Второй SHA-256
  фиксирует каталог ожидаемых семантических сценариев. Хеши защищают fixtures
  от незамеченного дрейфа, но не являются хешами личного backup.
- [`r03-fixtures.test.ts`](../../scripts/r03-fixtures.test.ts) проверяет 20
  сценариев: manifest, FK/shape, общую книгу и изоляцию клиента, сохранение
  факта при архиве, недопустимый дубль sourceFactId **внутри одного exercise**,
  повтор ID между разными sessions, питание и замеры, независимость
  исторического снимка от правки каталога и сохранение неизвестного нутриента,
  компенсацию Ledger, 10 ревизий и отказ при повреждённом manifest.
- [`r03-file-fixtures.test.ts`](../../scripts/r03-file-fixtures.test.ts) добавляет
  семь file-level случаев на **синтетическом** `.atbackup`: read-only аудит
  сохраняет SHA-256 файла, повреждённые SQLite-байты и manifest блокируются,
  отсутствующий и множественный вход не выбираются автоматически. Две отдельные
  account-scoped SQLite с разными synthetic bindings сохраняют каждый свой
  count/SHA-256 по таблицам из golden manifest; source selection блокирует
  неоднозначность и неизвестный marker, не объединяя строки. Общий R03
  набор теперь 27/27. `AuditLegacyCopy.ts` возвращает только безопасные коды
  ошибок; путь, содержимое и записи источника в отчёт не попадают.
  Отдельный файловый тест проверяет агрегаты 3 пищевых записей без изменения
  байтов исходной синтетической SQLite.

## Реальный sourceFactId audit (локально, без PII)

`SourceFactCollisionAudit.ts` выполняет только агрегатные запросы к временной
read-only копии. В предоставленном backup: 20 973 **строки источника** в
`training_session_sets` (не доказанное число реальных подходов), 0 пустых
`source_fact_id`, **47 групп повторяющихся ID (94 строки)**. Все 47 групп
пересекают разные sessions и programs одного клиента; cross-client групп 0.
В одной группе различаются `reps/weight`. Баги FitCoach 2.0 могли породить
как лишние, так и отсутствующие строки: это не доказывает число истинных
выполненных подходов или эквивалентность остальных 46 групп. Глобальный
`UNIQUE(source_fact_id)`
был бы ложным ограничением: legacy schema ограничивает пару
`(session_exercise_id, source_fact_id)`. Synthetic fixture исправлена, включает
два межсессионных повтора (один с конфликтующими метриками); golden hashes
обновлены. Вывод `npm run r03:audit -- <temporary-copy.atbackup>` не содержит
самих ID или строк клиента.

**Следствие для R04:** ни `first wins`, ни автоматическое N→1 по одному
`source_fact_id` не допускаются. Нужны session/client provenance,
эквивалентность исходного факта и quarantine при конфликте значений.

`LegacyRelationAudit.ts` отдельно проверяет 14 выбранных связей между
client, program, week, planned workout/exercise, session/exercise/set,
archive, appointment, nutrition, measurement и history. На копии все 14
были доступны, структурных разрывов по этим join-правилам не найдено.
Результат **не подтверждает реальность 20 973 строк или полноту отношений**:
ошибки версии 2.0 могли сохранять ссылочную целостность. Поэтому верхний
статус CLI при найденных повторах — `requires-semantic-review`, даже когда
выборочная проверка связей сообщает `no-detected-breaks`.

`LegacySemanticScreen.ts` добавляет только агрегатные сигналы, не вычисляя
«истинное число выполненных подходов». В переданном backup есть 802 строки
сессий и 20 973 строки подходов; пустых сессий по выбранным связям нет, но
277 строк упражнений сессий не имеют ни одной строки подхода. Отдельно есть
25 354 строки `training_exercise_history`: 14 525 не имеют пары среди строк
подходов по `(client_id, source_fact_id)`, а 47 сопоставляются с несколькими
строками подходов. Это **не** означает, что 14 525 подходов нужно создать:
history может быть отдельной проекцией или содержать иные legacy-события.
Ни один из этих агрегатов не доказывает полноту или правдивость выполненных
фактов. Даже без обнаруженных сигналов CLI теперь всегда возвращает
`requires-semantic-review`; автоматического разрешения миграции нет.
`LegacyAuditDecision.ts` добавляет машинно-читаемые reason codes без ID:
`SOURCE_FACTS_UNVERIFIED` присутствует всегда, даже если выбранные проверки
не нашли аномалий; повтор ID, конфликт метрик, разрыв связей, неполная схема,
неоднозначная история и упражнения без строк подходов отмечаются отдельно.
Одновременный разрыв связей и неполная схема дают **две** причины, не скрывая
друг друга. Это triage для R04, не решение о судьбе отдельных записей.

## Открыто до R03 acceptance

1. Это частичная synthetic fixture, не полная копия build120 schema и не
   обезличенный реальный backup. Нужны безопасно обезличенные реальные samples
   SQLite/JSON v1/v2, включая **реальный** многобазовый случай, с отдельным
   manifest. Файловый многобазовый случай пока только синтетический.
2. Нет source→target mapping и проверки доменной семантики реального архива:
   это R04 после определения D01/owner model. Нельзя считать тесты доказательством
   сохранения всех пользовательских фактов.
3. File-level corrupt проверен только на синтетическом SQLite. Low-disk,
   process-kill, Android restore и overlay evidence остаются OPEN по
   R05/R06/T01/T05; синтетический тест не заменяет проверку на устройстве.
