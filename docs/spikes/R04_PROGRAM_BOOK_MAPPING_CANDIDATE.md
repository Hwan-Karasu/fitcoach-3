# R04 — legacy program/book identity (кандидат)

**Статус: SOURCE GROUPING CANDIDATE / NOT TARGET-MAPPED / NO TARGET WRITES.**
Продолжение: [source graph программ и составной ключ библиотеки](R04_PROGRAM_STRUCTURE_MAPPING.md).
Ключ library — `(client_id,id)`; одинаковые ID разных клиентов допустимы.
Вход — `training_programs` и, если есть, `training_library_programs` в том же
read-only снимке, что R02/R04 coverage. Product §48.1 требует изоляцию
фактов участников; §48.2 запрещает закреплять legacy `book_id` как
преждевременную целевую сущность. Stage 3 §06 требует сохранить provenance,
включая различие между назначенной программой и общим книжным контекстом.

Каждая строка `training_programs` остаётся отдельным source program key
`(account scope, program ID)` со своим `client_id`. Одинаковый `book_id`
группирует строки **только для проверки**, не объединяет их, не переносит
подходы между клиентами и не создаёт target Cohort. Совпадение `book_id`
с `training_library_programs.id` тоже лишь ID-сигнал; пока не доказана
смысловая FK-связь и поведение шаблонов, это не разрешение на mapping.

На предоставленном build120 файле:

| Сигнал | Физические итоги |
|---|---:|
| Строки `training_programs` | 118 |
| Без `book_id` | 14 |
| Непустые группы `book_id` | 36 |
| Группы `book_id` с несколькими клиентами | 0 |
| Группы одного клиента с несколькими строками программы | 21 |
| `book_id` равен library ID того же клиента | 98 строк |
| `book_id` не найден среди library ID | 6 строк |
| `book_id` равен library ID другого клиента | 0 строк |
| Legacy deletion marker | 42 строки |
| Legacy template marker | 13 строк |
| Программа без существующего клиента | 0 строк |

Эти категории пересекаются; например, deleted/template входят в те же 118
строк. Нельзя удалить 42 marked rows без сверки с тренировками и архивом.
Синтетическая R03-фикстура имеет одну книгу из шести строк у двух клиентов:
тест подтверждает, что такой вариант остаётся шестью source назначениями.
Отсутствие cross-client группы в **этом** файле не отменяет поддержку
группового поведения продукта и не доказывает отсутствие других account DB.

Открыто до target mapping: значение `book_id` и 6 unmatched library hints,
структура 902 `training_weeks`/6501 `training_workouts`, связь сессий и
выполненных фактов, deletion/archive semantics, ID/revision target-модель
D01/D02 и staging parity R04/D03. Target-mapped programs = 0, writes = 0.

## Сессии и плановые тренировки, указывающие на программы

`ProgramLinkPreflight.ts` отдельно сравнивает `training_sessions.program_key`
и `training_workouts.program_id` с **точным** source program ID и client owner.
Совпадение только с `book_id` остаётся отдельным hint, а не программной
ссылкой. В том же снимке подсчитаны физические `training_session_sets` у
сессий, напрямую указывающих на marked-deleted программы; это **не** число
подтверждённых выполненных подходов.

В предоставленном файле 802 физических сессии: 790 имеют точный program ID
того же клиента, **2 указывают на program ID другого клиента**, 10 ключей
не найдены среди program ID/book ID. Все 6 501 плановых `training_workouts`
ссылаются на точный program ID того же клиента. Ни одно совпадение с
`book_id` не понадобилось для этих двух источников.

Из 42 программ с deletion marker **20 имеют прямые session-ссылки**;
в таких сессиях 2 179 физических строк `training_session_sets`. **41 имеет
прямые ссылки плановых тренировок.** Категории пересекаются. Наличие
deletion marker не доказывает намерение удалить результаты, а наличие строки
подхода не доказывает её каноническое выполнение. Две чужие ссылки и десять
неразрешённых ключей требуют quarantine/semantic review до target mapping.
Синтетические тесты подтверждают изоляцию клиента и сохранение source rows
при deleted-маркере. Target-mapped links = 0, target writes = 0.

Для будущего dry-run теперь формируется **внутренний поштучный quarantine
ledger** по всем 802 сессиям: source key включает account scope и session ID;
для каждой строки сохраняются исходный `program_key`, тип совпадения,
совпавший source program ID (только при точном ID), reason codes и пустой
target ID. Даже 790 точных same-client ссылок остаются
`BLOCKED_PENDING_SEMANTIC_REVIEW`, а не автоматически подтверждённым
выполнением. У 127 same-client сессий точный source program ID указывает на
программу с deletion marker. Сводка ledger сверяется с независимым
агрегатным проходом; наружу выходят только числа, без source ID и ключей.

Отдельная read-only сверка `source_workout_id` с `training_workouts` добавляет
независимую подсказку о происхождении сессии, но **не исправляет** её
`program_key` и не утверждает факт выполнения. В этом файле поле есть у всех
802 сессий: 778 указывают на тренировку того же клиента, 2 — на тренировку
другого клиента, 22 — на отсутствующую тренировку. Среди 778 совпадений
владельца программные ключи согласуются в 777 строках и расходятся в 1.
Ни одна из 12 сессий с чужой или неразрешённой прямой program-ссылкой не
получила same-client workout clue. Все 12 остаются в карантине; даже
совпавшие строки не становятся target-фактами. Target-mapped sessions = 0,
target writes = 0.
