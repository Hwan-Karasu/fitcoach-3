## Что установлено по исходникам 2.0

Каталог уже содержит `category`, `equipment`, `aliases_json`, `source`, временные
метки и `deleted_at`. При создании своего упражнения `source='user'`, пустое
оборудование сохраняется как `''`, категория по умолчанию — `Другое`.
Значит, новые признаки не всегда отсутствуют целиком: часть можно сохранить.
`source='stock'` означает старую системную запись, а не автоматическое совпадение
с новым RepDB. Неизвестный source нельзя нормализовать в stock, как делал v2 reader.

Плановый экземпляр ссылается на каталог через `template_exercise_id` и JSON
`catalogId`. История содержит `exercise_key`, JSON `catalogId` и/или `exerciseId`;
последний может быть ID экземпляра либо явным ID каталога. Старый backfill
пытался исправлять ссылки. Новый reader его не запускает и исходник не ремонтирует.

## Реализованные кандидаты

`LegacyExerciseCatalogSourceReader.ts` читает все записи каталога, включая
soft-deleted. Сохраняет исходные колонки, ID в области account scope, название,
категорию, оборудование, aliases, происхождение и lifecycle. Повреждённый JSON
aliases сохраняется в raw; он не превращается в пустой массив.

Профиль у кандидатов `LOAD_REPS`. Точные соответствия категорий проверены по
старому seed и текущим `ExerciseModel` / `ExerciseLabels`:

| Категория 2.0 | Кандидат 3.x |
|---|---|
| Грудь | `chest` |
| Спина | `back` |
| Плечи | `shoulders` |
| Кор | `core` |
| Ноги / Руки | Требуется уточнение: в 3.x есть несколько более узких категорий |
| Кардио / Другое / пустая / произвольная | Категория не назначается |

Это кандидаты dry-run, а не переклассификация сохранённых фактов. Конкретные
мышцы и оборудование по названию не определяются. Исходная категория сохраняется
даже при наличии однозначного соответствия. Неизвестная категория представлена
в staging-кандидате как `null`; теперь общая ExerciseDefinition также поддерживает
это состояние для сохранённого legacy import, сохраняя обязательность категории
при обычном CreateCustom.
Read-only candidate не получает target ID; отдельный staging ledger теперь
резервирует и сохраняет его. Production CHECK и обычное создание без категории
не изменяются. Сохранённый legacy import в общей domain model допускает null
category/unspecified equipment; частный registry stage проверяет такие records
без подстановки full_body/bodyweight. Runtime storage ещё не подключён.

## Проверка ссылок и истории

`LegacyExerciseReferencePreflight.ts` читает физические `training_exercises` и
`training_exercise_history` с сохранением исходных полей, заметок, имён-снимков,
JSON и признаков удаления. LEFT JOIN не скрывает отсутствующего владельца.

- Явные ID должны совпасть между колонкой, JSON, ключом истории и экземпляром.
- Ссылка на экземпляр истории принимается только в пределах того же клиента.
- Удалённая карточка остаётся доступной для проверки исторической ссылки.
- Совпавшие названия/aliases не объединяют записи и не создают ссылки.
- Конфликт, неизвестный ID, испорченный JSON и отсутствующий владелец сохраняют
  физическую строку в `requires-link-review`; ID целевого упражнения остаётся null.
- Повтор физического ID и несовместимые колонки блокируют проход.
- `linked-source` означает только согласованную ссылку на исходный каталог.
  Это не подтверждённый выполненный подход и не готовая целевая запись.

Единый `npm run r04:full` добавляет агрегатную секцию `exercises` в том же
read-only SQLite snapshot, что и остальные проверки. Наружу выходят только
счётчики; исходные названия, ID, заметки и JSON не выводятся.
Для старой узкой синтетической fixture без каталога секция null; если таблица
каталога есть, несовместимая форма отклоняется, а не пропускается.

## Проверки и оставшаяся работа

Синтетические тесты проверяют сохранение неизвестных полей, точные/неоднозначные
категории, удаление, aliases, конфликты, одинаковые названия, cross-client/account,
повторные ID и отсутствие PII в отчёте. Файловая интеграция полного аудита
проверяет неизменность байтов как при успехе, так и при ошибке формы.
Реальная пользовательская база в этом срезе не открывалась.

Source→target ID ledger и ссылки двух указанных source tables теперь проверены в
общем Client/Q/WorkData staging, включая read-back/FK/retry и17 новых tests.
Открыты проверка `exercise_identity_unresolved` и alias
registry, ссылки из session exercises, JSON программ/библиотеки/архивов, сохранение
исторической классификации, UI уточнения категории и полноценное восстановление.
Пользовательское уточнение новых полей не должно переписывать старые результаты.
Feature 08 EX-06 (категория при импорте) нужно учесть в конечном сценарии обновления.

На телефоне позднее предстоит проверить сохранение 2.0 до cutover, подпись/package,
обновление поверх установленной версии, проверенную safety-копию, сверку фактов,
прерывание процесса и повторный запуск. Наличие установленной 2.0 само по себе
не закрывает R05/R06 или release gate. Никаких установок или сбросов сейчас нет.
