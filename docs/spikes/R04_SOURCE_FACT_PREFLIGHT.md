# R04 — предварительная сверка identity legacy-подходов

**Статус 2026-10-15: PARTIAL / NOT DONE.** Это preflight на синтетическом
R03-наборе, а не миграция в FitCoach 3.0. Никаких production DDL, target ID,
записей в рабочую БД или автоматической дедупликации нет.

## Основание и граница

- Backlog `R04`: зависимость `R03` пока частично открыта; Product §48.5.7,
  §§49–50, сценарии INT-03–12. Реальная source→target сверка требует полного
  R03 source inventory и утверждённой target-модели D01.
- В личном backup R03 обнаружил 47 групп повторного `source_fact_id` между
  сессиями/программами одного клиента; в одной группе различаются метрики.
  Это не разрешает ни `first wins`, ни N→1 по ID, ни признание всех строк
  реальными выполненными подходами. Число 20 973 — физические строки источника.
- История упражнения, плановая структура и строка подхода не объявляются
  одним фактом только из-за совпадения подписи, позиции или `source_fact_id`.

## Реализованный безопасный preflight

`scripts/r04/LegacySetSourceReader.ts` читает только выбранный legacy-срез
из переданной SQLite-копии. Он требует явный account scope, проверяет форму
трёх таблиц, включает `query_only`, читает строки и их количество в одном
read transaction и закрывает его даже при ошибке. `LEFT JOIN` сохраняет
физическую строку с нарушенной связью в выборке; неполное происхождение
останавливает процесс кодом `R04_SOURCE_PROVENANCE_INCOMPLETE`. Данные и ID
источника не печатаются в ошибках.

`scripts/r04/SourceFactPreflight.ts` сохраняет отдельную запись на каждую
пару `(accountScope, sourceRowId)`. Все записи получают
`BLOCKED_PENDING_SEMANTIC_REVIEW`, включая одиночные ID. Повтор
`sourceFactId` в одном account scope помечается для проверки пересечения
клиента, программы, сессии и сырых метрик. Даже идентичные метрики не дают
автоматического слияния. `null` и пустые значения не превращаются в ноль.
Повтор физического ID и пустое происхождение блокируются.

`LegacyEvidenceReader.ts` получает строки подходов и истории упражнения из
**одного** SQLite read snapshot, чтобы классификация не смешивала два момента
состояния файла. `LegacyHistorySourceReader.ts` сохраняет все физические строки
истории и отказывает при отсутствующем клиенте. `HistoryLinkPreflight.ts`
различает отсутствие пары, единственную неподтверждённую ссылку и несколько
пар в рамках `(accountScope, clientId, sourceFactId)`. Совпадение ID только у
другого клиента не считается допустимой парой; ни один вариант не создаёт
подход из строки истории.

Следующий срез: [иерархия программ и client-scoped ключ библиотеки](R04_PROGRAM_STRUCTURE_MAPPING.md).

`npm run r04:audit -- <source.atbackup>` сначала проверяет допустимость
источника по R02, затем открывает SQLite с `readOnly: true`; наружу возвращает
только status, числа физических строк и фиксированные reason codes. Это
успешное выполнение аудита, **не** разрешение на импорт. Для обычной работы
предпочтительна временная копия, чтобы оригинал не зависел от инструмента.

`npm run r04:full -- <source.atbackup>` объединяет R02 source gate, покрытие
таблиц, перечисление source PK и сверку подходов/истории/исходных set logs в **одной** read-only
SQLite-транзакции. Неизвестная или дрейфовавшая таблица блокирует чтение фактов.
На предоставленном backup результат — `requires-semantic-review`, покрытие
`requires-mapping`, `targetWrites=0`; это единый диагностический проход, а не
разрешение на импорт. Синтетические тесты проверяют также единый снимок и
отказ до разбора фактов при неподдерживаемой форме источника.

В этом же снимке добавлена [проверка source identity клиентов](R04_CLIENT_IDENTITY_MAPPING_CANDIDATE.md).
Она хранит account scope, исходный Client ID и workspace owner раздельно,
отмечает неполное имя/время и не считает soft-deleted строку активной.
На предоставленном файле: 27 физических клиентов в одном source-workspace,
25 active-кандидатов, 2 archived, 0 deleted/неполных. Target Client ID
и target Workspace ID не назначены; все зависимые факты остаются на сверке.
Общий read-only проход по прямым `client_id` в 22 таблицах учёл 34 113
физических строк: 34 074 с существующим клиентом, 39 без ключа (все в
Calendar: 38 гостевых и 1 неназначенная), 0 orphan. Из связанных строк
1 407 принадлежат архивным клиентам и не должны пропасть при переносе.
Сумма строк разных таблиц не равна числу уникальных доменных фактов;
подробности и ограничения — в матрице source identity выше.

На предоставленном backup выполнен один прямой read-only проход без создания
копии: 20 973 физические строки, 20 973 заблокированных кандидата, 0 target
writes, 94 строки с повторным `sourceFactId`, 94 — с пересечением sessions и
programs, 2 — с конфликтом сырых метрик; cross-client строк по этому сигналу
нет. SHA-256 исходного файла до и после совпал. Эти числа **не** означают
20 973 подтверждённых выполненных подхода: legacy 2.0 содержал баги, а
проверка статуса выполнения, полноты и истории ещё не закончена.

Повторный проход с историей из того же SQLite-снимка показал 25 354
физические строки истории: 14 525 без пары по `(clientId, sourceFactId)`,
47 с несколькими парами, 10 782 с одной ссылкой. Все 25 354 остаются
неподтверждёнными; «одна ссылка» не равна «один выполненный подход».
Чужой client/account не подставлялся. Сигналы согласуются с R03, исходный
файл после повторного прохода также сохранил SHA-256.

`npm run r04:coverage -- <source.atbackup>` проводит отдельную read-only сверку
имён таблиц с реестром, наблюдённым **только в предоставленном build120 backup**.
Проверка R02 и чтение каталога таблиц идут в одном SQLite read snapshot;
транзакция закрывается также при блокировке или ошибке.
На этом файле обнаружены все 43 зарегистрированные таблицы: 13 затронуты
проверками формы/происхождения источника, 30 ожидают разбора и сопоставления,
0 признаны сопоставленными с target-моделью. Отчёт выдаёт только количества,
не имена таблиц или записи. Неизвестная либо отсутствующая таблица, а также
несовпадение отпечатка колонок либо DDL даёт `blocked-source-shape`;
совпадение даёт лишь `requires-mapping`, а не разрешение на миграцию.
SHA-256 исходного файла после прохода не изменился.
Отпечаток колонок включает имена, типы, nullability, default, PK-позицию и
скрытость колонок в 43 наблюдённых таблицах. Отдельный отпечаток DDL включает
определения таблиц, индексов, представлений и триггеров, в том числе FK,
описанные в DDL. На предоставленном файле оба совпали. Это консервативный
контроль дрейфа одного источника, не верификация правильности legacy-схемы.
Реестр не доказывает полноту всех account DB, стабильность legacy-схемы или
семантику какой-либо сущности.

В том же read snapshot аудит считает физические строки **каждой** обнаруженной
таблицы (включая ещё не зарегистрированные), проверяет безопасный целочисленный
итог и выдаёт суммарное число, количество непустых таблиц и стабильный SHA-256
реестра `(имя таблицы, количество)`. Ни имена таблиц, ни записи/ID в отчёт не
попадают. На предоставленном backup: 43 посчитанные таблицы, 33 непустые,
382 402 физических строки суммарно. Это не число клиентов, выполненных
подходов или доказанных доменных фактов: технические таблицы и разные сущности
входят в сумму вместе. Перенос данных, target parity и дедупликация отсутствуют.

Следующая read-only проверка использует `PRAGMA table_info` и считает таблицы с
явным PK, составным PK и физические строки с неполным ключом. Для provenance
нельзя молча подставить нестабильный `rowid`: таблица без PK или `NULL` в любой
части составного PK даёт `blocked-source-identity`. На предоставленном backup
все 43 таблицы имеют явный PK (8 составных), строк с неполным ключом нет.
Поэтому 382 402 строки являются **кандидатами на адресацию внутри этого
файла**, а не доказанными target ID, уникальными доменными фактами или
безопасными к слиянию между account DB. Технические записи тоже входят в счёт.

Классификация конфликтов метрик теперь различает сырые `NULL` и пустую строку:
они не объединяются в один ключ сравнения. Синтетический тест ловит этот
случай; повторный read-only аудит предоставленного backup сохранил прежние
агрегаты (2 строки с конфликтом метрик) и ноль target writes.

Аудит перечисляет типизированные значения явного PK каждой строки в том же
снимке и строит SHA-256 реестра `(account scope, таблица, PK tuple)` без публикации исходных
ключей. Число перечисленных ключей обязано равняться числу строк с полным PK;
при расхождении аудит блокируется. На предоставленном backup обе величины
равны 382 402. Синтетический тест подтверждает: изменение PK при том же числе
строк меняет отпечаток. SQLite INTEGER читается как `BigInt`, поэтому соседние
ключи за пределом точности JS `number` не схлопываются. Scope из проверенного
binding используется только как namespace и наружу не выводится; он не
доказывает уникальность разных файлов одного аккаунта. Это доказательство
полноты **обхода локального источника**, не глобального fact ID или target parity.

Отдельная preflight-классификация теперь сохраняет legacy-маркеры удаления
подхода/упражнения/сессии и отсутствие времени завершения/выполнения. Если
колонок нет в синтетическом срезе, это отдельная причина
`LIFECYCLE_COLUMNS_MISSING`, а не выдуманный `NULL` исходника. На переданном
backup: 132 строки с маркером удаления подхода, 4 с маркером на сессии,
101 на упражнении; **объединение — 132 строки**, категории пересекаются.
Отсутствующих маркеров завершения/времени выполнения на этом срезе нет.
Наличие времени не доказывает, что строка является canonical выполненным
подходом, а маркер удаления пока не определяет автоматическое решение о
переносе. Все 20 973 строки остаются заблокированными до semantic review.

История упражнений проверяется отдельно: на 10 720 из 25 354 её физических
строк есть маркер удаления. Из них 9 853 не имеют пары с подходом того же
клиента, 867 имеют одну неподтверждённую ссылку, 0 — несколько пар.
Категории непересекаются и суммируются в 10 720; это triage источника,
не команда удалить подходы и не создание новых выполненных фактов.

Для 10 782 строк истории с **одной** ссылкой на подход того же клиента
отдельный cross-tab сохраняет состояние маркеров по обе стороны связи:
9 880 без отметок, 832 только с отметкой на истории, 35 только на стороне
подхода/сессии/упражнения, 35 с обеих сторон, 0 с неизвестной формой lifecycle.
Категории взаимоисключающие и суммируются в 10 782. Это дополнительно
показывает, почему одинаковый `sourceFactId` и наличие одной ссылки нельзя
принимать за одну подтверждённую запись: две проекции могут расходиться.
Тесты проверяют все пять категорий и запрещают подстановку строки другого
клиента или account scope. Ни одна категория не запускает перенос или удаление.

Третий legacy-источник, `training_set_logs`, читается как отдельная физическая
проекция вместе с её exercise/workout ownership. `historyOriginId` из
`data_json` применяется только как **кандидат связи**; плохой JSON и значение
неподдерживаемого типа остаются отдельными unresolved-категориями, а не
подменяются ID строки. `LEFT JOIN` не скрывает orphan, отсутствие владельца
блокирует проход; маркеры завершения и удаления не становятся автоматически
выполненными фактами или командами миграции. На предоставленном backup:
137 152 физических current-set строк, 30 371 с `completed_at`, 107 920 с
маркером удаления на строке/упражнении/тренировке, 13 966 используют
`historyOriginId`; повреждённых JSON и неподдерживаемых origin-типов нет.
По `(account scope, clientId, effectiveSourceFactId)` 122 437 строк не имеют
пары в `training_session_sets`, 14 620 имеют одну неподтверждённую ссылку,
95 — несколько. Категории суммируются в 137 152; ни одна строка не переносится
и не сливается автоматически. Пять синтетических тестов покрывают
разделение клиентов, origin, повреждённый JSON, orphan и повтор физического ID.

Чтобы не смешивать независимые сигналы, тот же preflight разбивает каждую
физическую `training_set_logs`-строку одновременно по наличию same-client
ссылки в сессионной проекции и по legacy-маркерам:

| Ссылка на session set | Только `completed_at` | Только удаление | Оба маркера | Ни одного |
|---|---:|---:|---:|---:|
| Нет | 355 | 89 039 | 15 864 | 17 179 |
| Одна неподтверждённая | 11 631 | 537 | 2 426 | 26 |
| Несколько | 41 | 0 | 54 | 0 |

Сумма — 137 152 строк; неизвестных lifecycle-форм и unresolved origin в этом
backup нет. В частности, 355 строк с `completed_at` без маркера удаления и
без пары — приоритет для семантической сверки, **не** автоматически потерянные
выполненные подходы. Маркеры могут сосуществовать, поэтому отдельные итоги
30 371 и 107 920 пересекаются. Ни один столбец не доказывает канонический факт.

Узкая трёхсторонняя сверка этих 355 строк с `training_exercise_history` в том
же read snapshot нашла 354 без истории того же клиента, 1 с единственной
строкой истории без deletion marker, 0 с удалённой/неизвестной/множественной
историей. История другого клиента или account scope не подставляется.
Отсутствие истории не опровергает выполнение, а наличие одной строки не
доказывает его: все 355 остаются review-required, target writes = 0.

Дополнительная проверка **контекста тренировки**, не вложенного подхода,
сопоставила 354 строки без истории с `training_workout_logs` по тому же
account/client/workout ID. У 285 нет записи-снимка тренировки; у 69 ровно одна,
но в её валидном JSON отсутствует ожидаемый массив `exercises`. Повреждённого
JSON, множественных same-client снимков, чужого owner, deletion marker или
неизвестной формы lifecycle в этих 69 случаях нет. Наличие записи о тренировке
не означает, что конкретный подход был выполнен; отсутствие массива в этом
поле не исключает другие legacy-формы данных. Все кандидаты остаются на
семантической сверке. Чтение выполнено в том же read-only снимке.
Синтетический тест отдельно различает отсутствующую тренировку, чужого
владельца тренировки и отсутствующего клиента: чужие строки не подставляются.

Архивные `training_archive_entries` теперь читаются в том же read-only
снимке отдельно от выполненных сессий. Парсер отмечает форму JSON, наличие
массивов тренировок/недель, согласованность объявленного числа тренировок,
удаление и ссылку на программу с проверкой client ownership. На переданном
backup 6 физических архивных записей: 3 с deletion marker, 0 с повреждённым
JSON, 3 со ссылкой на программу того же клиента, 1 — на программу с другим
`client_id`, 2 — без program ID. У 3 есть массив `workouts` (42 вложенные
строки суммарно), у всех 6 — массив `weeks`; конфликтов заявленного числа
тренировок нет. Вложенные строки **не** считаются выполненными фактами и не
дублируют `training_session_sets`. Чужая ссылка остаётся review-required:
общая книга или legacy-ошибка не дают разрешения присвоить историю другому
клиенту. Синтетические тесты проверяют orphan, чужого владельца, JSON и
дубли физического archive ID; `targetWrites=0`.

Дополнительный read-only сигнал по единственной архивной ссылке на программу
другого клиента: у владельца архива **нет** собственной строки
`training_programs` с тем же непустым `book_id`; `otherClientSharedBookCandidate=0`,
`otherClientNoSameBook=1`. Равный `book_id` в синтетическом тесте тоже не даёт
разрешения переносить факты, а только помечает возможный контекст общей книги.
На просмотренном commit build120 [обычная команда архивирования](https://github.com/Hwan-Karasu/fitcoach/blob/e116b42e95f70a5a5e563420ab25394944c59ffd/apps/mobile/src/features/archive/application/archiveTrainingProgram.ts#L20)
начинает с поиска программы в scope клиента. Это делает наблюдённую ссылку
нетипичной для показанного пути, но не доказывает причину её появления в backup.
Нужна quarantine/ручная сверка ownership до target mapping.

Отдельный [program/book identity preflight](R04_PROGRAM_BOOK_MAPPING_CANDIDATE.md)
сохраняет каждую строку `training_programs` как назначение конкретного клиента,
даже при одинаковом `book_id`. В переданном файле 118 программных строк,
36 непустых book-групп и 0 групп с несколькими клиентами; 21 группа содержит
несколько строк одного клиента. У 98 строк `book_id` равен ID библиотечной
записи того же клиента, у 6 совпадение не найдено; это не доказанная FK-связь.
42 строки имеют deletion marker и требуют сверки с выполненными фактами.
Синтетический случай общей книги двух клиентов защищён тестом; target writes=0.
Прямые program key-связи в том же снимке выявили 790 same-client сессий,
2 с program ID другого клиента и 10 без найденного program/book ID; все
6 501 плановых тренировок ссылаются на program ID своего клиента. У 20
marked-deleted программ есть прямые сессии, содержащие 2 179 физических
строк подходов; у 41 — плановые тренировки. Это source-сигналы, не решение
удалить/перенести подходы и не подтверждение их выполнения.
Каждая из 802 сессий теперь также имеет внутреннюю запись карантина с
source key и reason codes; её обезличенная сводка независимо совпадает с
program-link агрегатами. 127 same-client сессий указывают точным ID на
программы с deletion marker. Никакая из этих ссылок пока не target-mapped.

`nutrition_days` теперь также читается в общем read-only снимке. Парсер
проверяет форму четырёх meal-массивов, фактические записи с source ID,
владельца-клиента, legacy-флаг `meals_recorded`, воду и наличие известных
макронутриентов. Только наличие пищевой записи делает день кандидатом для
статистики по Product §49.22; флаг, вода и пустой JSON не заменяют еду.
Повреждённые/неполные записи остаются на ручной сверке, отсутствующий
макронутриент не превращается в ноль. На предоставленном backup обнаружены
17 физических дней: 3 дня с 5 кандидатами пищевых записей, 14 пустых;
0 water-only, 0 malformed/ambiguous, 0 расхождений факта еды и legacy-флага,
0 записей с неизвестным макронутриентом. Это проверка формы одного файла,
а не признание всех пяти записей target-фактами. Покрытие: 14
source-inspected / 29 mapping-pending / 0 target-mapped, `targetWrites=0`.
Синтетические тесты дополнительно проверяют расхождение флага и еды,
water-only, неизвестный нутриент, карантин повреждённого JSON и отсутствие
владельца-клиента.

`client_measurements` проверяется без преобразования в target-модель. Legacy
таблица хранит одну широкую строку с восемью видами окружностей; отсутствие
значения остаётся отсутствием, десятичная запятая отмечается отдельно,
физические ID и client/date не выводятся. В предоставленном файле 5 строк,
22 заполненных числовых значения (2 с запятой), 0 неверных/неположительных,
0 пустых строк, 0 неверных дат/отсутствующих владельцев и 0 групп с несколькими
строками на один день клиента. Все 22 значения остаются с неподтверждённой
единицей измерения: legacy-строка не содержит unit/provenance или выбора
`primary` на день. Это не даёт права автоматически записать их как сантиметры
или создать target `BodyMeasurement`. Синтетические тесты проверяют пропуски,
запятую, неверные даты, orphan-клиента и повтор физического ID. Покрытие
источника теперь 15 source-inspected / 28 mapping-pending / 0 target-mapped.

Для этой широкой таблицы добавлен поэлементный кандидат с provenance
`(account scope, row ID, source field)`: точные десятичные строки не
округляются, отсутствующие значения не становятся нулём, date-only не
получает искусственного времени. На предоставленном файле 22/22 непустых
поля представлены как точные кандидаты, но единицы для всех 22 остаются
неподтверждёнными; target-mapped = 0, writes = 0. Результат включён в
общий read-only R04 report; [матрица полей и открытые решения](R04_MEASUREMENT_FIELD_MAPPING_CANDIDATE.md).

Календарные `calendar_appointments` также разбираются только как самостоятельный
source-домен. На предоставленном backup 392 физических строки: 353 с
существующим клиентом, 38 гостевых, 1 без клиента и гостя; 179 с deletion
marker. Типы: 380 `training`, 3 `guest_visit`, 9 `initial_instruction`.
Неверных дат/времени, duration/end mismatch, отсутствующих связанных
клиентов и неизвестных типов здесь нет. Неназначенная запись требует
сверки, а deletion marker не является командой удалять target-факт.
Никаких Workout facts или Credit settlements из этих строк не создано:
календарный слот, выполнение тренировки и учёт кредита независимы по
Product §§13,22.1.4,48.35–39. Синтетические тесты проверяют guest,
неизвестного клиента, неназначенную запись, дату/время, неизвестный тип и
повтор физического ID. Покрытие теперь 16 source-inspected / 27
mapping-pending / 0 target-mapped, `targetWrites=0`.

`client_day_facts` теперь читается в том же read-only снимке без смешения
с `client_measurements` и Workout/Credit Ledger. В переданном backup 76
физических client/date строк: вес заполнен в 20 (7 с десятичной запятой),
шаги в 4, текстовая отметка `training` содержит 20 «Да», 51 «Нет» и
5 пропусков. Неверных дат, владельцев, чисел и неизвестных вариантов
отметки нет. Пропуск веса или шагов не превращается в `0`; «Да» не
доказывает выполненную тренировку или списание кредита. Unit/time/provenance
веса требует дальнейшей сверки. Синтетические тесты проверяют missing/zero,
запятую, испорченные числа/дату, orphan и повтор составного ключа.
Покрытие 17 source-inspected / 26 mapping-pending / 0 target-mapped,
`targetWrites=0`.

Дневной вес теперь сохраняется отдельным date-only кандидатом с точным
десятичным текстом. `clients.weight` читается в том же снимке **только** как
недатированный сигнал сравнения, не как canonical измерение (Product §10).
На предоставленном файле 20 положительных дневных значений и 20 положительных
снимков профиля; 12 клиентов имеют оба источника, у 9 есть совпадение значения
хотя бы с одним днём, у 3 — нет. Совпадение не дедуплицирует факт, а
несовпадение не создаёт фиктивный замер. Целевые замеры = 0; подробные
[правила и открытые вопросы](R04_MEASUREMENT_FIELD_MAPPING_CANDIDATE.md).

Для пищевых записей добавлен отдельный identity/snapshot preflight внутри
того же read-only снимка. Он проверяет ID каждой вложенной записи, коллизии
ID между датами/клиентами, существование product/recipe source ID, совпадение
ID в замороженном снимке, типы макронутриентов и положительный размер порции.
Коллизия исключает **все** её вхождения из shape-complete кандидатов,
никакой `first wins` нет. На предоставленном backup 5 вложенных записей:
0 повторов ID, 0 отсутствующих ссылок на продукт, у всех 5 совпадает ID
снимка и положительны граммы. У 4 снимков КБЖУ сохранены как числа;
у 1 — как числовые строки, требующие отдельного правила проверки/конверсии.
Поэтому `shapeCompleteButUnverified=4`, `targetMappedEntries=0`,
`targetWrites=0`: даже эти четыре ещё не target-факты. Синтетические тесты
покрывают cross-client collision, отсутствующий продукт/снимок и случай,
когда оба вхождения одного валидного ID исключаются из кандидатов.
Дополнительная проверка полей будущей записи показала: 5/5 размеров порции
и итогов КБЖУ представимы ровно в ×100, 5/5 имеют явный `createdAt`, но
0/5 имеют отдельный `updatedAt`. Последний нельзя заменить временем обновления
целого дня. [Матрица полей и gates](R04_NUTRITION_FIELD_MAPPING_CANDIDATE.md).

## Справка по исходникам legacy 2.0

Read-only просмотр ветки `stable/v2.0.0-build120` на commit
`e116b42e95f70a5a5e563420ab25394944c59ffd` уточнил только поведение старого
приложения, не правила 3.0. Запись подхода ставит `completed_at` при проверке
полноты сегментов; пустой разминочный подход создаётся с `completed_at=NULL`.
При неполном подходе код может пометить строку истории `deleted_at` и обновить
сессию; отдельное удаление подхода также помечает сегменты, историю и исходный
подход. Поэтому `deleted_at` в истории не доказывает, что физический исходный
подход был удалён пользователем. Миграция 021 строила canonical session из
нескольких materialization sources и отдельно принимала часть старых строк без
`completed_at`: её результат нельзя считать независимой проверкой фактов.
См. [writer истории](https://github.com/Hwan-Karasu/fitcoach/blob/e116b42e95f70a5a5e563420ab25394944c59ffd/apps/mobile/src/features/training/data/writeTrainingExerciseHistory.ts#L53),
[удаление подхода](https://github.com/Hwan-Karasu/fitcoach/blob/e116b42e95f70a5a5e563420ab25394944c59ffd/apps/mobile/src/features/training/data/TrainingSetLogRepository.ts#L214)
и [миграцию 021](https://github.com/Hwan-Karasu/fitcoach/blob/e116b42e95f70a5a5e563420ab25394944c59ffd/apps/mobile/src/shared/db/migrations/021_training_sessions.ts#L242).
