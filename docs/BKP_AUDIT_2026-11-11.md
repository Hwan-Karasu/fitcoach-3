# BKP-AUDIT-1 — аудит и ускорение резервного копирования (2026-11-11)

Основа: build51 + HEAD `503f24b`. Срезы: `6aa11cd` (причины ошибок, меньше проходов, этапы) и следующий (нативный хеш, самопроверка).
Запрос владельца: автокопии «не восстанавливаются» (BUG-01), проверка после 100 % начинается заново (BUG-02), восстановление ~15–20 минут на копии ~70 МБ (BUG-03).
Product refs: §2, §§4, 46.1–46.6, Feature 18. Формат `.atbackup` (manifest formatVersion 3), схема БД, протокол `GuardedRestore`/журнала, retention автокопий не менялись.

## 1. Найденные дефекты и подтверждённые причины

| # | Дефект | Причина (доказана тестом реального конвейера) | Статус |
|---|---|---|---|
| D1 | Копия более новой сборки / чужая / повреждённая показывалась как «Не удалось прочитать… проверьте доступ к файлу» | `DatabaseCompatibilityError` не был `SnapshotError`, `typed()` превращал его в `SNAPSHOT_IO_FAILED` → `RESTORE_SOURCE_UNAVAILABLE`. Сценарий «автокопии build49 → установка build47» даёт именно `DATABASE_NEWER` | исправлено: `RESTORE_NEWER_BACKUP`, `RESTORE_INVALID_BACKUP`, на экране код и этап |
| D2 | Уход с экрана во время подготовки: она доходила до 100 %, результат выбрасывался | `RestoreSection` в cleanup `useEffect` вызывал `cancelPreview()` | исправлено: отмена только кнопкой, операция принадлежит сервису |
| D3 | При каждом открытии экрана (и после восстановления) — «Этап 1 из 5: копируем файл» на минуты | `refresh()` → `readPoint()` → полная проверка точки возврата (весь канонический хеш) под фазой `PREPARING` | исправлено: фаза `LOADING`, проверка по размеру и SHA-256 |
| D4 | Несколько проходов 0→100 % подряд под похожими подписями | Три полных прохода хеша в подготовке (проверка источника, повтор после преобразования, пин текущих данных) | исправлено: подготовка — один проход; процент этапа ≤ 99 % до следующего этапа |
| D5 | 11 полных проходов канонического хеша на одно восстановление | prepare 3, apply 7 (`currentContentSha256`, seal, validate, 4× `verifyPoint` в `createPoint`/`ReturnPointCompletion`, GC фото), показ экрана 1 | исправлено: 3 прохода (0 при нативном хеше) |
| D6 | 26 `PRAGMA integrity_check`+`foreign_key_check` | одни и те же байты (LIVE→SAFETY, INCOMING→LIVE) проверялись в `applyPreparedRestore`, `JournaledRestore`, `GuardedRestore.verified` | исправлено: 11 (по SHA-256 в пределах одного закрытого lease) |
| D7 | Хеш содержимого — чистый JS на Hermes | `SnapshotContentHash.ts` | исправлено: нативный двойник на Kotlin с JS-арбитром |

**Не воспроизведено (честно):**
- BUG-01 на уровне формата: ручная и автоматическая копии идут через один `sealSnapshot`/`validateSnapshot`; round-trip обеих через реальный `ExpoRestoreJobs` совпадает с эталоном построчно (клиенты, рецепты, фото). Проверялись также записанные между копией и восстановлением данные, повтор восстановления. Единственная найденная причина, по которой «автокопия не восстанавливается» — D1 (копия другой версии выглядела как «не удалось прочитать»). Фактический код ошибки владельца не получен, поэтому остаётся OPEN до проверки на телефоне: теперь вместо общего сообщения будет `Код: … · этап`.
- Незавершённые транзакции SQLite: снимок делается `backupDatabaseAsync` с `query_only`+`busy_timeout`, копия проверяется до публикации (R06-тесты).
- «Бесконечный цикл» проверки: автоматического повторного запуска в контроллере нет (подтверждено build51). Повторные прогоны были конечными: D3/D4.

## 3. Архитектура и защита данных

Единый механизм и для ручных, и для автоматических копий (один `sealSnapshot`); отдельной второй системы не создавалось.

- **Подготовка → проверка → применение сохранены.** Рабочая БД меняется только после подтверждения; перед заменой создаётся и проверяется точка возврата; замена идёт через guard/журнал R06 (14 процессных SIGKILL-тестов в foundation).
- **Пин «данные не менялись»** — `SharedSqliteDatabase.writeToken` (счётчик завершённых записей единственного писателя). Любая запись между предпросмотром и подтверждением → `RESTORE_STALE_PREVIEW`; ложные срабатывания безопасны.
- **Правило проверки по байтам.** Правильность файла — функция его байт, а байты привязаны к SHA-256. Полная проверка нужна один раз на содержимое (при создании или приёме внешнего файла); далее достаточно подтвердить SHA-256. После перезапуска процесса проверка снова полная.
- **Преобразование фото без второго хеша:** `total_changes()` растёт ровно на число фото, каждый UPDATE затрагивает 1 строку, JSON строки равен исходному с заменой только `photoUri`, набор объектов схемы заново проверен. Подставной «триггер» отвергается (тест).
- **Нативный хеш не может сделать копию невосстановимой.** Один раз за процесс самопроверка на золотой фикстуре (независимый узловой оракул): иначе нативный путь отключён. Совпадение с manifest принимается; несовпадение или сбой native → вердикт «повреждена» выносит только JS-пересчёт. Тесты: верный/лживый/падающий/всегда неверный native.
- **Журнал `[restore]`:** ID операции, фаза, код, класс исходной ошибки, миллисекунды. Без путей, имён и данных клиентов.

## 4. Замеры (ПК, Node 24 / V8, node:sqlite, один набор: БД 15,5 МБ, 30 000 рецептов + 40 клиентов + 20 фото × 300 КБ)

Реальные `ExpoRestoreJobs`/`ExpoSqliteBackup`/движок; подменён только ввод-вывод Expo. Файловый SHA-256 считается «нативно» (как `fileSha256` в APK с AUTO-BACKUP-1). Это НЕ время телефона: Hermes и мост медленнее, поэтому выигрыш по JS-хешу там больше. Файлы: `artifacts/bkp-audit/*.json`.

|---|---|---|---|---|---|---|
| build51 (до) | 3,5 с | 8,7 с | 1,0 с | **13,2 с** | 11 | 26 |

Оговорки:
- Последняя строка — оценка снизу: хеш считает `node:crypto`, а не Kotlin. Время Kotlin на телефоне не измерено.
- Основной вклад на телефоне даст нативный хеш: в build51 каждый из 11 проходов — чистый JS на Hermes (заявленные 15–20 минут на ~70 МБ).
- Профиль показал также, что без нативного `fileSha256` стенд завышал время (6,8 с JS SHA-256); поэтому «до» и «после» сняты в одинаковых условиях.

## 6. Остаётся открытым

- **BUG-01:** код ошибки владельца не известен; на телефоне после обновления смотреть строку «Код: … · этап» и лог `[restore]`/`[backup]`.
- **Kotlin-хеш (замечание ревью F1/F2):** компиляция есть, исполнения на устройстве нет. Самопроверка на золотой фикстуре (int64, ±0, ±∞, субнормальные, NULL, пустой BLOB, NOCASE, WITHOUT ROWID, составной PK, Юникод/эмодзи, перевод строки, табуляция и NUL внутри текста) выполняется один раз за процесс; при расхождении нативный путь отключается. Не покрыто фикстурой: невалидный UTF-8 в TEXT, одиночные суррогаты, строки равные при сортировке, но разных типов (1 и 1.0) в таблице без PK (порядок не гарантирован даже между сборками SQLite), строки > 2 МБ (Kotlin бросит исключение → безопасный откат на JS, но с лишней тратой времени). **Остаточный риск:** при создании копии хеш доверяется только native, а проверка готовой копии принимает совпадение native с manifest; JS-арбитр срабатывает лишь при несовпадении. Если на реальных данных native разойдётся с JS, копия получит хеш native и будет восстанавливаться, пока native работает; JS-проверка (другая сборка без модуля, провал самопроверки после обновления) признала бы её повреждённой. Для данных этого приложения (названия, JSON, числа) такие значения не ожидаются. Полное устранение требует одного JS-прохода при создании (отказ от выигрыша), поэтому принято как документированный риск; контроль — паритетный тест на устройстве владельца.
- **Время на телефоне / Hermes**, копия ~70 МБ, сворачивание приложения во время операции, реальное малое место — OPEN, нужна сборка APK и проверка владельцем.
- **Хранение:** точка возврата лежит внутри приложения и удаляется вместе с ним (текст на экране это говорит); автокопии пишутся в «Загрузки/Дневник атлета» или выбранную папку и переживают удаление приложения.
- Остаточные 11 `integrity_check` — независимые проверки (источник, кандидат, рабочая БД, снимок точки, чтения при замене); дальнейшее сокращение дало бы мало и ослабило бы защиту.
