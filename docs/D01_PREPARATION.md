## 2. Что D01 должен дать (acceptance из backlog)

Различие production/prototype; файлы версий миграций; ограничения, владельцы, внешние ключи и индексы; EXPLAIN целевых запросов. Из
`docs/adr/D01_REFERENCE_OWNER_AUDIT.md` обязательны охранные ограничения: 15 опасных сценариев чужих связей (Appointment→чужой
SessionType, FoodDiaryEntry→чужой Product, Program→чужая Cohort, смена owner/workspace у уже связанных строк) должны отклоняться на
INSERT и UPDATE обоих концов связи (кандидат — `scripts/d01/CandidateOwnerGuards.ts`).

## 3. Предлагаемый путь

1. **Базовая миграция на владельца.** Для каждого владельца — `001_baseline`, сгенерированная механически из итоговой dev-схемы
   (вместо переноса 63 промежуточных версий), плюс проверка эквивалентности: схема «baseline» равна схеме «вся dev-цепочка» с точностью до
   префикса. Дальше только добавляющие миграции.
2. **Имена.** Убрать префикс `dev_` у таблиц/индексов/триггеров скриптовым переименованием по списку из 145 имён во всех 32 файлах;
   правка проверяется всем набором foundation-тестов.
3. **Охранные ограничения и JSON.** Включить owner-guards из аудита; добавить `json_valid` двум колонкам nutrition и проверки формы
   JSON-снимков (TRN-018) триггерами/CHECK через `CASE`/`COALESCE` (правило проекта: NULL в CHECK не срабатывает).
4. **Production-реализации портов и composition root release.** Классы `Dev*Repository` получают production-имя/фабрику; `App.tsx`
   перестаёт закрывать продукт `__DEV__`; отдельный файл базы, не совпадающий с dev.
5. **R07/D06.** Транзакции, ревизии, `EXPLAIN` целевых запросов (список в отдельном приложении к срезу), общий интеграционный набор с фикстурами.
6. **Участники окончательного удаления клиента** — проверить по всем 64 таблицам (сегодня: клиентские данные покрыты; таблицы без
   клиента — каталоги и настройки — не участвуют).

Срезы: D01-1 (генератор baseline + тест эквивалентности цепочке), D01-2 (переименование, переход на baseline, импорт dev-базы), D01-3 (guards + JSON),
D01-4 (composition release), D01-5 (EXPLAIN + интеграционный набор).

## 4. Решения (владелец поручил выбрать по документации и практике команд, 2026-10-22)

Практика, на которую опираемся:
- **Миграции только вперёд, упорядоченные, каждая в транзакции; версия схемы хранится в самой базе** (`PRAGMA user_version` или журнал);
  разрушающий «пересоздай таблицы» откат недопустим — иначе у пользователя пропадут данные
  ([Room Migrations](https://commonsware.com/Room/pages/chap-migrations-001), [Room migrations — Infinum](https://infinum.com/handbook/android/common-android/room-migrations),
  [Expo: Database migrations](https://app.unpkg.com/expo-updates@57.0.10/files/guides/migrations.md)).
- **Проверять, что мигрированная база совпадает со свежесозданной** — одинаковая схема; у Room для этого генерируются файлы схемы (там же).
- **Перед крупным релизом старые миграции сворачивают в одну базовую** (squash), пока в обращении нет баз, которым нужна старая цепочка; прежние файлы
  архивируют ([OpenProject: migration squashing](https://www.openproject.org/docs/development/migrations/), [squasher](https://github.com/tobmatth/squasher));
  стандартная схема Rails: «новая база создаётся загрузкой итоговой схемы, а не прогоном всей истории».
  Предупреждение оттуда же: данные, которые вставляли старые миграции (начальные строки), нужно перенести в базовую миграцию явно.
- **SQLite:** внешние ключи включать на каждом соединении (`PRAGMA foreign_keys=ON`), проверять `foreign_key_check`; ограничения `CHECK` работают при вставке и
  обновлении ([SQLite STRICT tables](https://sqlite.org/stricttables.html)); таблицы `STRICT` — строгие типы колонок (по желанию, отдельным срезом).
- Про префиксы имён таблиц источники ничего не говорят; общее правило: в имени таблицы не должно быть признака окружения (`dev_`) — в production-схеме он вводит в заблуждение.

Принятые решения:
1. **Базовая миграция на владельца** вместо переноса 63 шагов: production — новая установка (данные 2.0 придут через D03/D04). Да.
2. **Префикс `dev_` убираем** у таблиц, индексов и триггеров (кроме диагностической `dev_boot_marker` отдельного dev-файла). Делается один раз сейчас, пока production-баз нет:
   потом переименование потребует миграции на каждом устройстве. Коллизий имён после удаления префикса нет (проверено).
3. **Имя файла production-базы:** `fitcoach_v3.db`, отдельный от dev-файлов; имя файла 2.0 в документах не зафиксировано — при установке поверх 2.0 (R02–R04) приложение обязано
   отказаться открывать файл без своего журнала миграций, а не «молча» работать с чужой схемой.
4. **Данные dev-базы владельца сохраняются:** новая dev-база заполняется из старой одноразовым импортом (таблица в таблицу, проверка `foreign_key_check`);
   в production они не попадают. SmokeA/B/C не теряются.
5. **Исторический снимок без источника:** запись дневника самодостаточна (снимок), ссылка на удалённый/архивный продукт допустима и помечается как архивная;
   физическое удаление продукта, использованного в дневнике, запрещено. Основание: аудит D01 (ссылка по `id` не доказывает владение) и правило проекта «факты не уничтожаются».
6. **Строгость JSON:** повреждённая строка не записывается (CHECK `json_valid`), а чтение устойчиво (строка пропускается и показывается ошибка), как уже сделано для состава дневника.

## 5. Риски

- Механическое переименование 145 имён — широкий diff; смягчается полным набором тестов и проверкой «baseline = dev-цепочка».
- Production DDL — необратимо после выхода релиза: добавляющие миграции только вперёд, поэтому до релиза схему нужно проверить на EXPLAIN и restore (D05/R06).
- Не проверено на реальном Android: открытие/миграция production-файла и откат при обрыве (R05/R06).

## 6. Что не входит

Бэкап и восстановление (D05/B01), миграция 2.0 (D03/D04/I01), release-сборка (R01).

## 7. Ход работ

   файлы не отстают от цепочки (перегенерация даёт тот же текст). **На момент D01-1 в приложение не подключалось; dev-подключение добавлено в D01-2.** Перегенерация: `npm run d01:baseline`
  (с Node 24 из devDependencies флаг `--experimental-sqlite` не нужен).
- **D01-2 (2026-10-22) — реализован, host-проверки пройдены; Android OPEN.** Репозитории и подготовка dev-схемы используют baseline v1 каждого владельца.
  Прежние 63 шага сохранены в `scripts/d01/history/` для генератора и исторических тестов, runtime их не импортирует. У объектов данных убран `dev_`.
  Новый dev-файл — `fitcoach_dev_v3.db`; прежний `fitcoach_f04_clients_dev.db` остаётся источником одноразового копирования без удаления или изменения его строк.
  Production-файл `fitcoach_v3.db` не открывается этим кодом.
  - Порядок boot: baseline всех владельцев → импорт → обычная инициализация/засев. При ошибке импорта boot получает `MIGRATION_INCOMPLETE`, засев не начинается,
    целевые строки откатываются, отметка успеха не ставится; Retry повторяет импорт. Ошибка больше не скрывается в `console.log`.
  - Непустая новая база без отметки импорта вызывает `LEGACY_IMPORT_TARGET_NOT_EMPTY`: данные не смешиваются и постоянная отметка пропуска не записывается.
    Уже завершённый импорт повторно не выполняется. Если в прежнем файле нет dev-таблиц, фиксируется `SKIPPED_NO_LEGACY` и начинается обычная новая установка.
  - Импорт рассчитан на итоговую dev-схему перед D01. Неизвестная dev-таблица или несовпадающий набор колонок останавливает перенос; старые промежуточные схемы
    не обновляются скрыто и неизвестные данные не отбрасываются. Журналы прежних миграций не копируются в новую базу.
  - Проверки: `npm run d01:test` (11 тестов), `npm run test:foundation` (696 тестов), `npm run typecheck`, `npm run lint`, `npm run arch:check`, `npm run source:verify`.
    Проверены равенство baseline архивной цепочке; все значения строк в 64 таблицах; FK; отсутствие дубликатов; откат частичного переноса;
    отказ на несовместимой схеме; закрытие соединений; сбой boot и успешный Retry на временных SQLite-файлах. Исторические тесты также проверяют перенос своих фикстур в baseline.
  - Живые dev-данные владельца не открывались и не переносились. Открытие через Expo на Android и прерывание процесса на устройстве ещё не проверены.
- **D01-3 (2026-10-22) — реализован, host-проверки пройдены; Android OPEN.** Добавлены миграции v2 для clients, accounting, nutrition, training plans и execution.
  Baseline v1 и архив 63 шагов не переписаны. Существующие строки проверяются перед установкой новых ограничений: несоответствие откатывает миграцию,
  не удаляет данные и не продвигает журнал. Схема после baseline→v2 совпадает со свежей установкой.
  - Проверки принадлежности текущей схемы: составные FK уже защищают тип занятия, пакет, ингредиенты рецепта и участие в программе;
    добавлены запрет смены идентичности клиента/программы/источников питания, проверки источников пищевого дневника, резервов/Ledger,
    workspace у сторон и дропов подхода. Исторические указатели на план не превращены в FK, уничтожающие независимость фактов.
    У исходной reference-схемы были Cohort/Program; в runtime вместо неё используются Program/Member/Mesocycle с составными FK и прежними owner-триггерами.
  - Самодостаточный пищевой снимок допускает отсутствующий источник. Существующий источник должен быть из своего workspace;
    архивирование допустимо, физическое удаление использованного продукта/рецепта запрещено. Появление чужого каталожного объекта с ID отсутствующего источника также запрещено.
    Коррекция клиента календарного занятия сначала снимает прежний резерв и пишет компенсацию в той же транзакции; исторические списания прежнего клиента не переписываются.
  - На INSERT и UPDATE проверяются синтаксис и форма состава пищи, сохранённых наборов, пакетных команд и основных JSON-снимков тренировок.
    Все девять участков TRN-018 используют проверку формы при чтении: версии, шаблоны, черновики, недельные отличия и происхождение выполнения.
    Повреждённая строка пропускается; чтение её не удаляет и не переписывает. Итоги еды не включают пропущенные строки.
  - Сообщение в интерфейсе: «Не удалось прочитать часть записей. Остальные данные доступны». Технических кодов и содержимого записей в нём нет,
    сообщение можно скрыть. Обычная запись не может создавать такие строки через новые ограничения. UI и сценарий повреждения на Android ещё не проверены.
  - Исправлено включение FK на транзакционном соединении. В установленной Expo SQLite `withExclusiveTransactionAsync` создаёт новый handle и запускает BEGIN до callback;
    включение FK на основном handle недостаточно, а внутри транзакции PRAGMA уже не действует. Адаптер теперь открывает отдельное соединение с `useNewConnection`,
    включает и проверяет FK до `BEGIN IMMEDIATE`, проверяет WAL и закрывает handle после commit/rollback. WriterCoordinator остаётся общим на файл.
  - Проверки: `npm run test:foundation` — 704 теста; `npm run d01:test` — 19 тестов; typecheck, lint, arch:check.

    пропуск повреждённого черновика с сигналом для UI, FK на каждом отдельном SQLite-соединении и продолжение записи после rollback.
