Различие production/prototype; файлы версий миграций; ограничения, владельцы, внешние ключи и индексы; EXPLAIN целевых запросов. Из

## 3. Предлагаемый путь

1. **Базовая миграция на владельца.** Для каждого владельца — `001_baseline`, сгенерированная механически из итоговой dev-схемы
   (вместо переноса 63 промежуточных версий), плюс проверка эквивалентности: схема «baseline» равна схеме «вся dev-цепочка» с точностью до
   префикса. Дальше только добавляющие миграции.
2. **Имена.** Убрать префикс `dev_` у таблиц/индексов/триггеров скриптовым переименованием по списку из 145 имён во всех 32 файлах;
   правка проверяется всем набором тестов (680).
3. **Охранные ограничения и JSON.** Включить owner-guards из аудита; добавить `json_valid` двум колонкам nutrition и проверки формы
   JSON-снимков (TRN-018) триггерами/CHECK через `CASE`/`COALESCE` (правило проекта: NULL в CHECK не срабатывает).
4. **Production-реализации портов и composition root release.** Классы `Dev*Repository` получают production-имя/фабрику; `App.tsx`
   перестаёт закрывать продукт `__DEV__`; отдельный файл базы, не совпадающий с dev.
5. **R07/D06.** Транзакции, ревизии, `EXPLAIN` целевых запросов (список в отдельном приложении к срезу), общий интеграционный набор с фикстурами.
6. **Участники окончательного удаления клиента** — проверить по всем 64 таблицам (сегодня: клиентские данные покрыты; таблицы без
   клиента — каталоги и настройки — не участвуют).

Срезы: D01-1 (генератор baseline + тест эквивалентности цепочке), D01-2 (переименование, переход на baseline, импорт dev-базы), D01-3 (guards + JSON),
D01-4 (composition release), D01-5 (EXPLAIN + интеграционный набор).

## 4. Решения (владелец поручил выбрать по документации и практике команд, 2026-10-22)

Практика, на которую опираемся:
- **Миграции только вперёд, упорядоченные, каждая в транзакции; версия схемы хранится в самой базе** (`PRAGMA user_version` или журнал);
  разрушающий «пересоздай таблицы» откат недопустим — иначе у пользователя пропадут данные
  ([Room Migrations](https://commonsware.com/Room/pages/chap-migrations-001), [Room migrations — Infinum](https://infinum.com/handbook/android/common-android/room-migrations),
  [Expo: Database migrations](https://app.unpkg.com/expo-updates@57.0.10/files/guides/migrations.md)).
- **Проверять, что мигрированная база совпадает со свежесозданной** — одинаковая схема; у Room для этого генерируются файлы схемы (там же).
- **Перед крупным релизом старые миграции сворачивают в одну базовую** (squash), пока в обращении нет баз, которым нужна старая цепочка; прежние файлы
  архивируют ([OpenProject: migration squashing](https://www.openproject.org/docs/development/migrations/), [squasher](https://github.com/tobmatth/squasher));
  стандартная схема Rails: «новая база создаётся загрузкой итоговой схемы, а не прогоном всей истории».
  Предупреждение оттуда же: данные, которые вставляли старые миграции (начальные строки), нужно перенести в базовую миграцию явно.
- **SQLite:** внешние ключи включать на каждом соединении (`PRAGMA foreign_keys=ON`), проверять `foreign_key_check`; ограничения `CHECK` работают при вставке и
  обновлении ([SQLite STRICT tables](https://sqlite.org/stricttables.html)); таблицы `STRICT` — строгие типы колонок (по желанию, отдельным срезом).
- Про префиксы имён таблиц источники ничего не говорят; общее правило: в имени таблицы не должно быть признака окружения (`dev_`) — в production-схеме он вводит в заблуждение.

Принятые решения:
1. **Базовая миграция на владельца** вместо переноса 63 шагов: production — новая установка (данные 2.0 придут через D03/D04). Да.
2. **Префикс `dev_` убираем** у таблиц, индексов и триггеров (кроме диагностической `dev_boot_marker` отдельного dev-файла). Делается один раз сейчас, пока production-баз нет:
   потом переименование потребует миграции на каждом устройстве. Коллизий имён после удаления префикса нет (проверено).
3. **Имя файла production-базы:** `fitcoach_v3.db`, отдельный от dev-файлов; имя файла 2.0 в документах не зафиксировано — при установке поверх 2.0 (R02–R04) приложение обязано
   отказаться открывать файл без своего журнала миграций, а не «молча» работать с чужой схемой.
4. **Данные dev-базы владельца сохраняются:** новая dev-база заполняется из старой одноразовым импортом (таблица в таблицу, проверка `foreign_key_check`);
   в production они не попадают. SmokeA/B/C не теряются.
5. **Исторический снимок без источника:** запись дневника самодостаточна (снимок), ссылка на удалённый/архивный продукт допустима и помечается как архивная;
   физическое удаление продукта, использованного в дневнике, запрещено. Основание: аудит D01 (ссылка по `id` не доказывает владение) и правило проекта «факты не уничтожаются».
6. **Строгость JSON:** повреждённая строка не записывается (CHECK `json_valid`), а чтение устойчиво (строка пропускается и показывается ошибка), как уже сделано для состава дневника.

## 5. Риски

- Механическое переименование 145 имён — широкий diff; смягчается полным набором тестов и проверкой «baseline = dev-цепочка».
- Production DDL — необратимо после выхода релиза: добавляющие миграции только вперёд, поэтому до релиза схему нужно проверить на EXPLAIN и restore (D05/R06).
- Не проверено на реальном Android: открытие/миграция production-файла и откат при обрыве (R05/R06).

## 6. Что не входит

Бэкап и восстановление (D05/B01), миграция 2.0 (D03/D04/I01), release-сборка (R01).
