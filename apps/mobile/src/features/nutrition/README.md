## UX FatSecret, 21.10.2026

Актуальная сверка 15 экранов и 92 требований, результаты проверок и ограничения:
`docs/ui/NUTRITION_FATSECRET_ACCEPTANCE_2026-10-21.md` (от корня репозитория).
Клиентские сохранённые наборы — отдельные снимки; рецепты — общий локальный каталог.
Dev v11–v14: наборы, optional recipe details, отдельная история запросов, idempotency receipts пакетных записей.
UI использует порты; `editEntry` сохраняет массу/слот/override атомарно. Фотографии — локальные файлы.
Это dev-реализация: production D01, build120 migration, backup/restore и полная UI-приёмка остаются OPEN.
Описания исходных срезов ниже исторические, уточняются решениями ADR-025/026/027 и указанной сверкой.

Продукты, рецепты, снимки порций, дневник и действующие по датам цели.
Обновление каталога не изменяет историческое потребление.

Dev-only срез N01 ч.1 (`data/DevFoodCatalogRepository.ts`) живёт в общем dev-файле, журнал миграций
`nutrition_schema_migrations`. Таблица `dev_food_products` — общий каталог рабочего пространства (не привязан к клиенту).

- Собственный продукт (§49.3): название, марка, эталон `100 г` / `100 мл` / порция и значения ккал, Б, Ж, У
  в десятых долях. Незаполненный нутриент — `null`, а не ноль; продукт без единого значения отклоняется.
- `scaleNutrients` — пересчёт на фактическое количество (§49.3.3); нулевое или нечисловое количество — `INVALID_PORTION`.
- Удаление из каталога — скрытие (`archived_at`): `get(id)` по-прежнему читает скрытый продукт для истории (§49.5.2).
  Правка меняет только будущие использования; revision — защита от устаревшей правки.

N01 ч.2 (`data/DevRecipeCatalogRepository.ts`, миграция v2): рецепт из продуктов каталога (§49.4) — итог только сумма ингредиентов,
неизвестный нутриент ингредиента делает итог неизвестным. Дневник получает основы «1 порция» и «100 г» (последняя — только при указанной
массе готового блюда, без выдуманной массы). `FoodSnapshot` (`snapshotOfFood/Recipe`) — неизменяемый снимок для дневной записи
(§49.5.1): правка продукта и рецепта прошлые дни не меняет, состав рецепта в сумму дня повторно не входит. Состав заменяется целиком;
скрытый продукт нельзя добавить в рецепт заново, но он остаётся в рецептах, где уже был (FK не даёт физически удалить ингредиент).

N02 (`data/DevNutritionDiaryRepository.ts`, миграция v3): пищевой дневник клиента (§49.1–49.5, 49.22). Запись = снимок + количество + слот
(Завтрак/Обед/Ужин/Перекус) + дата; «съедено» считается из снимка, количества и отдельного override. Правка записи сохраняет массу/слот/override атомарно;
итог дня — сумма записей как в 2.0 (неизвестное = 0, неизвестен только если неизвестен во всех записях; калории без числа — из Б/Ж/У 4/9/4, ADR-028). Вода — отдельная сумма за день: еду и «день с учётом»
не создаёт. «День с учётом» (П15=B) — есть хотя бы одна пищевая запись (`accountedDates`). `devNutritionClientDeletionParticipant` подключён
к окончательному удалению клиента. Все чтения и записи ограничены `clientId`.

N03 (`data/DevNutritionTargetsRepository.ts`, миграция v4): цели питания клиента — коридоры `min–max` по ккал/Б/Ж/У (§49.8), расписание по дням недели
(§49.9), датированные версии с даты действия (§49.11) и разовые исключения даты (§49.12). Приоритет: исключение → версия на дату → «цель не установлена»
(`resolveTarget`). Версия на ту же дату молча не заменяется (`TARGET_VERSION_EXISTS`, правка с revision); прошлые версии не удаляются; `min > max` не исправляется молча.
`assessDay` сравнивает показатели независимо; день без еды и неизвестное значение дают `UNKNOWN`, а не «ниже». `energyConsistency` — предупреждение о несовместимости калорий
и макродиапазонов, значения не меняет. Участник удаления клиента: `devNutritionTargetsClientDeletionParticipant`.

N04 (`domain/NutritionStats.ts`, чистые правила без хранилища): статистика питания по внесённым записям (§49.22). Среднее — по учтённым дням
с известным значением показателя (две даты: 450 и 2100 → 1275 за 2 дня); доля попаданий = дни в коридоре / дни с известным значением и коридором на дату
(5 из 8 → 62,5 %, нулевой знаменатель → `null`, «—»). Неизвестный показатель исключается только из своего расчёта. `days` — все даты периода как общий
знаменатель графиков. Вода и пустые дни не учитываются. Веса и замеры берутся из Measurements (`clientBodyweight`), здесь не дублируются.

Границы: предложение коридоров П6 удалено по решению владельца; экраны, вода, копирование и участники удаления реализованы в dev.
Production схема/миграция build120 и восстановление через релизный backup-протокол не завершены.


## A02: КБЖУ на главной (2026-10-20, актуальнее исторического описания N03 выше)

`CalcRules` рассчитывает калории существующими формулами. БЖУ требуют сухой массы из веса и % жира;
приближение 80 % веса удалено. `HomeMacroTargets` формирует один результат для сводки и сохранения.
«Коридор» действует и без ручного ввода: белок ±10 % от точного, жир 0,8–1 г/кг сухой массы, углеводы по остатку.
В ручном ряду только явные значения: при вводе У пересчитывается Б, при вводе Б/Ж — У, жир последним.
Недопустимый остаток или диапазон жира блокируют сохранение; три ручных значения определяют калории по 4/9/4.
При одном/двух ручных значениях исходный калораж не заменяется суммой округлённых макро.

`TargetVersionInput.homeAdjustment` хранит режим и nullable ручные Б/Ж/У отдельно от итоговых `days`.
Dev migration v10 добавляет nullable JSON; запись происходит в той же транзакции с CAS, без production DDL.
Старые версии имеют `homeAdjustment = null` и не заменяют формулу главной. UI расписания удалён;
исторический resolver остаётся для дневника и статистики. Автоматический просмотр ничего не записывает.
Нижние поля первоначально пустые, восстанавливается только сохранённый ручной ввод. Ссылка на недостающий % жира
открывает вкладку «Расчёт» у текущего клиента; оценка ВМС применяется только явным действием тренера.

## Аудит 2026-10-21, ADR-029

Цель дня = расчёт главной с ручной корректировкой на дату (`corridorsForDate`); её используют дневник, главная и статистика (`computeNutritionStats({ corridorsFor })`). Особая цель на дату в UI не нужна. `recipeTotals` считает как сумма дня (неизвестное = 0, калории из известных Б/Ж/У). Единица продукта из рецепта не меняется (`FOOD_UNIT_LOCKED`); `editEntry` принимает `copyToSlots`.

Правка продукта меняет будущие значения всех рецептов с ним (рецепт хранит ссылки на продукты, не копии); история дневника защищена снимками. Единственный путь правки дневной записи — `editEntry` (количество, приём, правка К/Б/Ж/У, копии в другие приёмы); отдельные `updateQuantity`/`moveEntry`/`setOverride`/`clearOverride` удалены (аудит, этап 4).
