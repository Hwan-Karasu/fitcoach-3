# FitCoach 3.0 — правила для Claude Code

@AGENTS.md

Отвечать владельцу всегда по-русски, включая вопросы и описания команд.

## 1. Протокол памяти

- **Перед любой задачей** прочитать `memory-bank/` (все 5 файлов). После
  старта сессии и после сжатия контекста их содержимое подставляет хук
  SessionStart; если его нет в контексте — прочитать файлы вручную.
- **После завершения задачи** (и по командам «обнови память» / «смена»)
  актуализировать:
  - `activeContext.md` — дата, последние коммиты, текущий фокус, следующий шаг;
  - `progress.md` — что сделано, новый техдолг (с файлом и строкой);
  - `decisions.md` — новое техническое решение в формате ADR.
- Банк памяти — короткая выжимка. Подробный журнал среза пишется в
  `docs/PROJECT_STATUS.md` (новое сверху), UI-решения — в
  `docs/ui/UI_STYLE_DECISIONS.md`. Не дублировать их целиком.
- Не записывать в память секреты, пути к ключам, реальные данные клиентов.

## 2. Технические правила

**Стек:** Expo 57, RN 0.86, React 19, TypeScript strict, React Navigation 7,
expo-sqlite, RNGH + Reanimated 4 + worklets. Новые библиотеки — только с
согласия владельца и через `npx expo install` (совместимые с SDK версии).

**Слои и границы**
- Фича: `domain/` (модель, правила, порты) → `data/` (адаптер) →
  `presentation/`; наружу — только `public.ts`.
- Чужая фича — только через её `public.ts`. Кросс-модульная запись — в
  `workflows/`, производное чтение — в `read-models/`.
- UI не импортирует SQLite и `data/`. Сервисы получает из composition root
  (`app/composition/createDevServices.ts`).

**Данные**
- Запись — только `WriterCoordinator.write(tx => …)`, одна транзакция на
  команду; CAS по `revision`; `publish` подписчикам — после commit.
- Новая таблица — миграция в журнале своего владельца
  (`<owner>_schema_migrations`), никогда не правка старой миграции.
- Ограничения целостности — в схеме (CHECK, триггеры): учитывать, что NULL в
  CHECK/`WHEN NOT …` не срабатывает — использовать `CASE`/`COALESCE`.
- Новые данные клиента → участник окончательного удаления (owner/tables/count).
- Факты не уничтожаются: отмена/исправление — новой записью или статусом.

**UI**
- Цвета только из токенов темы (`usePrototypeTheme()`), никаких hex в экранах.
- Сначала искать компонент в `shared/ui/components/public.ts`; новый общий
  элемент — туда же, а не копию в экран.
- Геометрия, шрифт, иконки, шапки — по `docs/ui/UI_STYLE_DECISIONS.md`.
- Одна строка шапки, без второй дублирующей «← назад».
- Hit-area ≥ 48dp, `accessibilityLabel` у иконок, тексты на русском,
  неразрывные пробелы через ` `.

**Утечки и производительность**
- Каждая подписка (`subscribe`, слушатели, таймеры) возвращает и вызывает
  отписку в cleanup `useEffect`.
- Объекты жестов RNGH и тяжёлые колбэки — в `useMemo`/`useCallback` с refs;
  функции геометрии для жестов помечать `"worklet"`, в JS — `scheduleOnRN`.
- Не держать в state то, что вычисляется из props/снимка.

**Тесты**
- `node --experimental-strip-types --test`; dev-хранилища тестируются через
  `scripts/support/node-sqlite-port.ts`.
- Тест, импортирующий `.tsx` через `public.ts`, — в `apps/mobile/scripts`.
- Новый тест-файл добавить в `test:foundation` в корневом `package.json`.

**Как писать тесты**
- Проверять поведение через публичный интерфейс (порт, `public.ts`, правило
  домена), а не внутренности. Прямой SQL в тесте — только для правил
  целостности самой схемы (CHECK, триггеры).
- Ожидаемое значение — из независимого источника: пример из спецификации,
  заранее известный литерал. Не пересчитывать его тем же кодом, что и в
  реализации.
- Не мокать внутренние модули; подменять только внешнюю границу (SQLite →
  `node-sqlite-port`, время → параметр `now`).
- Тест и код — маленькими срезами: один сценарий → падающий тест → минимальный
  код. Без кода «на вырост».

**Как искать баг**
1. Сначала быстрый повторяемый сигнал «красный/зелёный» (тест, скрипт,
   шаги на телефоне). Без него гипотез не строить.
2. Воспроизвести и сократить сценарий до минимального.
3. 3–5 проверяемых гипотез с предсказанием, проверять по одной, логи с
   тегом (`[bug-x]`); для скорости — сначала замер.
4. Регрессионный тест до исправления, затем фикс.
5. Убрать отладочный код; подтверждённую причину — в сообщение коммита.
   Секреты и данные клиентов в логи и артефакты не попадают.

**Нельзя**
- Повышать статусы без доказательства; начинать production DDL, миграцию
  build120, overlay APK, release до gates.
- Открывать/коммитить `*.atbackup`, `*.jks`, `*.pem`, `keystore.properties`.
- Удалять синтетических клиентов SmokeA/B/C; трогать реальных клиентов.
- Переносить код или правила из build120 автоматически.
- Писать правки через heredoc/`node -e` с обратными кавычками — только
  Write/Edit или `.cjs`-скрипт в scratchpad.
- Делать `git push` без просьбы.

## 3. Алгоритм задачи

1. **Анализ:** прочитать `memory-bank/`, нужный README фичи и пункты
   нормативного пакета; назвать task ID, входы, Product refs, открытые gates.
2. **План:** коротко — какие файлы и зачем, как проверить.
3. **Согласование:** спросить владельца, если решение за ним (продукт, UI,
   новая зависимость, gate, необратимое действие). Рутинный срез по backlog —
   делать сразу.
4. **Правки:** точечно, в стиле соседнего кода, без лишних слоёв и
   рефакторинга вне задачи.
5. **Проверка:** `npm run typecheck`, `npm run lint`, `npm run arch:check`,
   `npm run source:verify`, `npm run secrets:check`, нужные `*:test` или
   `test:foundation`; для UI — проверка на телефоне через Expo Go.
6. **Фиксация:** запись в `docs/PROJECT_STATUS.md`, коммит среза
   (сообщение по-русски, `<ID>: что сделано`).
7. **Память:** обновить `activeContext.md`, `progress.md`, `decisions.md`.
